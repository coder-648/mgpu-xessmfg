# gpu_codec —— 同一份 HLSL 码流在所有显卡上跑一遍

回答一个具体问题：**双卡混搭（N/A）时，"谁编谁解" 的四种组合要不要各测一遍？**
不需要四份测试，因为码流与厂商无关；需要证明的是两件事，这个工具都测：

1. **每个适配器上 `decode(encode(x)) == x`**（正确性）
2. **每个适配器产出的压缩字节逐字节相同**（可互换）

有了这两条，`N→N / N→A / A→N / A→A` 四种组合同时成立（并且每条流还要与
CPU 参考实现 `fr_codec.h` 的字节一致，防止"自洽但错"）。

```bash
./scripts/build_gpu_codec.sh --list                       # 列出适配器
./scripts/build_gpu_codec.sh --all --w 3840 --h 2160 --nw 2
./scripts/build_gpu_codec.sh --all --raw 'E:\mgpu_dataset\...\f00_mv.raw'
```

`--nw 1` = R32/RG16F（MV、depth），`--nw 2` = RGBA16F（colour）；
`--pattern 0|1|2` 是合成数据（MV 风格 / 纯噪声 / 全零）。

## 2026-11-21 实测（RX 6750 GRE + RTX 3080 Ti，真实 dump 帧）

码流 **v1**（每 tile 取最大位宽）：

| 流 | AMD enc | AMD dec | NV enc | NV dec | 比率 | 字节一致 | 回环 | vs CPU |
|---|---|---|---|---|---|---|---|---|
| MV 4K 33.2 MB | 2.854 ms | **6.402 ms** | 2.286 ms | 1.203 ms | 1.54x | ✅ | ✅ | ✅ |
| depth 4K 33.2 MB | 2.643 ms | 6.125 ms | 2.202 ms | 1.211 ms | 1.88x | ✅ | ✅ | ✅ |
| colour 4K 66.4 MB | 5.763 ms | 10.300 ms | 3.343 ms | 3.110 ms | 1.19x | ✅ | ✅ | ✅ |

码流 **v2**（例外编码，`n_out=0` 退化成 v1；**当前 HEAD**）：

| 流 | AMD enc | AMD dec | NV enc | NV dec | 比率 v1→v2 | 字节一致 | 回环 | vs CPU |
|---|---|---|---|---|---|---|---|---|
| MV 4K 33.2 MB | 3.02 ms | 5.49 ms | 2.89 ms | 1.51 ms | **1.54 → 2.81x** | ✅ | ✅ | ✅ |
| depth 4K 33.2 MB | 2.86 ms | 5.58 ms | 2.86 ms | **1.23 ms** | **1.88 → 2.37x** | ✅ | ✅ | ✅ |
| colour 4K 66.4 MB | — | — | 4.66 ms | 4.25 ms | **1.19 → 1.45x** | ✅ | ✅ | ✅ |

演进（同一份位流，都 bit-exact；tile 固定 256 值）：

| 形状 / 几何 | NV dec | AMD dec | 备注 |
|---|---|---|---|
| 一线程一 tile + 逐字节 + 16×16 | 2.03 | 6.16 | 第一版 |
| 一线程一 tile + 按字 + 无暂存 | **1.51** | 5.49 | 3a |
| block-per-tile + 16×16 | 2.15 | 4.06 | 3b |
| block-per-tile + **32×8** | **0.91** | **3.79** | 当前 HEAD |
| block-per-tile + 64×4 | 1.28 | 4.25 | |
| block-per-tile + 128×2 | 1.23 | 5.49 | |
| block-per-tile + 256×1 | 1.49 | 6.53 | 无垂直预测 |

**几何决定成败**：32×8 让每行写满 128 B（一整条 cache line），同时保留 8 行垂直预测 ——
速度和比率同时最好（MV p50 2.71 / depth 2.56 / colour 1.46）。
（4K、33 MB、合成 MV 型、`--iters 5`；真帧 MV：NV 编码 2.25 / 解码 1.18。）

**编码端也并行化**（block-per-tile，每线程一个值，每 warp 独立直方图）：2.87 → **1.22 ms**。

当前两卡（4K、单流 33 MB、真帧）：

| 流 | NV enc | NV dec | AMD enc | AMD dec |
|---|---|---|---|---|
| MV（4K 33.2 → 11.2 MB，2.97x） | 1.02 | **0.58** | 1.38 | 1.98 |
| depth（4K 33.2 → 13.6 MB，2.44x） | 1.02 | 0.72 | 1.41 | 2.08 |
| 1080p（8.3 MB 单流） | **0.23** | **0.15** | **0.87** | **0.64** |

AMD 的固定开销：全零输入（不读任何位）解码仍要 2.04 ms，而纯拷贝地板 0.97 ms
⇒ 剩下的 1.07 ms 全在块扫描 / 行扫描 / barrier / LDS 上。

**消融地图**（临时改一行、跑一次、回退）：

| 消融 | 结果 |
|---|---|
| AMD 解码跳过块扫描 | 2.04 → 1.70 ms（块扫描 = 0.34 ms）|
| NV 编码跳过 e_out 原子 | 1.02 → 0.85 ms（原子 = 0.17 ms）|
| AMD 解码喂全零（width=0）| 2.04 ≈ 真实 1.98 → 位解包不是瓶颈 |

下一步：① 每行位偏移表（−0.34 ms，+4.6% 字节）；② 编码按输出字分工替代原子；③ 每 block 2 个 tile 摊薄 barrier。

剩余瓶颈（已定位）：解包仍是每值一次标量 `Src.Load`（未向量化）、行内 O(c) 求和未换 scan、
AMD 的 LDS/barrier 代价约为 NV 的 4×（需单独 profile）。

1080p 参考：NV 解码 0.34 ms/流、编码 1.12 ms/流。

读这些行要知道的事：

- **比率和 CPU 参考逐字节一致**（v1 1.54/1.88/1.19，v2 2.81/2.37/1.45），
  说明 HLSL 与 `fr_codec.h` 是同一份规格；
- **字节跨厂商完全一致**：NV 编的字节 AMD 能解，反之亦然 —— 四种组合一次覆盖；
- **这些 ms 是"参考形状"的耗时，不是生产耗时**。当前 shader 是一个线程干一个
  16×16 tile（v2 编码要对同一个 tile 扫四遍：直方图 / mask / 值 / patch），
  编码只有 7–14 GB/s；目标形状（流式 + warp 协作直方图，CUDA 实测 0.13 ms/66 MB
  ≈ 500 GB/s）要快 30–40 倍。
- 它暴露了一个**真实的、会在优化后依然存在**的问题：**AMD 的解码比 NV 慢 3 倍**。
  当前的解码虽然已经把残差先全解出来（v2 的 `z[]`），但"重建"那一步仍然是
  "每个像素读左邻居"——一条 256 长的依赖链。**上生产前必须把重建也改成
  每行 inclusive scan**，这样 A 卡当消费端时才不会被拖死。
