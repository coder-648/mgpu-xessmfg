# 进度与基线确认（2026-11-15）

## 1. 目标

双卡 FG（游戏在 NVIDIA，`xess_mfg_consumer.exe` 在 AMD + XeFG）下，
在**输入帧率会波动**的前提下，让显示帧率稳定在指定上限附近、间隔平滑。
动态逐帧 = 倍率随负载自适应，但 pacing 不被逐帧改动打散。

## 2. 当前结论（一句话）

- **固定倍率 + 输入驱动 + 小队列**是已验证的平滑基线，生产上可用；
- **动态逐帧继续沿 bridge 式 carry（相位进位 + hold）迭代**，
  epoch 档位/out-clock/逐帧 m,k 选择已证伪，保留为 A/B。

## 3. 基线数据（用户实测，均为 4K/den1、MV+depth 全用）

### 3.1 固定倍率（游戏外部锁帧）

| 指标 | 3x / queue1 / 锁40 | 4x / queue1 / 锁30 | 3x / queue2 | 4x / queue2 |
|---|---|---|---|---|
| show 均值 / 峰 | 117.0 / 122 | 115.2 / 120 | 117.6 / 121 | 116.1 / 120 |
| load 均值 / 峰 | 28.9 / 95 | 65.4 / 123 | 92.0 / 98 | 93.6 / 101 |
| capture 均值 | 0.1 ms | 3.4 ms | 25.1 ms | 19.8 ms |
| pf served / missed | 2233 / 2 | 2106 / 3 | 2639 / 1 | 1995 / 3 |
| HITCH | **0** | 3 | **0** | **1** |
| reset-history | 3 | 8 | 2 | 4 |

- queue2 的 load 变高是把“capture 等待”转移到“gpu 等待”（后者计入 load），
  `total` 基本不变，不是变慢；代价是延迟 +1 帧。
- 4x cq2 唯一一次卡顿是 251 ms 的 `colour=209.9ms` 拷贝停顿（系统/GPU 层），
  不是 cadence。

### 3.2 动态方案对照

| 指标 | epoch 档位 | carry（hold 8） |
|---|---|---|
| k 分布 | 2×32 窗，3×7 窗 | 2×17，3×19，4×3 |
| out 均值 | 96.9 Hz | 约 120 Hz |
| show 均值 | **87.5** | **112.5** |
| switches | 3 / 39 窗 | 197 / 39 窗（≈5/窗） |
| HITCH | **16** | **2** |

结论：**carry 胜出**。长期平均贴住 120、HITCH 少；epoch 会在低档停很久再整档跳变。

### 3.3 已否决的路径（数据留档）

- **逐帧 mean/phase（bres）**：15–31 switches/s，输出 90–93 Hz，HITCH 多；
  每次 `SetNumInterpolatedFrames` 在这份 pacer 上约丢 1 张输出。
- **optimal (m,k,paced)**：4K 4x 会 `ERR_OTHER`/只出 1 张；没有可实现性反馈时卡死。
- **out-clock（缓存捕获帧 + QPC tick）**：capture 等待 78–87 ms，
  prefetch 命中从 40/40 掉到 13–17/40，4x load 89–95%，比固定 4x 更差。
- **epoch 档位**：50 fps 下停在 k=2/100 Hz，show 87.5、HITCH 16。

## 5. 动态逐帧：carry 迭代路线

当前实现（已经落地）：

```
phase += want                       // want = T_in × target / 1000
k      = round(phase)
k      = min(k, ceil(want))         // bridge over-refresh guard
if (k != current && |phase-k| > deadband && 驻留 >= hold)
    k = current ± 1
phase -= applied_k
frameRenderTime = T_in              // 不锁输入、不丢帧
```

待优化（按优先级）：

1. **hold 扫描（进行中）**：8 / 12 / 15，目标是在 `show≈112–120` 的前提下
   把 switches 从 ~5/窗降到 ~3/窗；取“肉眼最顺”的那个作为默认。
2. **reset-history 清零**：carry 日志仍有 8 次
   `reset-history ... MV/publication discontinuity`。需要区分：
   - MV auto 切换（一次性）；
   - 配对缺口（`marker_slot<0`/pub-queue 不在队列）。
   在 carry 路径下配对失败应继续“复用上一组 MV/depth”，不得 reset。
3. **切换成本反馈**：统计每次计数变更实际丢了几张输出（`expected_out` vs
   `GetLastPresentCount`），用来自动调 hold / deadband；这是 bridge 之外我们
   独有的信息，可把“carry 的切换次数”压到刚好不伤平均值。
4. **cap-limited 处理**：输入低于 `target/J` 时（如 21 fps、J=4），
   carry 只能输出 84 Hz；日志与 UI 明确 `cap-limited`，不要继续当作 120。
5. **默认化条件**：连续两轮实机满足
   - `show` 均值 ≥112 且 min（稳态）≥100，
   - `HITCH` ≤2、`reset-history` 0（启动除外），
   - 主观无档位跳变，
   则把 `run_consumer_carry12.bat` 设为动态默认。

## 6. 已知风险

- 4K 4x 在部分场景 `load` 已达 90–100%，偶发 200 ms 级 colour 拷贝停顿；
- 外部锁帧仍是当前最稳的操作方式；carry 只在“不锁帧 + 有波动”时作为动态路径；
- 单卡 FG 的平滑来自“固定输出节拍 + 队列 + 固定倍率”，我们已确认
  不要在 consumer 侧延迟捕获/使用 out-clock。

这正是要在实机上做 8/12/15 A/B 的原因——模型只能给出候选区间，
`show` 与主观顺滑度只能实测。

### 8.2 结论

1. **hold 8 是本轮唯一可用档**：show 116.5、p10 112、short 1.36/窗、HITCH 2；
   12/15 每窗多丢 1.4–2.5 张输出，show 掉到 113.6/112.4，`show<110` 的窗口从 6% 涨到 25%/33%。
   **hold 越大不是越顺，是越慢**——它把“该换档”推迟了，期间 k 一直是错的。
2. **carry 与固定倍率仍有 ~3 Hz 差距**（97.0% vs 99.3% 的面板填充）。
   但注意输入不是同一个数：carry 档没锁帧，跑在 42–43 fps；
   固定档锁在 40/30（整除）。所以这个差距里有一部分是“非整除输入的算术代价”，
   不能直接说 carry 比固定差 3 Hz。
3. **`swloss` 不是常数**：h8 每切换 1.28 张、h15 2.36 张。真正被丢的多数不是
   “切换本身”，而是**长驻留期间 k 停在错值**。因此“按每次切换丢几张自动调 dwell”
   会得出错误方向（以为切换贵 → 继续加 dwell → 更差）。**measure-only 是正确选择，
   不要开 auto**，除非改成按“延迟换档造成的欠帧”归因。
4. **reset 的 8 次几乎全是 colour-drop，不是配对缺口**：pair-gap 0–3 次，
   colour-drop 14–19 次（固定档也一样）。所以“配对缺口不 reset”最多省 1–3 次，
   真正该查的是**颜色队列为什么每 4–5 秒丢一帧**（load 均值 59% 但峰值 99%）。
5. **HITCH 的性质变了**：carry 档的 HITCH 是 54–93 ms（xN=1，欠一档），
   不再有之前 250 ms 的 colour 拷贝停顿；固定档的 HITCH 仍是 249–257 ms。
6. **carry 的结构性上限在“想换档但不允许”**：`reason=deferred` 占 30–40% 的帧。
   42 fps 下要精确贴住 120 需要 k 在 3/2 间平均约 17 次/秒的交替，实际只做到 5.5 次/秒
   （h8）。排空/驻留门限把它压下来，而少换的那些帧就是“欠帧”。所以这不是参数没调好，
   而是“整数 k + 面板 120 + 输入 42–43”这套算术下 carry 的固有代价。

## 9. 250 ms 卡顿：先止血、再根治（2026-11-15）

### 9.1 因果修正

用户侧的初判是“每次 reset 导致 250 ms”。日志证据相反：

```
SLOW frame: total=249.0ms colour=209.3 inputs=0.3 present=39.4
HITCH gap=249.2ms
reset-history: forced ... (colour-drop 13)
```

三次卡顿的 `colour=` 是 209.3 / 222.4 / 207.6 ms，同帧 `inputs` 只有 0.3 ms；
而 8 次 reset 里只有 1–3 次伴随卡顿。链路是：
**sink 拷贝阻塞 207–222 ms → 循环停 250 ms → 2 深颜色队列溢出丢帧 → 丢帧才 forced reset**。
reset 是末端症状，不是原因。详见 `docs/design/COLOUR_STALL.md`。

### 9.2 本轮实现（三层里的前两层）

| 层 | 改动 | 位置 |
|---|---|---|
| L1 止血 | colour stall guard：上一次拷贝 >40 ms / D3D11 侧 ≥2 张在飞 / D3D12 侧 3 帧落后 → 跳过本次拷贝、复用上次写过的 sink（连续上限 4）；**先判定再换 sink**（修掉复用帧读到 2–3 帧前内容的顺序 bug） | `frame.cpp`、`frame_io.cpp` |
| L1b | 颜色队列溢出**不再**写 `g_force_reset_history`，只计数；配对失败仍 reset | `main.cpp` |
| L1c | `AcquireSync(0, 20)` 的返回值此前一直被忽略：没拿到锁仍照样 `CopyResource`（driver 会把这次写排到读者之后 → 200 ms 级阻塞）。现在拿不到锁就复用上一帧并计数 | `frame.cpp` |
| L2 隔离 | 动态逐帧的输入时钟默认改为 `producer`（游戏自己的 `frame_time_ms`），我们的停顿/丢帧不再改变 k；`--cad-input arrival` 做 A/B | `frame.cpp`、`main.cpp`、`state_overlay.cpp` |


新增日志：breakdown 行的 `cskip=N`；事件行
`colour: <原因> - reusing the last frame ... (streak, skipped so far)`。

L3（根治：去拷贝 / 走 copy queue / 降采样 / 捕获侧直接转 PQ）按性价比排期，
验收指标见 `COLOUR_STALL.md` §4–§6。

### 11.2 `--no-fg-pace` 那轮是无效实验 —— 找到根因并修复

`mgpu_consumer_carry_nopace.log` 第一屏就是 `mode: fg=off`，xN 恒 1.00、
`presents/expected 49.9%`、cap-limited 22/23 窗口。

根因：`--no-fg` 用 `wcsstr(GetCommandLineW(), L"--no-fg")` 做**子串**匹配，
而 `--no-fg-pace` 里包含 `--no-fg` → 帧生成被整轮关闭。
（所以历史上 `run_consumer_dynamic_nopace.bat` 的“无 pacer”实验其实也都是 1X。）

已修：新增 `flag_alone()` 精确匹配（后面必须是结尾/空白/引号），`--no-fg` 改用它。

### 11.3 pacer 的实际代价（值得继续测）

- `fgpace` 均值 **5.28 ms/帧**、最大 7.9 ms —— 占 23.5 ms 帧时间的 **22%**，是纯延迟。
- 同一轮 `qdrop` 252 次（2.4/窗口，最大 15）—— pacer 把捕获往后推，2 深队列溢出。

所以 `--no-fg-pace`（修好后）仍是最值得做的一步：它同时减少延迟和丢帧。
注意 pacer 只影响“交给 XeFG 的时点”，不影响 k（k 已改用 producer 时钟）。

## 16. locked 实测：间距对了，残余顿挫来自"丢掉的那 7% 输入帧"

**每秒 3 个游戏帧被丢掉**。每丢一帧，下一批就要把 **46.7 ms 的内容塞进 25 ms 显示**
（≈1.9× 速度突跳），每秒 3 次 —— 与间距无关，这就是残余顿挫。

算术上 43/120 的最小失真就是 `3×43/120 − 1 = 7.5%`，**任何整数 k 都无法消除**。
所以只有三条出路：把游戏锁到 40（失真 0）、VRR（不可用）、或接受 7.5%。

### 16.1 新增第二种预算哲学（已实现）

同一份固定 k，另一种铺法：**预算 = 实测 T（23.3 ms）**。这样每批正好跨 1 个输入间隔
（内容时间准确、没有 2 倍速突跳），代价是 129 提交 / 120 上屏，面板每秒丢 9 张
—— 每张只差 8.3 ms，步长比上面的 23.3 ms 小 3 倍。

- `--cad-budget input` + `--cad-policy locked` → `run_consumer_locked_T.bat`
- 部署：`xess_mfg_consumer.exe` = `68c9545664956aa3a2b5cedf477ba1b5567aee455b2f524b6ced67be10d48459`
  （备份 `…bak_20261115_lockT` = `335c9966`）

### 16.2 两个决定性测试

| # | 怎么做 | 验证什么 |
|---|---|---|
| 1 | RTSS/驱动把游戏锁 **40**，跑 `run_consumer_locked.bat` | 若**完全顺** → 证实残余就是那 7.5%，不是算法问题；也说明"动态路径在整除输入上等于固定基线" |
| 2 | 不锁帧，跑 `run_consumer_locked_T.bat` | 同样的固定 k，改用 T 预算：步长从 23.3 ms 降到 8.3 ms，观感是否更好 |

如果 1 顺、2 更好，那产品结论就是：**动态路径 = 选 k + 选预算哲学；要在非整除输入上做到"无顿挫"，只能靠锁帧或 VRR**。

## 17. 定位残余顿挫：`late`（提交错过 vblank 槽），不是 cadence

### 17.1 两轮对照

| 指标 | locked + RTSS 锁 40 | locked_T（不锁帧） |

| 输入 | 40.0 fps | 42.9 fps |
| show | **119.8**（p10 120，min 114） | 118.5（p10 116） |
| 间距误差 / 不齐帧 | **0.4% / 0%** | 7.4% / 55% |
| presents / vblanks | 99.8% | 98.7% |
| switches | 1 / 68 窗 | 3 / 78 窗 |

| SLOW frame | 2 次（启动 present 87.7ms；colour 51.1ms） | 1 次 |

**锁 40 时 cadence 已经解决**（间距 0.4%、0% 不齐、丢帧≈0）。
唯一剩下的内部信号是 `late`：**20% 的批次没踩在 vblank 边界上**。

原因：单帧 `total` 均值 22.4 ms、**p95 ≈ 26.5 ms > 25 ms 预算**。
pacer 的网格是"每批 25 ms"，晚 1–2 ms 就错过一个 slot，pacer 只能压缩或让某个 vblank 出两张

## 18. 显示端 vblank 已接入（用户指出的那条路）＋ 延迟问题

### 18.1 为什么之前拿不到、现在怎么拿

`GetFrameStatistics` 在本 swapchain 不支持（日志已确认），但那不是唯一来源：
**consumer 自己驱动 overlay 那块屏**，可以直接对它对应的 `IDXGIOutput` 做事。

实现（`cadence.cpp`）：

- `vblank_init()`：在 `init_fg()` 末尾，按 overlay monitor 找到该显示器对应的
  `IDXGIOutput`，连续 `WaitForVBlank()` 9 次，用 8 个 QPC 间隔的**中位数**当真实周期，
  最后一次的 QPC 当相位基准；
- 每帧 `Present()` 后计算 `phase = (t_present − t0) mod period`（距上一次 vblank 的位置）；
- 每个报告窗口输出：

```
vblank: period=8.3392ms phase mean=0.42 std=0.06 min=0.31 max=0.55 ms (n=40)
```

启动时还会打一行，直接把实测周期和假设周期对比：

```
vblank: measured period 8.3392 ms (119.916 Hz); assumed 8.3333 ms (120.000 Hz)
        - drift 0.006 ms/s  <== our grid differs from the panel
```

这一行价值很大：如果面板实际是 119.88 Hz 而我们按 120.000 铺网格，
两者的相对漂移会让"提交相位"缓慢打滑 —— 典型的**周期性（几秒一次）顿挫**，
而且**再怎么调 hold / k / 预算都修不掉**，只能改用实测周期。

`cadence_report.py` 已能解析这一行（`vphase` 段）。

### 18.2 延迟：链路上真正的加法项

用户反馈"锁 40 顺，但延迟有点大"。按链路拆：

| 环节 | 量级 | 能否减少 |
|---|---|---|
| 游戏 present → fakerFG 发布 | ~0 | – |
| WGC 捕获延迟（`age=`） | 1 帧级 | `--pool 2` |
| 我们等待颜色队列 | 0–1 帧 | `--colour-queue 1` |
| 等上一帧 GPU 完成（深度 1 节流） | 0–1 帧 | `--no-throttle`（+1 帧松弛，代价见 17.3） |
| XeFG 生成 + 上屏 | ~1 帧（FG 固有） | – |
| pacer 等到 vblank 槽 | 最多 1 批 | 取消它并不会更早上屏（面板只在 vblank 翻），**不是延迟源** |

所以低延迟入口：**`run_consumer_locked_lowlat.bat`**（`--pool 2 --colour-queue 1`）。

## 19. vblank 实测结果：面板不是 120.000 Hz（这就是"几秒一次"的来源）

### 19.1 数据

| | locked | **locked_lowlat**（pool2 + cq1） |
|---|---|---|
| 实测周期 | 8.3560 ms = **119.674 Hz** | 8.3410 ms = **119.890 Hz** |
| 假设值 | 8.3333 ms = 120.000 Hz | 同 |
| show / min | 119.8 / 101 | 119.9 / **116** |
| presents / vblanks | 99.8% | **99.9%** |
| colour-drop | 7 | **3** |
| HITCH | 1（76 ms） | **0** |
| 相位 std（每窗口） | 1.44 ms | **0.61 ms** |

3×8.3333 = 25.000 ms，而面板的 3 个 vblank = 25.068 ms → **每批差 0.068 ms，
提交相位以 ~2.7 ms/s 打滑**（相位 mean 在窗口间 2.5→4.2→4.9 之间游走）。
这正是"几秒一次"的轻微顿挫，而且**调 hold/k/预算都不可能修掉**。

另外：`pool 2 + colour-queue 1` 在**所有**指标上都更好（尾帧 min 101→116、
丢帧 7→3、HITCH 1→0、相位 std 1.44→0.61），用户也确认延迟改善。

### 19.2 已改：全面改用实测周期

- `vblank_init()` 移到 `cad_core_configure()` **最前面**，`cc.refreshHz = 1000/period`；
- `refresh_ms()` 优先返回实测周期（影响 pacer 网格、`fg_input_pace`、`presents/vblanks` 统计）；
- 结果：预算 = `k × 8.356` 与面板的 k 个 vblank 完全一致，相位不再系统性漂移。

部署：`10115dddae38292cbd241896618c1c54cadee1fc1e8defb400dcbdcf7a392369`
（备份 `…bak_20261115_vbperiod` = `68433cec`）

### 19.3 结论与下一步

1. **锁 40 + lowlat + 实测周期 = 目前唯一"完全顺 + 延迟可接受"的配置**；
2. 非整除输入（43 fps）仍有 `k·f/R − 1 ≈ 7.6%` 的失真 —— **物理下限**，
   `--lock`（我们自己的 limiter）只能把它"规则化"，消不掉（丢帧后那一批会跨 2 个输入间隔）；
3. 所以产品化路径是：`locked` 负责选 k 与预算，OSD 明确显示
   **"当前输入 43.0 fps，建议锁 39.96（=R/3）"**，让用户/驱动去锁；
4. 下一步验证：以实测周期重跑 `run_consumer_locked_lowlat.bat`，看
   `vblank: phase mean/std` 是否变成**稳定值**（std < 0.3 ms、mean 不随窗口漂移）。
   如果是，说明"打滑型"顿挫已被消除，剩下的只有用户是否接受 43 fps 的 7.6% 失真。

## 20. 实测周期本身不可信（第三次运行暴露）→ 改用 DWM 合成时钟

### 20.1 问题

三次运行用 9 次 `WaitForVBlank()` 中位数估出的周期：

| 运行 | 周期 | 换算 |
|---|---|---|
| locked | 8.3560 ms | 119.674 Hz |
| locked_lowlat（第一次） | 8.3410 ms | 119.890 Hz |
| locked_lowlat（第二次） | 8.3132 ms | **120.291 Hz** |

面板不可能在 119.67–120.29 Hz 之间跳。**说明这个估计的噪声 (~±0.3%) 与我们要消除的
漂移同量级** —— 直接拿它铺网格，反而会在另一次运行里引入反方向的漂移。
（第二次运行的其他指标仍然好：show 119.8、min 113、presents/vblanks 99.9%、
k=3 恒定、rhythm 0.3%、HITCH 2。）

### 20.2 已改：DWM 的 qpcRefreshPeriod

- `DwmGetCompositionTimingInfo()` 直接给出 `qpcRefreshPeriod`（合成器自己的刷新周期）
  与 `qpcVBlank`（最近一次 vblank 的 QPC），**不受我们线程唤醒抖动影响**；
- 拿不到时回退到 **120 个 vblank 的长基线平均**（不是 9 个的中位数）；
- 日志标明来源：`vblank: measured period ... via dwm`；
- 链接加 `dwmapi.lib`，`consumer_internal.h` 加 `<dwmapi.h>`。

部署：`ce430fc9591deacca5efa31c8d0414bfc02a9383ab296ba61c807460a4473be8`
（备份 `…bak_20261115_dwm` = `10115ddd`）

### 20.3 注意：相位指标测的是"提交时点"

`phase = t_present − vblank 边界`，而 `t_present` 在 `Present()` **之前**取，
所以它反映的是**我们循环的抖动**（p95 总时长 > 预算时就会漂），不是显示端的最终落点。
它的用途是：在同一配置下判断"提交是否稳定"，**不能**当作面板实际显示的单调证明。

### 21.3 修正：`late` 不是可用指标

`late` 在这次是 1975（20.6/窗 ≈ 51%），但**它不代表"错过槽"**：
`fg_input_pace` 里的 `now` 是在 `Present()` **返回之后**取的，而 Present 本身会阻塞到
vblank 后才返回，所以 `now + k*vblank` 天然落在"下一个槽之后" → 恒定 late。
只有 `budget = T`（不铺满）时 `late` 才有意义（那时它 100% late 也是同样道理）。
**结论：以 `phase std` 取代 `late` 作为提交稳定性指标**，代码里那条注释也已按此理解使用。

## 23. 动态输入：把可选空间收干净（下一阶段研究计划）

### 23.1 结构性约束（已证明，不再是猜测）

1. `k` 张输出必须正好占 `k` 个 vblank，否则不是**留洞**（k 张铺 >k 个 vblank）就是**面板丢帧**（<k）。
2. 所以 `sum(k_i)` 必须等于总 vblank 数，而 `sum(输入间隔)` 是游戏给的 → `k` 的长期平均被钉死为 `R/f`。
3. 43 fps @120 Hz → 2.79，**非整数**。于是只有三条路：

| 方式 | 谁来吸收 7% | 节奏表现 | 实测（43 fps） |
|---|---|---|---|
| carry（k 交替 3↔2，预算 T） | 间距 | 8.33/12.5 ms 交替，60% 帧不齐 | show 118.9，HITCH 4 |
| locked（k=3 固定，预算 3V） | 输入帧 | 间距恒 1 vb，每 ~14 批一次 46.7 ms 内容跳 | show 118.5，qdrop ≈3/s |
| （若面板能跟）VRR | 无 | 完美 | 本机不可用 |

**不存在第四种**：任何整数 k 的每帧决策都落在这三格里。这一点把"再调参数"的空间关掉了。

### 23.2 尚未排除的变量：3x 模型质量

XeFG 的 3x/4x 是"2x 模型跑两次、复用同一组 MV"（`FINAL_CONFIG 5.17`）。
43 fps 只能 3x，所以**看不清的顿挫里可能有一部分根本不是 cadence，而是模型**。
唯一干净的对照：**锁 60 + 原生 2x**（60×2=120，整除、无丢帧、原生模型）。

- 新入口：`run_2x60.bat`（`--interp 1 --interp-cadence`，其余走默认 locked）

预期：
- 若 2x@60 明显更顺 → 动态输入的"顿挫"主要是 3x 模型，产品建议改为
  "尽量跑 60 fps 用 2x"，而不是继续在 43 fps 上找整数 k；
- 若 2x@60 与 3x@40 一样顺 → 说明 3x 模型不是瓶颈，43 fps 的残余就是那 7%，
  动态输入按"三选一"写进文档即可。

### 23.3 建议的测量矩阵（同一场景，各 2 分钟）

### 24.2 根因：`ceil` 在整数边界上抖

```cpp
int kTarget = (int)std::ceil(wantK - kLockSnap);   // 3.0024 -> 3；2.79 -> 3；3.43 -> 4
```

仿真不变（table 5c 全过）。部署：`552df5cf4d0b39463ee9b592e58f8161a13145ebdd6a724c818de8834d24b449`

1. **2x 模型（原生）明显比 3x 好**（3x/4x 复用同一组 MV）；

### 24.4 用户提议：自建"目标帧队列"平滑 WGC 输入

**可行，而且正好治我们量到的那类抖动**（WGC 到达间隔被合成器量化成 2/3/4 vblank，
以及停顿后的追赶突发）。但要说清能做/不能做：

| 能解决 | 不能解决 |
|---|---|
| 追赶突发：两帧背靠背到达 → 不再产生两个相邻批次 | 7% 的速率不匹配（43→120） |
| 停顿后的空洞：队列空时"重复上一帧"而不是留洞/阻塞 | 3x 模型的 MV 复用伪影 |
| 随机丢帧 → 有意的、均匀的"丢最旧" | 面板端的调度/丢帧 |
| WGC 间隔抖动不再直接改变 k（决策仍用 producer 时钟） | 延迟（队列深度 N 会 +N 帧） |

设计草案（分三步）：

1. **队列项**：`{ colour, slot(配对后的 MV/depth), seq, producer_qpc, wgc_ts }`。
   现在是"颜色队列 + 后续按 seq 配对"，需要把配对结果一起入队；
2. **稳态消费**：presenter 按自己的节拍（k×vblank）pop 一项，而不是"WGC 一到就处理"；
   - `depth > target` → 丢最旧（`tq_drop`），保证延迟有界；
   - `depth == 0` → 重复上一项（`tq_starve`），且**不推进相位**（按 reuse 处理）；
3. **观测**：`tq depth min/mean/max`、`tq_drop/s`、`tq_starve/s` —— 这三个数就能回答
   "输入被平滑了多少"。

注意：现在的 `--colour-queue` 其实就是 1 深缓冲，所以**最小验证可以先做**：
`--colour-queue 3` 在 43 fps 下跑一次，看 `qdrop` 与观感变化，再决定是否值得做完整队列。

## 25. 用户纠正：真实锁帧从不是理想值 → 默认回到 optimal

### 25.1 用户的三点（都对，且第 1 点有数据支持）

1. RTSS/驱动锁帧**不可能稳定**，几乎必然 ±1–2 帧波动 → 纯 `R/f` 的整数切分（locked）
   天然缺死区，一定会在边界上翻。
2. 动态输入 = "更不稳定的固定倍率"（上下限差异大且不均匀），但**死区处理可以借鉴**。
3. cq3 只有一点点改善。

第 1 点我们自己的数据就是证据：锁 40 时 `wantK = 3.002` → `ceil = 4`，k 在 3↔4 之间
**76 次 / 53 窗**。我当时用 0.08 帧容差打补丁，但那只是把边界挪了 2.6% ——
真实抖动 ±5% 时照样翻。**修法不是调容差，而是要有死区。**

### 25.2 改动

| 项 | 之前 | 现在 |

| 输入速率给 core | 最新发布帧的**单次**原始间隔 | **16 样本中位数** |

这正是"动态输入上下限差异大"里最伤的一环：先用错速率，再谈选 k。

## 27. 修正 §26：`game=` 是我们自己的到达 EMA；T 的真实来源是 producer 的发布 EMA

### 27.1 两处纠正

1. 日志里的 `game=` 打印的是 `g_arrival_ms_ema`（**我们循环的 WGC 到达间隔**），
   不是 producer 的帧间隔。所以在 43 fps 场景下 `game=25.2`（被 pacer 限到 40/s）
   而 core 的 `T=23.4`（43 fps）**本来就是对的** —— §26 的"读数 bug"判断错误。
2. 但 `T` 确实会**成段掉到 19.4–22.4 ms**（=51 fps），而游戏实际 43 fps。
   根因：`FrameShared.frame_time_ms` 是 producer 对**发布间隔**的 EMA ——
   游戏一帧内可能发布多次，EMA 就会读到比真实帧率更高的值。

### 27.2 修法：用 `frame_qpc_ms` 自己算真实间隔

`frame_qpc_ms` 是游戏自己的 present 时间戳（单调）。对**已配对**的帧求差、
过滤重复发布（Δt≈0）、取 16 样本中位数：

```cpp
const double tq = (double) fr.frame_qpc_ms;      // 配对帧
if (prev_qpc > 0 && tq > prev_qpc && tq - prev_qpc < 250.0) {
    const double dt = tq - prev_qpc;
    if (dt > 3.0) { push16(dt); }                // 重复发布直接丢
}
prev_qpc = tq;
g_prod_interval_ms = median16();                 // 样本 <4 时退回 frame_time_ms
```

日志同时改名，避免再误读：

```
arr=25.2ms pin=23.2ms   ← arr = 我们的到达间隔（受 pacer 影响）；pin = 游戏真实间隔
```

## 28. `pin` 第二轮修正：必须按 frame_id 归一化

### 28.1 实测（04:47 那轮 #3）

```
pin = 49–58 ms（17–20 fps）→ slots 6.4 → k=4 → cap-limited 26/27 窗，HITCH 12
```

原因：`pin` 用的是**已配对帧**之间的 Δqpc，而我们为了跟上 120 Hz **本来就会丢发布**。
两条发布之间隔一次丢弃 → Δqpc ≈ 46.6 ms，读成 21 fps。**它测的是"我们消费的间隔"，
不是"游戏的呈现间隔"** —— 和 `arr=` 犯的是同一类错误。

### 28.2 修法：除以 frame_id 的增量

```cpp
const double dt = (tq - prev_qpc) / (double)(id - prev_id);   // id 是 producer 的发布计数
if (dt > 3.0) push16(dt);     // 重复发布（同一 present 时间）直接丢
```

这样即使我们每两个发布才处理一个，读到的仍是**每条发布的平均间隔**（43 fps → 23.2 ms）。

> 教训（写进代码注释）：任何"输入速率"都必须以 **per-publication** 为单位；
> 不能用"我们处理了两帧之间的时间"—— 那个量同时包含了丢弃和节流。

## 29. 速率估计第三次修正（并停止盲改）：回到 producer 的 per-present 定义

### 29.1 这轮为什么更差

`pin` 换成 Δqpc/Δframe_id 后，`T` 反而变成 **19.1 ms（55 fps）** → k=2 → show 95.8、填充 80%。

原因在 producer 的源码注释里（`producer.cpp:105`、`1198`）：

> `frame_time_ms` 是**publish 之间**的 EMA —— publish 每*呈现帧*一次，所以它就是帧间隔；
> `frame_qpc_ms` 是 **Evaluate** 时刻，游戏一帧会 Evaluate 多次（CP2077 约 3.3 次），
> 相邻值只差 ~7.5 ms，**不是帧间隔**。

也就是说：我拿一个"每 Evaluate 一次"的时间戳去算"每帧"的间隔，方向上就错了。
