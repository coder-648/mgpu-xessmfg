# 无损压缩替代“降采样/升采样传输”：成本对比与可行性（2026-11-21）

> 问题：能不能用**通用无损压缩**（nvComp / 移植到 A 卡的 hipComp）替掉现在的
> `StreamPercent` 降采样 → 跨卡 → 消费端升采样这条路径？
>
> 结论先行：
>
> 1. **它替代不了 `StreamPercent`**。降采样是“字节数按面积平方下降”（150 档 = 4/9，
>    200 档 = 1/4）；游戏帧上的通用无损压缩给不到这个数。压缩只能作为**链路上再乘一个
>    系数**，不能当作档位本身。
> 2. **形态不是“熵编码”，是固定码率的块内预测打包**（bit-exact、代价可预测）。
>    理由见 §3：这条 4K→150% 的 9-tap 中值降采样在本机实测 **0.30 ms**，而一次编码只要
>    **0.13 ms/66 MB** —— 编码器比它替代的 pass 还便宜。
>    熵编码（nvComp 那一类）仍然出局：3–8 ms/帧，比省下的链路时间还多。
> 3. **它是“叠加”，不是“替代”**（§12 的实测把这条钉死了）：MV 只有 **1.50x**，
>    永远顶不掉 150% 档的 4/9；但把三条流都按**今天的尺寸**压一遍，
>    字节 95.9 → 74.0 MB/帧、生产端 SM −0.33 ms，**画质一个像素都不变**。
>    colour 反而是最划算的一条：1.20x 纯赚（它没有降采样可替代），
>    而 R10 换格式（2:1）是它的**替代品**而非叠加项 —— 两者一个买字节、一个买 bit-exact。
> 4. **nvComp / hipComp 直接落地不划算**，不是算法不好，是位置不对：CUDA context 进游戏
>    进程、NV 生产端 + AMD 消费端两套位流、变长输出要改协议、消费端在 4K/3x 已经
>    20.6 + 8.33 > 25.0 ms（`TIMING_4K40.md` §4.2），收不下解码。
>
> **gate 1 已完成（§12，32 帧 4K 真机）**：MV **1.50**（p5 1.500）、depth **1.89**、colour **1.20**，
> 96/96 帧 bit-exact。裁决：**替代 ❌ / 叠加 ✅**，下一步先做 colour 的编码器（§12.5）。

## 1. 先看清“要替代的东西”是哪三笔账

现在的成本不是“传输”一项，而是三笔，压缩只影响第一笔：

```text
(a) 链路字节     数据写进跨卡槽 → 消费端读回          ∝ bytes / link_BW   ← 压缩只打这一笔
(b) 生产端 SM pass 降采样（读全分辨率、写小尺寸）       ∝ 像素 × ALU        ← 压缩不省，只换名字
(c) 消费端 pass    升采样/转换（本地，副卡）            ∝ 本地带宽           ← 压缩会变差（多一步解码）
```

实测账（4K render，`StreamPercent=150`，来自 `COLOUR_TRANSPORT_V22.md` §4.5 与本机复测）：

| 流 | 每帧字节 | 链路占用 @13 GB/s | 生产端 pass | 说明 |
|---|---|---|---|---|
| colour（源格式 FP16） | 66.4 MB | **5.11 ms** | 无（纯拷贝） | 实测边际成本 ≈ 6% 渲染卡 |
| MV（150%） | 14.7 MB | 1.13 ms | 9-tap medoid ≈ **0.30 ms** | 只有降采样才需要 pass |
| depth（150%） | 14.7 MB | 1.13 ms | 9-tap median ≈ **0.30 ms** | 同上 |
| 元数据 | < 4 KB | ≈ 0 | ≈ 0 | 共享内存里，已免费 |
| **合计** | **95.8 MB** | **7.4 ms/帧** | **0.60 ms/帧** | 40 fps 真实帧 ⇒ 3.8 GB/s ⇒ 13 GB/s 链路的 29% |

两个必须记住的事实：

- **链路没有饱和**。2x@120 下 5.7 GB/s、3x 下 3.8 GB/s，都远低于 13 GB/s。
  所以“省字节”买到的是**余量**，不是当下的帧率 —— 除非平台是 PCIe 3.0 x8（`TRANSFER_V2.md` §13）。
- **名义链路时间和实测边际成本不一致**。66.4 MB 名义 5.1 ms，实测只有 ≈ 6%（25 ms 帧的 1.5 ms），
  因为拷贝和游戏剩余工作重叠。这意味着**任何“省 X MB ⇒ 省 Y ms”的推算都要打折**，
  §2 的不等式用的是名义值，是保守（对压缩有利）的一侧。

## 2. 两条不等式：什么时候压、什么时候不压

设某条流今天传 `B` 字节、生产端 pass 花 `T_down`，压缩后传 `B'`、编码花 `T_enc`，
链路带宽 `BW`：

```text
字节不等式（画质/带宽）   B'  <  B               压缩率 r = B/B' > 1
时间不等式（渲染卡）      B'/BW + T_enc  <  B/BW + T_down
                         ⇒  B - B' > BW·(T_enc - T_down)
```

第二条是关键，它说明**压缩率不是唯一变量**：如果编码器比它替代的 pass 便宜，
那么“字节略增”也可以接受。

代入实测（§3）：

| 流 | 今天的 B | T_down | 固定码率编码 T_enc | 允许的 B'（上限） | 需要的 r |
|---|---|---|---|---|---|
| MV 4K full | — | — | 0.13 ms | — | — |
| MV vs 150% 档 | 14.7 MB | 0.30 ms | 0.13 ms | **17.0 MB** | **≥ 0.87**（2:1 已净赚，甚至允许轻微膨胀） |
| depth vs 150% 档 | 14.7 MB | 0.30 ms | 0.13 ms | 17.0 MB | ≥ 0.87 |
| colour vs 原样 | 66.4 MB | 0（无 pass） | 0.13 ms（固定码率） | **64.7 MB** | ≥ 1.03（几乎白送） |

反过来，**换成一个真正的熵编码器**（LZ4/GDeflate/Zstd 级，编码 8–20 GB/s）：
66.4 MB 要 **3.3–8.3 ms**，代入不等式：

```text
B - B' > 13 × (6.0 - 0.30) = 74 MB      ⇒  B' < -8 MB      不可能
```

**这就是全篇的分水岭**：不是“压缩有没有用”，而是“编码器每帧要花多少 ms”。
固定码率块变换（0.13 ms）能进预算；熵编码（数 ms）不能。

## 3. 实测：这些 pass 在 3080 Ti 上到底多贵

渲染卡就是 3080 Ti（与本文档的实测机同型号）。复现：`tests/lossless_bench/`（Linux + CUDA 12，
`nvcc -O3 -arch=sm_86 lpbench.cu -o lpbench && ./lpbench`）。全部是**数据无关**的流式 kernel，
所以耗时可以直接外推到真实帧；只有“压缩率”必须用真帧量（§8）。

```text
device: NVIDIA GeForce RTX 3080 Ti  SMs=80  sm_clock=1695 MHz  bus_bw=912 GB/s  sm_86
copy 66MB -> 66MB (plain copy)        0.188 ms     707 GB/s effective
pack 2:1  66MB -> 33MB                0.130 ms     767 GB/s effective
unpack 2:1 33MB -> 66MB               0.148 ms     671 GB/s effective
tile bit-width scan (64k tiles)       0.257 ms     258 GB/s effective
downsample 4K->150% 9-tap median      0.307 ms     271 GB/s effective
```

三个可直接用的结论：

1. **固定码率编码 ≈ 0.13 ms/条流**（66 MB 输入），解码 ≈ 0.15 ms。相对 25 ms 帧是 0.5%。
2. **今天的降采样比编码器更贵**（0.30 vs 0.13 ms）—— 9 抽头中值/medoid 是 ALU 与
   cache 密集，而一次 2:1 打包是纯带宽。**“压缩会更耗渲染卡”在固定码率下不成立。**
3. **变长/需要规约的 pass 立刻掉一个数量级**（位宽扫描 0.26 ms 只读不写，比整份拷贝还慢），
   这正是 GPU 上 LZ/ANS 类编码器昂贵的原因：它必须两趟（扫描 + 写），且写是变长的、
   要原子预留或串行前缀和。nvComp 的所有算法都属于这一类。

## 4. 逐流的压缩率（2026-11-21 已被 §12 的实测取代，此表保留作对照）

> 下表原本是经验区间；2026-11-21 用 32 帧 4K 真机数据实测后已就地更新（§12）。
> 决策一律用 **p5（最差帧）**，不是平均值。

| 流 | 内容特征 | 帧内无损的合理预期 | 今天的档位要求 | 判定 |
|---|---|---|---|---|
| colour 4K FP16 | HDR scRGB、TAA/TAAU 抖动噪声、dither、胶片颗粒；已色调映射 | **实测 1.20**（zlib 1.95–1.96，§12.1） | 替掉 66.4 MB 只需 ≥ 1.03 | ✅ **做**（固定码率；熵编码仍因 3–8 ms 出局） |
| MV 4K RG16F | 大面积精确 0（静止）、整屏常量（纯平移）；亚像素/TAA jitter 让低位噪声 | **实测 1.50**（p5 1.500，32 帧，§12.1）；150% 档压缩后 1.48 | 替代 4/9 需 ≥ 2.25（**做不到**）；叠加只要 ≥ 1 | ✅ 叠加 / 🟡 升 100% 待 gate 2 |
| depth 4K R32F | 反向 Z/对数深度，邻域强相关；轮廓处跳变 | **实测 1.89**（150% 档 1.77，§12.1） | 同上 | ✅ 做叠加；不升 100%（深度不敏感） |
| UI 掩码 | 已经是 1/4 R8 | — | — | 无需压缩 |

两张必须一起看的表：

- **MV 的收益是画质，不是带宽**。`UPSAMPLE_QUALITY.md` §3 已经承认：块内亚像素变化与
  被遮挡背景的矢量“不可恢复”。回 100% 全分辨率 + bit-exact 解码把这两条一起消掉，
  而成本（§2）打平甚至略好 —— 这才是这个提案真正的卖点。
- **depth 不敏感 ⇒ 压缩它没有收益**。除非用它把 depth 也升到 100% 来省掉生产端 pass；
  那是“省 0.30 ms 的 SM”而不是“省带宽”，收益有限。
  按实测 1.88 算：100% 档压缩后是 33.2/1.88 = **17.7 MB**，而 §2 的允许上限是 17.0 MB ——
  比今天的 14.7 MB 还多 3 MB，也就是说“bit-exact 的 depth”只能买到画质，买不到字节。

## 5. nvComp / hipComp 体检

### 5.1 它们提供什么

`docs.nvidia.com/cuda/nvcomp`（2026-11 查）列出的算法与定位：

| 算法 | 类型 | 用在这条链路上合适吗 |
|---|---|---|
| LZ4 / Snappy | 通用字节级，无熵编码 | 🟡 只要 1.5–2 倍时是候选；但仍是两趟 + 变长写 |
| GDeflate / Deflate / Gzip | DEFLATE 家族（GPU 友好版） | ❌ 为"解压快"设计，编码慢 |
| Zstandard（v6 起提供） | Huffman + LZ77 + ANS | ❌ 压缩率好、编码最慢 |
| Cascaded | 面向表格/分析型数据 | ❌ 数据不匹配 |
| **Bitcomp** | 面向科学计算的**浮点**无损，标称 proprietary | 🟡 唯一"为 float 设计"的，值得测；位流不公开 |
| ANS | 专有熵编码 | ❌ 同 Zstd |

`hipComp`（ROCm）是 nvComp 的移植，API 形状对齐（`nvcompBatched*`），覆盖 Snappy/LZ4/GDeflate/
Deflate/ANS/Zstd 等子集。**两条独立的库、两套位流实现**，这是本方案最大的结构性风险（§5.3）。

> 本节没有给出 nvComp 的实测吞吐：本文写作时本机拉不下 nvComp 的 wheel（网络），HIP 侧也没有硬件。
> 请把"nvComp 在本机 66 MB / 33 MB 上的压缩与解压耗时"当作 §8 的 **gate 0 先测**。
> §3 已经给出了任何编解码器都突破不了的下限（66 MB 读 + 33 MB 写 = 0.13 ms），
> 实测与它的比值就是"算法开销"。

### 5.2 位置不对：三笔账只有一笔受益，却要付两笔新的

```text
受益：链路字节 66 → 33 MB（2:1）           省 2.55 ms/帧（名义）
付出：① 编码在渲染卡上（游戏进程里）        熵编码 3–8 ms/帧 ⇒ 净亏
      ② 解码在消费卡上（4K/3x 已超预算）     熵解码 1.7–3.3 ms/帧 ⇒ 挤掉 XeFG
```

第②条是硬伤。`TIMING_4K40.md` §4.2 的判据是 `gpu_p50 + 1 vblank ≤ T_in`，4K/40 已经
`20.6 + 8.33 = 28.9 > 25.0`，**消费端没有任何余量**（`UPSAMPLE_QUALITY.md` §4 也写了
"4K/40 的余量只有 0.3 ms"）。任何加在消费端的每帧固定开销，代价都是掉输出帧。
唯一能藏解码的位置是"等 `fwd` fence 的空窗"，而那正是 `gpu_throttle` 20.6 ms 里已经被
XeFG 占满的部分。

### 5.3 五个具体的落地障碍

| # | 障碍 | 说明 | 缓解 |
|---|---|---|---|
| 1 | **CUDA context 进游戏进程** | producer 是注入游戏的 DLL；加 CUDA runtime = +200–400 MB 显存、100–300 ms 初始化、与 D3D12 的 external memory / external semaphore 互操作。任何一步失败都发生在游戏 present 路径上 | 只在 NVIDIA 生产端；失败必须能整条降级回 raw 拷贝 |
| 2 | **变长输出破坏"容量一次 place"** | 现在槽位是固定尺寸 texture + 内容矩形（v9 约定）；压缩后要变成 byte buffer + 每帧 `offset/length`，还要处理"本帧膨胀超预算" | 协议 v24 加 payload 描述；每帧可回退 raw（同一路径、两种 case） |
| 3 | **双厂商位流** | NV 端 nvComp、AMD 端 hipComp；算法同名**不代表位流一致**（版本/块大小/头都可能不同） | 不用两个库：自写固定码率 HLSL（两端同一份代码），或限定 NV→NV |
| 4 | **块头与补齐开销** | 分块（64 KB 级）后每块的头、最坏情况回退、尾部对齐，通常吃掉 1–3% 压缩率 | 块 ≥ 32 KB；允许"整帧回退" |
| 5 | **许可证** | 项目是 GPL-3.0（`docs/ops/LEGAL.md`）。nvComp 的 Bitcomp/ANS 标称 proprietary、位流不公开；hipComp 是 MIT。混用的再分发边界会变复杂 | 优先纯自研、无第三方位流的方案 |

### 5.4 一个反直觉的替代：不要压缩，换格式

同样为了把 66.4 MB 的 colour 变小，**R10G10B10A2 是固定 2:1**：

```text
colour FP16 → R10（生产端一次转换 pass）  读 66.4 + 写 33.2 ≈ 0.19 ms（§3 同量级实测）
链路                                      66.4 → 33.2 MB，省 2.55 ms（名义）
画质                                      10 bit 量化；对 8/10 bit 输出足够，
                                          但它是 XeFG 的**输入颜色**，渐变/暗部要实测
```

也就是说：**一个 0.19 ms 的格式转换，拿到了"2:1 无损压缩"想拿的全部带宽**，而且不引入
任何编解码器、位流、协议变化。它唯一比不上无损的是"bit-exact"。所以对 colour，
真正的选择题是 `R10` vs `无损压缩`，前者便宜 30 倍。

（`ColourPercent` 是更狠的一档：2:1 降采样 = 16.6 MB，但那是画质变量，已在
`COLOUR_TRANSPORT_V22.md` §9 里单独标记为"不与成本变量混在一起"。）

## 6. 如果要做，做成什么样：固定码率的块变换（不是熵编码）

目标：**bit-exact、代价可预测、两端同一份 HLSL、不引第三方库**。

### 6.1 变换

```text
1) 有序整数映射（IEEE-754 正数按位比较等价于数值比较，负数反向）
     u = bits ^ ((bits >> 31) ? 0xFFFFFFFF : 0x80000000)          // 32 bit 深度
     u = half ^ ((half >> 15) ? 0xFFFF     : 0x8000)              // 16 bit MV 的每一半
   → 之后“数值接近”⇔“整数接近”，减法才有意义（直接对 float 位做减法会炸）
2) 邻域预测：d = u - left；没有左邻居用上邻居；都没有则存绝对值
   （每个 tile 只有左上角像素属于这一类，占 4 字节/条流/tile）
3) zigzag：z = (d << 1) ^ (d < 0 ? 0xFFFFFFFF : 0)              // 负数不浪费高位
   （注意：负数要异或全 1，不是右移出来的那个 1 —— 写成 `^ (d >> 31)` 会让每个
    下降沿都变成 32 位，压缩率直接归零；`scripts/lossless_ratio.py` 里踩过这个坑）
4) 16×16 像素 tile（256 px × 每像素 nw 个 word）：w = max(bit_length(z))
   header = u32（bit0..5 位宽、bit6 模式），随后是左上角那 nw 个 word 的绝对值
5) 打包：z 按 w 位 LSB-first 连续写入；w == 32 → 整个 tile 原样（任何输入都无损）
```

这是 GPU 版的"块内定长化"：**每块自己决定位宽**，所以
- 平滑区（深度渐变、静止 MV）w 只有 6–10 → 3–5 倍；
- 轮廓/噪声区 w 到 32 → 1 倍（不亏，只是不赚）；
- 不需要熵编码、不需要两趟扫描、不需要原子预留 —— 一个线程块负责若干 tile，
  先算 w 再原地打包，**一趟读写**。

成本和上限都来自 §3 的实测：0.13 ms / 66 MB（编码）、0.15 ms 量级（解码）。
**可执行规格 = `tests/lossless_bench/fr_codec.h`**（可移植 C++，编码/解码 + 位流契约，
已用 300 组 fuzz 与真实帧验证 bit-exact）；`scripts/lossless_ratio.py` 的 `word`/`half`
是它的**快速一维近似**（偏保守：depth 1.88 vs 实测 1.94、colour 1.06 vs 1.22）。

### 6.2 协议与落点

| 项 | 变化 | 备注 |
|---|---|---|
| 槽位 | `stream[i]` 增加 `payload {offset, length, mode}`；`mode = raw \| fr-block` | 容量仍按**最坏情况**（raw）place，所以布局不重建 |
| 生产端 | `scale_dispatch()` 换成 `encode_dispatch()`（MV/depth 各一次），同一 copy list / 同一 `fence_forward[s]` | 部署位置与今天的降采样 pass 相同，没有新增同步点 |
| 消费端 | `copy_publication_inputs()` 里"跨卡拷贝"后多一步解码到本地 ring | 解码在 `wait_slot` 之后、XeFG 之前；**不再需要 upsample pass**（MV/depth 已是 100%） |
| 开关 | `MvCodec=raw\|fr`、`DepthCodec=raw\|fr`；`StreamPercent` 语义保留（`fr` 只在 100 档有意义） | 每帧可独立回退；`active_mask`/`stream_bytes` 继续如实上报 |
| 版本 | `kSharedVersion` +1（v24） | 与颜色入槽同一条"换代必拒绝"规则 |

关键：**压缩只用来消掉"降采样"这个有损中间态，不用来省绝对带宽**。
所以它和 `StreamPercent` 不是竞争关系，而是把它钉在 100：
`MV 100 + fr` ≈ `MV 150 + 降采样`（§2 表：17.0 vs 14.7 MB 的预算内），但前者无损。

## 7. 三种配置的成本对照（4K，每真实帧）

`link = 13 GB/s`（`--link` 默认，PCIe 4.0 x8 实测）；生产端/消费端毫秒取 §3 实测；
"名义"表示未打折的 `bytes / BW`（实际因为重叠会更小，见 §1）。

| 配置 | colour | MV | depth | 合计字节 | 链路（名义） | 生产端 SM | 消费端 |
|---|---|---|---|---|---|---|---|
| **A 今天**（colour raw + 150/150） | 66.4 | 14.7 | 14.7 | **95.8 MB** | 7.4 ms | 0.60 ms（两个降采样） | 0 |
| **B 压缩**（colour raw + MV 100/fr 2:1 + 150） | 66.4 | 16.6 | 14.7 | 97.7 MB | 7.5 ms | 0.43 ms（编码 0.13 + 降采样 0.30） | +0.08 ms（解码） |
| **C 换格式**（R10 + MV 100 raw + 150） | 33.2 | 33.2 | 14.7 | **81.1 MB** | 6.2 ms | 0.49 ms（转换 0.19 + 降采样 0.30） | 0（已有 convert） |
| D 极限（R10 + 150/200，无压缩） | 33.2 | 14.7 | 7.4 | 55.3 MB | 4.3 ms | 0.60 ms | 0 |

读法：

- **A → B 不是省钱，是换画质**：字节 +2%，生产端 −0.17 ms，消费端 +0.08 ms，MV 从
  "150% + 中值降采样 + 可能升采样"变成 bit-exact。要省钱请走 C/D。
- **C 才是这条链路上真正的带宽杠杆**：−15% 字节、生产端持平、消费端零新增，
  代价是 colour 的 10 bit 量化（需要实测渐变/暗部）。
- 三者在 2x@120（60 真实帧）下的链路占用：A 5.75、B 5.86、C 4.87 GB/s ——
  **都不饱和**，所以"省带宽"只在 PCIe 3.0 x8 或 4K/60 输入时才直接变成帧率。

## 9. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 压缩率不达标 | 现代渲染帧有 TAA 抖动/颗粒，MV 低位噪声大 | gate 1 用 p5；不达标就停 |
| 每帧字节可变 | tiled 定宽也有 1–3% 头开销 + 最坏帧膨胀 | 容量按 raw 预留；每帧可整条回退 |
| 消费端无余量（4K/3x） | 已 `20.6 + 8.33 > 25.0` | 解码 0.08–0.15 ms/流可接受；熵解码 1.7–3.3 ms 不可接受 |
| CUDA/HIP 进游戏进程 | context/互操作失败 = device removed | 只走 HLSL 自研，不留第三方运行时在游戏进程里 |
| 双厂商位流不一致 | nvComp / hipComp 同名算法 | 同一份 HLSL，两端一致 |
| 与动态逐帧的相位耦合 | 编码耗时随内容变化 → 发布间隔抖动？ | 固定码率 = 常数时间；这是选它而不是熵编码的另一个理由 |
| 只对 100 档有意义 | 150/200 档位下它反而更费 | 文档与 UI 绑定：`fr` 只在 `StreamPercent=100` 时可开 |

## 10. 一句话回答

**它能“叠加”，不能“替代”，而且不该用 nvComp/hipComp。**
用固定码率的块内预测打包（0.13 ms/66 MB，实测）把**今天的字节再压一遍**：
colour 1.20x、MV 1.48x、depth 1.77x，合起来 95.9 → **74.0 MB/帧**、生产端 SM −0.33 ms，
**画质一个像素都不变**（96/96 帧 bit-exact 回环）。
顺带它还给了一个原来算不起的选项：把 MV 升回 100% 全分辨率，代价被 colour 的压缩
收益盖掉，整体仍然 −1.1 ms/帧（§12.2 的 U 变体）。
降采样那个 4/9 仍然顶不掉（MV 只有 1.50x，需要 2.25），熵编码仍然出局
（3–8 ms/帧，比省下的链路时间还多）。
**下一步：先给 colour 写编码器（§12.5），收益最大、风险最低、比率 < 1 时自动回退。**

## 11. gate 1 首轮实测（2026-11-21，真实 CP2077 帧）

数据来自本机 `/mnt/c/temp/` 下历史上 `--dump` 留下的真实帧（bridge 时代，CP2077）：

| 目录 | 内容 |
|---|---|
| `dump3/` | 3 帧，colour `3840x2160 fmt 10`（RGBA16F）、MV `2560x1440 fmt 34` |
| `dump2077b/` | 1 帧，colour 同上 + depth `2560x1440 fmt 39`（R32 typeless）+ MV |
| `dump2077/` | 1 帧，colour 偏黑（zlib 67x，等于退化），MV 零 |

命令：`python3 scripts/lossless_ratio.py <dir>`（纯 CPU；`zlib` 是不折速的比率代理，
`word`/`half` 是 §6.1 码流的一维近似 —— 精确值见 §11.1 的 `fr_codec` 列）。

### 11.1 结果

`word`/`half` 是 `lossless_ratio.py` 的一维近似；`fr_codec` 是 §6.1 真正实现的精确字节数
（`tests/lossless_bench/fr_codec_test`，2D 16×16 tile、bit-exact 回环验证通过）。

| 流 | 帧数 | 原始 | zlib | word（1D 近似） | half（1D 近似） | **fr_codec（精确）** |
|---|---|---|---|---|---|---|
| colour 4K RGBA16F | 3（dump3） | 66.4 MB | **1.95–1.96** | 1.06 | 1.13 | **1.22** |
| colour 4K RGBA16F | 1（dump2077b） | 66.4 MB | 1.99 | 1.08 | 1.18 | 1.22 |
| depth 1440p R32F | 1（dump2077b） | 14.7 MB | 1.54 | 1.88 | — | **1.94** |
| MV 1440p RG16F | 3+2 | 14.7 MB | 1027（全零） | 256（全零） | 全零 | 128（全零） |

四条能直接用的结论：

1. **一维近似偏保守**（depth 1.88 → 实测 1.94、colour 1.06 → 1.22）：2D tile + 左/上预测
   比“同行左邻居”多吃到一点相关性。所以 gate 1 用 `lossless_ratio.py` 初筛是安全的，
   真值只会更好；要写进规格时用 `fr_codec`。
2. **固定码率码流对 colour 无效（1.22）**。原因不是实现，是数据：HDR FP16 的低位尾数被
   TAA/抖动/色调映射填成了噪声，16×16 里总有一个值要 32 位，整块就只能 32 位（raw 回退）。
   这条把 §4 的“别对 colour 做压缩”从经验变成了实测。
3. **colour 的熵编码比率其实够（1.95–1.96）**，所以 colour 的否决理由**只剩编码成本**
   （§2 的不等式）。1.96 意味着 66.4 → 33.9 MB，名义省 2.55 ms/帧；而 deflate 级编码在
   3080 Ti 上要 3.3–8.3 ms。**这是全篇唯一需要小心的地方：如果某天有一个 1.5 ms 内
   跑完 66 MB 的 2:1 编解码器，colour 这一格会被翻案。**
4. **固定码率对 depth 反而比 zlib 好（1.94 vs 1.54）** —— 平滑浮点 + 有序整数预测正是它
   擅长的。但按 §2 的账，depth 100% 档（33.2 MB）压缩后 = 33.2/1.94 = **17.1 MB**，
   仍高于允许的 17.0 MB：只有画质收益，没有字节收益。

`interp=1` / `no_mv 0 no_depth 0` / 96 个 raw / 4.0 GB）。

### 12.1 码流比率（`fr_codec`，精确）

| 流 | 原始 | 压缩后 | p5 | p50 | p95 | min |
|---|---|---|---|---|---|---|
| **MV** 4K RG16F | 33.2 MB | 21.5 MB | **1.500** | 1.530 | 1.570 | 1.490 |
| **depth** 4K R32F | 33.2 MB | 17.6 MB | 1.880 | 1.890 | 1.900 | 1.870 |
| **colour** 4K RGBA16F | 66.4 MB | 55.7 MB | 1.190 | 1.200 | 1.200 | 1.190 |

再量一遍「今天的 150% 流」压缩后是多少（`tests/lossless_bench/downsample_test.cpp`，
用同一个 3×3 足迹的中值近似 shader 的降采样）：

| 流 | 150% 原始 | 压缩后 | 比率 |
|---|---|---|---|
| MV | 14.75 MB | 9.95 MB | **1.48** |
| depth | 14.75 MB | 8.34 MB | **1.77** |

### 12.2 结论变了：**替代不行，叠加很行**

我原来只算了「用压缩**替代** 150% 降采样」，那确实不成立（MV 1.50 < 2.25）。
但把同一份比率摊到三条流上，还有两个更有价值的用法，而它们的账是正的：

| 变体 | 链路字节/帧 | 链路（名义） | 生产端 SM | 画质 | 净变化 |
|---|---|---|---|---|---|
| **今天** | 66.4 + 14.75 + 14.75 = **95.9** | 7.38 ms | 0.60 ms（两个 9-tap） | 150% 有损 MV/depth | — |
| **S 叠加**（三条流都按今天的尺寸压） | 55.7 + 9.95 + 8.34 = **74.0** | 5.69 ms | 0.27 ms（三个编码） | **与今天完全一致**（bit-exact 保存） | **−2.0 ms/帧** |
| **U 升级**（S + MV 回 100%） | 55.7 + 21.5 + 8.34 = **85.5** | 6.58 ms | 0.27 ms（无降采样） | **MV 全分辨率 bit-exact** | **−1.1 ms/帧** |

- **S 是白赚的**：字节 −23%、生产端 SM −0.33 ms，画质一个像素都不变
  （压的是已经在传的那份数据，解码后逐字节等于今天 tag 的东西）。
- **U 更有意思**：把 MV 升回 100% 的代价（+6.75 MB）被 colour 的压缩收益
  （−10.7 MB）覆盖，整体仍然 −1.1 ms/帧，还顺手消掉 `UPSAMPLE_QUALITY.md` 里
  承认的两条不可恢复误差。**原来「MV 100% 要多付带宽」的前提不成立了。**
- 消费端也不吃亏：解码是**替代**本地拷贝（读 74/86 MB、写 95.9 MB），
  本地总流量反而下降，只多了一次 ALU —— 不像原来担心的「额外 0.25 ms」。

### 12.3 但必须打折：名义 ≠ 实测

§1 已经说过：66.4 MB 名义 5.11 ms，实测边际只有 ≈6%（1.5 ms）。把同样的
「重叠折扣」套上去，**S 的真实收益大约 −0.6 ms/帧（25 ms 的 2–3%），
U 大约 −0.3 ms/帧**，链路占用从 3.8 降到 2.9 GB/s。
这不足以单独解决 §0 的 15%，但它是**画质不降级**的那部分，也是
「MV 回 100%」这个画质升级的入场券 —— 没有 S，U 要多付 6.75 MB/帧。

### 12.4 逐流裁决（更新）

| 流 | 裁决 | 理由 |
|---|---|---|
| **colour** | ✅ **做** | 1.20x 是纯赚：没有降采样可替代，只要比率 > 1.03 就赢；编码 0.13 ms 换 0.82 ms 链路 |
| **MV** | ✅ **做（叠加）** / 🟡 升级可选 | 150% 档 1.48x（−4.8 MB）；升 100% 需要额外 6.75 MB，要用 gate 2 证明画质值这个钱 |
| **depth** | ✅ **做（叠加）** | 150% 档 1.77x（−6.4 MB），生产端还省 0.17 ms；深度不敏感，所以只做叠加、不升 100% |
| 熵编码 / nvComp | ❌ 不做 | 结论不变：编码 3–8 ms/帧，比省下的链路时间还多 |

### 12.5 下一步（按性价比）

1. **gate 3 先做 colour**：规格已就绪（`tests/lossless_bench/fr_codec.h`），
   收益最大、风险最低（比率 < 1 时自动 raw 回退，等价于今天）。
2. 再把 MV/depth 的 150% 流换成「编码 → 跨卡 → 解码」，生产端顺手删掉两个
   9-tap pass（`scale_dispatch` → `encode_dispatch`）。
3. **U（MV 100%）已经过 gate 2**（§12.6：边界带 EPE p95 4.81 px → 0），
   所以它也可以进同一批 HLSL：等价于“多付 0.9 ms/帧 名义成本，换边界带矢量误差归零”。

### 12.6 gate 2 预演：降采样到底丢了多少（离线 EPE）

`tests/lossless_bench/epe_test.cpp` 用同一份 4K 真值做了 gate 2 的测量
（全分辨率 MV → 3×3 中值降到 150%/200% → 双线性重建回 4K → 与真值比）：

| 档位 | 全图 EPE p50 / p95 / p99 | 边界带（梯度 > 0.5 px，3.6%）p95 / p99 |
|---|---|---|
| 150% | 0.012 / 0.059 / **0.52 px** | **4.81 / 45.07 px** |
| 200% | 0.037 / 0.119 / 0.84 px | 7.70 / 54.85 px |
| **100% + 无损** | **0 / 0 / 0**（构造上） | **0 / 0** |

读法：

- **平滑区几乎无损**（p50 0.012 px），这印证了 `UPSAMPLE_QUALITY.md` §3；
- **边界带是真伤口**：150% 档的 p95 就有 **4.8 px**、p99 45 px 的矢量误差 ——
  这正是插值帧在运动物体边缘“拖影/串色”的来源，也正是无损流能整条消掉的东西；
- 用双线性重建是**偏悲观**的一侧（真实 `--upsample` 是深度引导 JBU，会好一些），
  但量级不会变：4.8 px 不是靠更好的重建能抹平的。

**gate 2 判据（EPE p95 改善 ≥ 30%）→ 边界带 4.81 → 0，通过。**
所以 §12.2 的 U 变体成立：多付 0.9 ms/帧（名义）买到“边界带矢量误差归零”。

## 13. 双卡混搭（N/A）的厂商矩阵：不用测四个场景

问题：环境里 NVIDIA 和 AMD 混搭，`N编N解 / N编A解 / A编N解 / A编A解` 四种组合
要不要各补一套测试？

**不需要四套。** 码流是纯整数的定长块格式，与厂商无关；真正要证明的只有两条：

1. 每个适配器上 `decode(encode(x)) == x`；
2. 每个适配器产出的**压缩字节逐字节相同**。

有了这两条，四种组合同时成立（编出来的字节谁都能解）。再加一条与 CPU 参考
（`fr_codec.h`）的字节比对，防止"自洽但错"。工具：`tests/gpu_codec/`（D3D12 + 同一份 HLSL，
`scripts/build_gpu_codec.sh` 一条命令编译并跑）。

### 13.1 实测（RX 6750 GRE + RTX 3080 Ti，2026-11-21，真实 dump 帧）

| 流 | AMD enc | AMD dec | NV enc | NV dec | 比率 | 字节一致 | 回环 | vs CPU |
|---|---|---|---|---|---|---|---|---|
| MV 4K 33.2 MB | 2.854 ms | **6.402 ms** | 2.286 ms | 1.203 ms | 1.54x | ✅ | ✅ | ✅ |
| depth 4K 33.2 MB | 2.643 ms | 6.125 ms | 2.202 ms | 1.211 ms | 1.88x | ✅ | ✅ | ✅ |
| colour 4K 66.4 MB | 5.763 ms | 10.300 ms | 3.343 ms | 3.110 ms | 1.19x | ✅ | ✅ | ✅ |

- **比率与 CPU 参考逐字节相同**（1.54 / 1.88 / 1.19）→ HLSL 与 §6.1 规格一致；
- **字节跨厂商完全一致** → `N→A`、`A→N` 都能解，四种组合一次覆盖；
- 绝对 ms **不是生产数**：当前 shader 是一个线程串行处理一个 16×16 tile（编码 11–20 GB/s），
  目标形状（流式，CUDA 实测 0.13 ms/66 MB ≈ 500 GB/s）要快 30–40 倍。

### 13.2 这个测试抓到的真问题：AMD 的解码慢 3–5 倍

不是带宽（两卡带宽差 2.1x，编码只差 1.15–1.7x），而是**依赖链**：现在的解码是
"每个像素读左邻居已解出的值"，256 个像素串成一条链，A 卡的调度特性把这条链放大成
6.4 ms（NV 1.2 ms）。

**上生产前必须改成无依赖形状**：

```text
pass 1  并行：每个像素独立算出 zigzag 残差（只读压缩字节 + 种子）
pass 2  每行段 inclusive scan（前缀和）→ 加行首种子 → 还原
```

这样解码就没有跨像素依赖，A 卡当消费端（本项目的默认拓扑）时不会被解码拖死。
这也是"要不要在 A 卡上测"的答案：**要，因为同一份代码在两个厂商上的形状代价可能差 5 倍，
而消费端恰恰是余量最小的那一侧。**

### 13.3 hipCOMP-core 源码审计：**没有 CPU 编解码回退**

有人问"AMD 侧是不是降级成 CPU 编解码了"。把 `third_party/hipCOMP-core-amd-develop`
（hipCOMP v2.3.0，基于 nvCOMP branch-2.2）逐项查过，结论是**没有 CPU 码路径**：

| 证据 | 位置 |
|---|---|
| 库里没有任何 zlib/zstd CPU 调用：`grep zlib\\|zstd.h\\|compress2` 在 `src/`、`include/` 里 0 命中 | `src/`、`include/` |
| `find_package(ZLIB)` 只出现在两处：顶层 `CMakeLists.txt` 的 `if(gdeflate_FOUND)` 分支，以及 `tests/third-party/`（用来**造 CPU 压缩输入**去测 GPU 解压） | `CMakeLists.txt:254`、`tests/third-party/CMakeLists.txt:44` |
| `src/CMakeLists.txt` 只链 bitcomp / gdeflate / ans 三个 NVIDIA 专有包，**从不链 ZLIB** | `src/CMakeLists.txt:115-126` |
| Zstd 解压走 `gpu_zstd_decompress(...)`（device 函数）；Deflate/Gzip/Zstd 的**压缩**直接 `throw "not implemented; no compression support for zstd"` | `src/lowlevel/ZstdBatch.cpp:121`、`src/highlevel/ZstdManager.hpp:88` |
| `__global__` kernel 在 `hipcomp_common_deps/hlif_shared.cuh` + `src/*Kernels.cu`；LZ4 压缩有完整 `lz4BatchCompress` | `src/lowlevel/LZ4Batch.cpp:176` |
| 公共头里的 "CPU" 只指 **pinned host 内存里的 status 数组**（元数据），不是编解码 | `include/hipcomp/hipcompManager.hpp:208` |

**但它有一个比"CPU 回退"更实际的问题：算法在 AMD 上不齐。**（README 的支持表 + 源码核对）

| 算法 | NV (nvComp) 编 / 解 | AMD (hipCOMP 2.3) 编 / 解 | 混合配对可用？ |
|---|---|---|---|
| LZ4 / Snappy / Cascaded | ✓ / ✓ | ✓ / ✓（README 标 **✗ Optimized**） | ✅ 双向 |
| RLE | ✓ / ✓ | ✓ / ✓（未优化） | ✅ |
| **Zstd** | ✓ / ✓ | **✗ / ✓** | 仅 `N编→A解` |
| **Deflate / GZIP** | ✓ / ✓ | **✗ / ✓** | 仅 `N编→A解` |
| Bitcomp / ANS / GDeflate | ✓ / ✓ | **✗ / ✗**（NVIDIA 专有，需 `find_package`） | ❌ |

也就是说：**`A编→N解` 只能用 LZ4/Snappy/Cascaded/RLE，而它们在 AMD 上明确"未优化"**；
`N编→A解` 可以用 Zstd 拿到较好比率，但**位流互通需要用一帧真实数据验一次**
（hipComp 的 zstd 解码是从参考实现移植的，理论上吃标准 zstd 帧）。

这对本项目的意义（与 §12 的结论一致，且更强）：

1. 我们**不需要** nvComp/hipComp：自己的 HLSL 码流在两张卡上**逐字节一致**（§13.1），
   不用赌两个库的位流兼容，也不用把 CUDA/ROCm 运行时塞进游戏进程；
2. 如果哪天真要用第三方库，`A编` 这一侧（游戏跑在 A 卡）是短板——只有未优化的 LZ4/Snappy；
3. 顺带确认：**没有"悄悄退回 CPU"这种事**，失败是显式的 `throw`/错误码，不会变成
   "能跑但慢到爆"的静默降级。

## 14. 有没有更好的通用压缩路径？（三个候选，两个死路，一个 +67%）

§12 的码流在真帧上是 1.19 / 1.53 / 1.88。要再往上走，直觉上有三条路。**三条都量了**，
用的是同一个 32 帧 4K 数据集（`tests/lossless_bench/temporal_test.cpp`、
`predictor_test.cpp`、`exception_test.cpp`）。

### 14.1 死路一：帧间（时间域）差分 —— 不成立

`temporal_test` 的做法：`r = zigzag(mono(cur) − mono(prev))`，再用同一套 tile 记账。

| 流 | 帧内（现状） | 纯帧间差分 | 每 tile 自适应 min(帧内, 帧间) |
|---|---|---|---|
| MV | 1.53 | **1.16** | +0.0% |
| depth | 1.88 | **1.67** | +0.6%（p95 甚至 +47%） |
| colour | 1.20 | **1.15** | +0.6% |

**帧间比帧内差**，而且"每个 tile 自己挑更好的那个"几乎一分钱没赚。
原因是这份内容里相机一直在动、TAA 每帧抖 jitter —— **帧内的平滑性远大于帧间的相关性**。
（这不是"帧间预测永远没用"，而是"在这个 workload + 这个预测器上没用"；
如果是静态机位或用运动补偿，结论会不同 —— 但运动补偿就是另一个工程了。）

### 14.2 死路二：更好的帧内预测器 —— 不成立

MED（JPEG-LS）/ Paeth / 平均，对同一批真帧：

| 流 | left（现状） | MED | Paeth | avg |
|---|---|---|---|---|
| MV | 1.517 | +0.0% | −0.0% | −0.2% |
| depth | 1.886 | +0.1% | +0.0% | +0.1% |
| colour | 1.194 | +0.6% | +0.5% | +0.5% |

**为什么换预测器没用**：格式是"每 tile 一个位宽，取该 tile 内**最大**比特长度"。
一个离群像素就能把整块抬到 16 位，剩下 255 个像素预测得再准也省不下来。
**这直接指向真正的瓶颈。**

### 14.3 活路：例外编码（每 tile 主位宽 + mask + patch）—— +22%~+68%

同一个 tile、同一个预测器，只把"一个位宽管全块"换成：

```text
header  4 B: 1 bit 模式 + 5 bit 主位宽 w
mask    cnt × 1 bit          // 1 = 这个值放不进 w 位，走 patch
data    (cnt - n_out) × w bit
patch   n_out × 32 bit       // 原值直接存，保证无损
w 的选取：让 cnt + (cnt-n_out)·w + n_out·32 最小（每 tile 搜一遍，≤32 次）
```

实测（32 帧 4K，逐帧与现状对比）：

| 流 | 现状（每 tile max） | **例外编码** | 提升 | p5 | p50 |
|---|---|---|---|---|---|
| **MV** | 1.54 | **2.58** | **+67.6%** | 2.05 | 2.58 |
| **depth** | 1.89 | **2.46** | **+30.6%** | 2.36 | 2.43 |
| **colour** | 1.20 | **1.46** | **+22.4%** | 1.45 | 1.46 |

为什么它有效：**把"离群像素让整块买单"改成"谁分离谱谁付 32 位"**。
mask 一值 1 bit，换来的是主位宽从"最大值"降到"典型值"。

代价与收益：

- **没有熵编码**（不需要两趟、不需要第二套库、不需要赌位流兼容）；仍然是纯整数、定长块；
- 编解码都还是**一个 tile pass**，只是多一个 mask 和 patch 数组（patch 上限 = 全 32 位，
  所以最坏情况仍等于 raw 逃逸，slot 尺寸不变）；
- **顺带修掉 §13.2 的 AMD 解码问题**：解码可以改成「并行解包 + 每行 inclusive scan」，
  没有跨像素依赖链（现在慢 5 倍就是因为"读左邻居"的 256 级链）。

### 14.4 成本账要重算（第 12 节的 S / U 都变好了）

`exc` 提升后（MV 150% 流与 depth 150% 流按同样的 +60%/+28% 折算，标注为估算）：

| 变体 | colour | MV | depth | 合计 | 链路名义 | 净变化 |
|---|---|---|---|---|---|---|
| 今天 | 66.4 | 14.75 | 14.75 | 95.9 MB | 7.38 ms | — |
| §12 的 S（max 版） | 55.7 | 9.95 | 8.34 | 74.0 MB | 5.69 ms | −2.0 ms |
| **S′（exc 版）** | **45.5** | **≈6.2** | **≈6.5** | **≈58.2 MB** | **4.48 ms** | **≈−3.2 ms** |
| **U′（exc + MV 100%）** | 45.5 | **12.9–16.2** | ≈6.5 | **≈65–68 MB** | ≈5.0–5.2 ms | **≈−2.5 ms**，MV bit-exact |

**注意 U′ 这一行推翻了 §12 的裁决**：MV 全分辨率例外编码后是 12.9 MB（p50）到 16.2 MB（p5），
而今天是 14.75 MB —— **"用无损压缩替代 150% 降采样"从 ❌ 变成了"基本平价"**，
而画质从"边界带 p95 4.8 px 误差"变成 0（§12.6）。

### 14.5 如果还要更狠：把"字节预算"变成旋钮（有损但可控）

例外编码之后最自然的下一步不是熵编码，而是**在编码前做一次按 tile 的位截断**：

```text
先量化，再无例外编码：
  colour  每值砍到 16 位 → 33.2 MB（2:1）      平滑区仍然是 30+ 位，只有噪声块被削
  colour  每值砍到 12 位 → 24.9 MB（2.7:1）
  depth   每值砍到 12 位 → 12.4 MB            深度本来就不敏感（480×270 都能用）
```

注意：**不能**靠"给例外编码的主位宽设上限"来做这件事 —— patch 里存的是原始 32 位值，
把 `w` 压低只会让更多值掉进 patch，字节反而变多。有损只能来自"编码前的量化"这一步。
这也是它比 `R10` 聪明的地方：损失自动落在最脏的块上，平滑区保持全精度。

### 14.6 结论

**有，而且不需要任何第三方库：**
把 §6.1 的"每 tile 取最大位宽"换成**「主位宽 + 例外 mask/patch」**，
同一份 HLSL 从 1.54/1.89/1.20 变成 **2.58/2.46/1.46**（+68%/+31%/+22%，32 帧 p5 也已给出），
成本不变（同一趟、无熵编码、纯整数、slot 不变），还顺手修掉 AMD 解码慢 5 倍的依赖链。
帧间差分和换预测器这两条"看起来更高级"的路，实测都是死路 —— 因为瓶颈一直是被离群值
抬高的那个位宽。

## 15. 定案：N/A 混搭 + 颜色走 WGC + 无损 4K MV/depth

### 15.1 场景约束（用户给定）

```text
拓扑      NVIDIA + AMD 混搭，两种方向都要能跑（N渲染/A消费 是默认，A渲染/N消费 也要）
颜色      仍然走 WGC（不占跨卡链路）
目标      MV + depth **无损**、**全分辨率**（DLAA 档 = 渲染就是 3840×2160，取游戏实际给的尺寸）
动机      把 FG 的画质短板补掉：现在 150% 降采样在运动边界上的 4.8 px 矢量误差
```

颜色不在链路上，所以**链路预算只花在 MV + depth 上**，而且要求无损 —— 这就把问题
收敛成一个纯格式问题：**在"字节 ≈ 今天"的前提下，把两条流变成 bit-exact 全分辨率。**

### 15.2 方案（一句话）

**MV/depth 传 100% 全分辨率、用「例外编码」无损压缩（§14.3），生产端删掉两个 9-tap
降采样 pass、消费端用「并行解包 + 每行 scan」解码并删掉升采样 pass。**
颜色、WGC、槽位/信用窗口/fence 一律不动。

### 15.3 码流 v2（比 v1 更简单）

```text
tile     16×16 px（nw=1 时 256 个值，nw=2 时 512 个；真实数据里 1KB 级的块就够）
header   u32 : bit0..5 = w (0..31)，bit6 = mode (0 = 例外编码, 1 = raw 逃逸)
absolutes nw × u32   // 左上角像素，没有邻居可预测
mask     cnt bit      // 1 = 该值放不进 w 位 → 走 patch
data     (cnt − n_out) × w bit
patch    n_out × u32  // 原值直存 → 无损
```

- **v1 的"每 tile max 位宽"不是被删掉，而是它的特例**：`n_out = 0` 时例外编码 == max 模式，
  所以宽度搜索自然会在"更少的位"和"更少的 patch"之间选一个最优，不需要额外的 mode。
- 最坏情况仍然是 raw 逃逸（每 tile `4 + cnt·nw·4` 字节）⇒ 一条流的字节上限 =
  **原始大小 + 8 B/tile**（4K 是 32400 个 tile ≈ +0.26 MB，+0.8%）。所以共享堆按
  "raw + 0.8%" 预留即可，fence/信用窗口/槽位数都不变；要改的只是**载荷描述**
  （从"texture + 内容矩形"变成"buffer + 每 tile 长度数组"）。
- 纯整数、无熵编码、无第二趟、无第二套库；每 tile 多出的只是"32 桶位宽直方图"（≈32 条 ALU）。

### 15.4 三条流各自的处置

| 流 | 处置 | 依据 |
|---|---|---|
| colour | **不动**（WGC） | 用户约束；另外 colour 的帧内无损只有 1.46，且熵编码要 3–8 ms 才到 1.96 |
| **MV** | 100% 全分辨率 + 例外编码 | 33.18 → **12.8 MB（p50）/ 15.2 MB（p5）**，2.59x / 2.19x（32 帧实测 v2） |
| **depth** | 100% 全分辨率 + 例外编码 | 33.18 → **13.5 MB（p50）/ 13.8 MB（p5）**，2.46x / 2.41x（同上） |
| 元数据 | 不变（共享内存几百字节） | jitter / 相机 / 矩阵本来就是 0 成本 |

合计 **26.3 MB（p50）/ 29.0 MB（p5）**，对比今天的 `150/150` = **29.4 MB** ——
**无损全分辨率 ≈ 今天的字节**（p50 少 10%，最坏帧持平）。

### 15.5 成本与收益（4K，每真实帧）

| 项 | 今天（150/150） | **本方案（100 + 例外编码）** | 变化 |
|---|---|---|---|
| 链路字节 | 29.4 MB | 26.3–29.0 MB | ≈0（p50 −10%） |
| 链路占用 @40 fps（3x@120） | 1.18 GB/s | 1.06–1.21 GB/s | ≈0 |
| 生产端 SM | 0.60 ms（两个 9-tap） | **0.13 ms**（两次编码） | **−0.47 ms** |
| 消费端 pass | 升采样 JBU（0.2–0.5 ms，`--upsample` 开时） | **无**（尺寸已匹配） | **−0.2~0.5 ms** |
| 消费端解码 | —（现在是直拷） | 2 × 0.1–0.15 ms（scan 形状的**目标值**，见 §15.7 步 3） | +0.2~0.3 ms |
| MV 误差 | 边界带 EPE p95 **4.81 px**，p99 45 px | **0（bit-exact）** | 画质问题的根被拔掉 |
| depth 误差 | 中值降采样 + 重建 | **0（bit-exact）** | 同上 |

一句话：**同样的总线字节，换来 bit-exact 的 4K MV+depth，渲染卡还少花 0.47 ms。**
从"要付 15%"变成"付同样的钱、拿更好的画质、渲染卡更轻"。

### 15.6 与其它候选的对比（为什么是它）

| 方案 | 字节/帧 | 画质 | 生产端 | 结论 |
|---|---|---|---|---|
| 今天：150/150 + 9-tap | 29.4 MB | 边界带 4.8 px 误差 | 0.60 ms | 基线 |
| **本方案：100 + 例外编码** | **26.6–30.3 MB** | **bit-exact** | **0.13 ms** | ✅ **最优** |
| 100 + max 位宽（§6.1） | 33.2+33.2 = 66 MB | bit-exact | 0.13 ms | 字节翻倍，淘汰 |
| 100 + nvComp Zstd | ~17+17 MB | bit-exact | 3–8 ms | 渲染卡亏死，淘汰 |
| 100 + hipComp | A 卡**没有** zstd 压缩（§13.3） | — | — | 不可用 |

| 150/200 + 例外编码 | ~20 MB | 有损（4.8 px） | 0.13 ms | 只在链路真的不够时作为降级档 |

### 15.7 落地顺序（每步都有现成判据）

1. **codec v2**：`fr_codec.h` 加例外编码（`n_out=0` 自动退化成 v1 行为，可 A/B），
   `fr_codec_test` 的 300 组 fuzz + 真实帧必须仍然 bit-exact；`exception_test` 的
   2.58 / 2.46 由实现复现（误差 < 1%）。
2. **HLSL v2 + 厂商矩阵**：`tests/gpu_codec` 在两张卡上跑——**字节跨厂商一致 + 与 CPU 一致 +
   回环 OK**（已有工具，改 shader 即可）；同时量出 v2 的编码/解码 ms。
3. **解码形状**：把"读左邻居"改成「并行解包 → 每行 inclusive scan → 加行首种子」，
   判据：AMD 解码 ≤ NV × 1.5（当前是 5.3×），且 4K 单流 ≤ 0.15 ms。
4. **接生产端**：`scale_dispatch()` → `encode_dispatch()`（两条流），
   `StreamPercent*` 固定 100；`fakerFG.ini` 新增 `MvCodec=exc|raw`、`DepthCodec=exc|raw`
   （默认 raw，灰度验证后再默认 exc）。
5. **接消费端**：解码写进本地 ring，**跳过 `record_upsample`**；`active_mask`/`stream_bytes`
   如实上报；每帧 ratio < 1 时自动 raw 逃逸（格式内建，等价于今天）。
6. **协议**：`kSharedVersion` +1；`streams[i]` 增加 `codec` 与 `tile_len` 偏移；
   槽位容量/放置/信用窗口不变。
7. **端到端验收**（4K/40 锁定 3x）：
   `show ≥ 119`、`presents/vblanks ≥ 99.5%`、`HITCH ≤ 1`、无 reset；
   `stream_bytes` ≈ 26–30 MB；`--dump` 的 MV/depth 与游戏原值**逐字节相同**；
   边界带 EPE = 0。

### 15.8 风险与回退

| 风险 | 处理 |
|---|---|
| 例外编码的 patch 让最坏帧变大 | 每帧 ratio < 1 → 整条流 raw 逃逸（格式内建），字节上限 = 今天 |
| A 卡解码仍慢 | 第 3 步的 scan 形状是硬前提；不达标就不合并解码步骤（保留直拷 + 无损关闭） |
| DLAA 下 MV/depth 尺寸与输出不同（某些游戏的 depth 是 1/2） | 以 `streams[i].width/height` 为准，`fnv` 的 tile 划分按实际尺寸走；不需要 upsample |
| WGC 的配对抖动（既有问题） | 本方案不引入新变量；MV/depth 仍按 publication/槽位配对 |
| 逐帧 ratio 波动（p5 16.2 MB） | 预算按 p5 算；`--link` 的 OSD 百分比会如实显示 |

**编码端也并行化了**（4K、33 MB、NV）：2.87 → **1.22 ms**。做法：block-per-tile、
每线程负责一个值 —— LDS 暂存像素 → **每 warp 独立直方图**（8×33 槽，InterlockedAdd 争用降 8×）
→ 合并后选 mode/宽度 → mask 用 InterlockedOr → 块前缀和算位偏移 → **每个线程把自己的位
OR 进 LDS 输出缓冲** → 合并刷出（合并访问）。

当前两卡（4K、单流 33 MB）：

| 流 | NV enc | NV dec | AMD enc | AMD dec |
|---|---|---|---|---|
| MV（4K 33.2 → 11.2 MB，2.97x） | 1.02 | **0.58** | 1.38 | 1.98 |
| depth（4K 33.2 → 13.6 MB，2.44x） | 1.02 | 0.72 | 1.41 | 2.08 |
| **1080p（8.3 MB 单流）** | **0.23** | **0.15** | **0.87** | **0.64** |

⇒ **1080p 渲染尺寸下两条流（MV+depth）NV 编码 0.47 / 解码 0.31 ms，已在预算内**；
4K 下 NV 解码可用（0.58–0.75），但编码（2.0 ms/两流 vs 今天 9-tap 的 0.60）还是短板。

**消融地图**（避免再猜；都是临时改一行、跑一次、再回退）：

| 消融项 | 结果 | 说明 |
|---|---|---|
| AMD 解码：跳过块扫描 | 2.04 → **1.70 ms** | 块前缀和值 **0.34 ms**（17%），换"每行位偏移表"（+16 B/tile ≈ +4.6% 字节）可整块消除 |
| AMD 解码：纯拷贝地板 | 0.97 ms | 剩 ~0.73 ms 在行扫描（5 barrier）/列链/存储 |
| AMD 解码：全零输入（width=0） | 2.04 ms ≈ 真实 1.98 | **位解包在 AMD 上不是瓶颈** |
| NV 编码：跳过 e_out 原子 | 1.02 → **0.85 ms** | 每值一次 `InterlockedOr` 值 **0.17 ms**（17%）；剩下 ~0.85 ms 在 staging 读 / 直方图原子 / 扫描 / flush |

结论：两边都还差 3–8×，但**瓶颈已经从"算法"变成"每 tile 的固定往返"**（barrier、LDS、原子）。
下一步的性价比顺序：① 每行位偏移表（−0.34 ms AMD 解码，+4.6% 字节）；
② 编码端按输出字分工替代原子；③ 每 block 处理 2 个 tile 摊薄 barrier。

**试过但失败的两个形状**（都已在代码里回退，记录备查）：

| 尝试 | 结果 | 原因 |
|---|---|---|
| 行内前缀和搬进寄存器（`uint myacc[2]`） | 解码 0.91 → 1.25 ms（更慢） | 动态下标 `myacc[l]` 掉进 scratch（本地内存），比 LDS 还慢 |
| 编码端 256 线程 block + LDS 暂存像素 | 编码 2.15 → **15.9 ms** | 255/256 线程空转，且 `hist[33]`/`over[33]` 的 scratch 按 256 线程分配（X4714） |

由此得到的结论：**编码端的并行化必须让每个线程都干活**（LDS 原子直方图 + 每线程把
自己的值 OR 进 LDS 输出缓冲，最后合并拷贝），不能沿用"一个 tile 一个线程 + 别的线程帮忙搬数据"。

**还没吃到的三块**：① 阶段 A 的解包仍是每值一次标量 `Src.Load`，没向量化；
② 行内 O(c) 求和没换成 LDS scan（32 宽 → 最坏 31 步）；③ AMD 的 LDS/barrier 代价明显高于 NV
（同 kernel 0.92 vs 3.7），需要单独 profile。
**编码端**（2.15–2.9 ms）必须按上面那条重写，才能回到 0.13 ms 量级。

### 15.9 一句话回答

**做"100% 全分辨率 + 例外编码 + scan 解码"这一件事就够了**：
字节数与今天的 150/150 打平（26.6–30.3 vs 29.4 MB），画质从"边界带 4.8 px 矢量误差"
变成 bit-exact，渲染卡还省 0.47 ms；不用 nvComp/hipComp、不用熵编码、不用时间域预测、
不用任何新的库或运行时。颜色按既定约束继续走 WGC，一个字节都不动。

## 16. 4K 定案对比：整条链路成本 vs 原有升降采样

场景固定：4K、N/A 混搭、**颜色走 WGC 不占链路**，链路只承载 MV + depth。
所有 ms 都是本机实测（RX 6750 GRE / RTX 3080 Ti，`tests/gpu_codec` 与 `tests/lossless_bench`）。

### 16.1 单件成本（每真实帧、4K）

| 工序 | 4K 全分辨率（33.2 MB/流） | 150% 流（14.75 MB/流） |
|---|---|---|
| 9-tap 降采样（今天） | — | **0.30 ms**（`lpbench`） |
| 例外编码 | **1.02 ms**（NV）/ 1.38（AMD） | 0.46 ms / 0.84 |
| 解码 | **0.58（MV）/ 0.72（depth）** NV；1.98 / 2.08 AMD | 0.32 / 1.12 |
| 链路（实测 0.023 ms/MB，= 66 MB 颜色 1.5 ms 反推） | 11.2 MB → 0.26 / 13.6 → 0.31 | 6.2 MB → 0.14 |

### 16.2 四种配置的整条账（两条流合计）

| 配置 | 渲染卡 SM | 链路字节 | 链路代价 | **渲染卡合计** | 消费卡解码 NV / AMD | 画质 |
|---|---|---|---|---|---|---|
| **A 今天**（150/150 + 两个 9-tap） | 0.60 | 29.4 MB | 0.68 | **1.28 ms（5.1%）** | 0 / 0（+0.2–0.5 升采样） | 边界 EPE **4.8 px** |

### 16.3 三条结论

1. **渲染卡：今天最便宜。** C 比 A 贵 **+1.33 ms（+5.3 个百分点）**；
   B（降采样后再压）只贵 0.5 ms 且字节少 58%（但画质与今天一样，属于"买带宽"）。
2. **消费卡余量：以 1.2.2 的实机日志为准（2026-11-21 修正）。**
   `TIMING_4K40.md` §4.2 的 `20.6 + 8.33 = 28.9 > 25.0` 是**旧配置**（keep2x 之前）。
   实机 4K/3x@40（`lock_frame_port_3x.log`，`--mfg-model=keep2x`）：

   ```text
   game clock: in 39.9 fps (25.06 ms) -> kept=40 dropped=0
   breakdown: gpu=6.7–8.3ms present=7.3–7.7ms total=14.6–16.7ms load=56–63%
   bus: mv 14.1MB + depth 14.1MB = 28.1MB/frame (1.1 GB/s at 40 fps)
   show=118  presents=118/120  xN=3.00  drops=0
   ```

   ⇒ **消费端还有 ~9 ms 余量**（`load` 只占 56–63%），不是"零余量"。
   而且这台机器的消费卡是 **AMD 6750 GRE**，所以要看的是 AMD 解码：
   **M = 1.98 ms（load → ~71%）、C = 4.06 ms（load → ~79%）**，两者都塞得下 3x。
   代价是 C 吃掉约 44% 的余量，且 AMD 解码与 XeFG 抢同一个 SM —— 需要实机确认 `show` 是否掉。
3. **C 目前是"画质采购"而不是"省钱手段"**：+1.33 ms 渲染卡 + 1.3~4.1 ms 消费卡，
   换来边界带矢量误差 4.8 px → 0。是否值得取决于 4K 跑 2x 还是 3x。

### 16.4 还有哪些优化空间（按实测收益排序）

| # | 优化 | 收益 | 代价/风险 |
|---|---|---|---|
| 1 | **编码器 3× 提速**（1.02 → 0.35） | C 的渲染卡成本 2.04→0.70，合计 **2.61 → 1.27 ≈ A**，即"C 变成免费" | 需要 profiler（消融显示瓶颈在每 tile 的固定往返 + 原子，不是算法） |
| 2 | **depth 走 R16（有损）** 而不是编码 | depth 字节 14.75 → 7.4 MB，代价只有一次 ~0.15 ms 的转换（vs 编码 0.46）；深度实测不敏感（480×270 都够用） | 有损，但 `FINAL_CONFIG.md` §2.1.2 已证明深度分辨率不敏感 |
| 3 | **消费卡解码 1.30 → ≤0.3**（C 在 NV 上）| 让 4K/3x 有可能收下 | 同 #1，需要 profiler；AMD 差距更大（4.06 vs 1.30） |
| 4 | 只解 MV（M 方案），depth 保持降采样 | 消费卡解码 0.58 / 0.90，渲染卡 +0.64 | 已是最小改动版本，质量收益集中在 MV（边界 EPE 的主因） |
| 5 | 每行位偏移表 | AMD 解码 −0.34 ms，+4.6% 字节 | 又一轮位流变更 |

**结论（4K，修正后）**：消费端有余量（~9 ms），所以瓶颈回到**渲染卡**：

- **想省渲染卡的钱**：今天最好（1.28 ms）；
- **想买 MV 的无损**：M，+0.64 ms 渲染卡 + 1.98 ms AMD 解码（load 56→71%）；
- **想买全比特精确**：C，+1.33 ms 渲染卡 + 4.06 ms AMD 解码（load 56→79%），**现在就能跑**，
  但吃掉 44% 余量；是否值得看 4K/3x 下 `show` 会不会从 118 掉下来。

### 17.2 主机侧契约（写进代码时不能错的三条）

```text
cbuffer b0 : W, H, NW, TilesX, TilesY, SlotWords      // 6 x 32-bit root constants
几何       : tile = kTileW x kTileH = 32 x 8 = 256 像素；NW = 1（MV / depth 都是 4 B/px）
输出       : 每 tile 一个 "slot"（SlotWords 个 32-bit 字）+ TileLen[tile] = 实际字节数
容量       : 按 raw 最坏情况取值 = 4 + 256*NW*4 字节/tile（NW=1 → 1028 B，建议 SlotWords=264）
```

### 17.2b 生产版 shader 已改成 texture↔buffer（2026-11-21 晚）

原来的 kernel 是 buffer I/O，而链路上 MV 的两端都是 **texture**（游戏资源 → `g_mv_local[]`）。
现在 `src/shaders/fr_codec.hlsl` 是生产形状，**两个 entry point 同一个文件**：

```text
Encode : Texture2D<float2> SrcTex(t0)  -> RWByteAddressBuffer DstBytes(u0) + TileLen(u1)
Decode : ByteAddressBuffer SrcBytes(t0) -> RWTexture2D<float2> DstTex(u0)
```

（fxc 允许同一 register 上声明两个资源，只要每个 entry 只用其中一个 —— 已用探针验证。）

**位型为什么不会变**：像素侧走 `f16→f32→f16`。对全部 **65536** 个 fp16 位型做过穷举：
**除 NaN payload（2044 种）会被规范化成 0x7E00 之外，其余全部逐位不变**（含 ±0、denormal、±Inf）。
MV/depth 不含 NaN，所以字节流与 buffer 版完全一致。

`lock_frame/build.sh` 的 producer 与 consumer 都已编译这两个 entry（`kFrEncodeCSO` 22 KB /
`kFrDecodeCSO` 9.2 KB），两个产物都构建通过。

默认路径的代码逐行未变；`1` 才走码流。回退只需把 `MvCodec` 改回 0 重开游戏
（协议版本两边一致，不需要换回旧 exe）。

判据（4K/3x@40，`run_3x.bat`）：`bus` 28.1 → ≈25.9 MB/帧、`presents` 不掉、
MV 与 `MvCodec=0` 的输出逐位一致（无损）。

### 17.5 第一次真机跑（MvCodec=1）的两个坑

生产端一次就对了：`fr: encode pass ready` → `fr: encode mv 3840x2160 -> 32400 tiles`
→ `publish #1 mask=0x3 mv=3840x2160 depth=2560x1440`，`dropped=0`。
消费端在 `open_shared()` 之后 `CreateForWindow FAILED` 退出，没走到解码。

1. **reserve 从 960 MB 涨到 2194 MB**（两处叠加）：MV 槽按 `slot_w/h`(3840x2304) 而不是
   1:1 content(3840x2160) 定尺寸；而 MV 走 100% 又把共享容量顶到 3840x2304，于是 **depth
   槽**从 16 MB 涨到 35.4 MB/槽（32 槽 = +620 MB）。修法：codec 槽按自己的 content 定尺寸
   并发布自己的 `slot_w/h`，容量只跟 depth（→ 约 1.6 GB），编码端加「tiles > 槽容量就丢 MV」的钳位。
2. **capture item 与传输建立是竞态**：`open_shared()` 一返回就 `CreateForWindow`，此时游戏
   常常还在切呈现模式（独占全屏时 WGC 恒失败），旧代码直接 `return 7`。改成 10 s 重试
   （250 ms 一次，句柄失效按 pid/exe 重找）。

顺带一条读日志的经验：`flags=0x0`（而不是 0x21D1）表示消费端读头时生产端还没发布过第一帧，
`producer.declared_frames`/相机等声明都是空的；每帧 publish 都会重写这些字段，所以只影响启动那几行日志。

### 17.6 第二次真机跑：设备被移除（INVALID_CALL）

两条 codec 运行时游戏直接退出，报 `present: xefg failed 0x887A0005, device reason:
INVALID_CALL`，紧接着游戏自己的 crash handler（0x80000003）。消费端日志证明它只是被牵连
（`pid ...: 0 visible window(s)`），真正被移除的是**渲染卡（游戏进程）的 device**，时间点正好
是 `publish #1`（第一帧编码刚提交执行）。

reserve 的浪费已在这一轮修掉（`2194.1 MB -> 1526.1 MB`，`capacity 2560x1536`，槽 `34275328 B`）。
真正的违规点是两个 D3D12 用法错误：

1. **raw UAV 描述符少了 `D3D12_BUFFER_UAV_FLAG_RAW`。** `Format=UNKNOWN` + `StructureByteStride=0`
   只有在 `Flags=RAW` 时才是一次 raw view；离线 harness（`tests/gpu_codec`）用的是 **root
   descriptor**（无格式），所以这条路径从没被测到。
2. **TileLen 以 `COMMON` 创建却被 shader 当 UAV 每帧写。** buffer 不能以 COMMON 创建，
   现在以 `D3D12_RESOURCE_STATE_UNORDERED_ACCESS` 创建。

另外为了确诊留了两个诊断档（`fakerFG.ini` 的 `MvCodec`）：
`2` = 编码写本地私有 buffer（不碰跨卡槽，用来判断「跨卡 buffer 作 UAV」是否合法）、
`3` = 只建描述符/做状态转换但不 Dispatch。两档都会照常建槽、强制 MV 100%。

### 17.7 真凶：raw UAV 必须是 R32_TYPELESS（2026-11-21 结案）

三档全崩之后打开 D3D12 校验层（生产者 `fakerFG.ini` 的 `D3dDebug=1` 在游戏进程里、游戏建
device 之前开层，并把设备校验消息每帧镜像进 `Cyberpunk2077_mfg_producer.log`；消费者用
`--d3d-debug`），调试层一句话就定位了：

```
ID3D12Device::CreateUnorderedAccessView:
  When creating a RAW Unordered Access View, the format must be DXGI_FORMAT_R32_TYPELESS.
ID3D12Device::RemoveDevice: DXGI_ERROR_INVALID_CALL ...
```

- 正确写法：`Format = R32_TYPELESS` + `StructureByteStride = 0` + `Flags = RAW`；写 `UNKNOWN`
  是无效组合（执行期未定义 → 设备被移除，且要等 20–30 s 才爆）。
  离线 harness 用的是 root descriptor（无格式），所以这条路径此前从未被覆盖。
- 顺带确认：buffer 的 `InitialState` 一律被忽略（"Buffers are effectively created in state
  COMMON"），UAV 初态无害；消费者侧校验消息为 0，说明 buffer 槽放置与解码路径是干净的。
- 两侧放置 MV 槽的 `D3D12_RESOURCE_DESC` 已对齐（都带 `ALLOW_UNORDERED_ACCESS`）：
  跨卡 placed resource 两端描述必须完全一致。
- `D3dDebug=1` 会把游戏自身的非法状态转换也判死（日志里 PostFX 列表的 CopyResource /
  ResourceBarrier 状态不匹配），所以它只用于取证，A/B 时必须关掉。

### 17.8 两条流独立：四种组合都合法

`MvCodec` 与 `DepthCodec` 各自判定，互不影响（`stream_codec(int)`）。实测组合：

| MvCodec | DepthCodec | 生产端 | 消费端 | 升采样 | reserve |
|---|---|---|---|---|---|
| 0 | 0 | 纹理槽 + copy | 跨卡 copy | 需要 | 960 MB |
| 1 | 0 | MV 4K 编码 + depth 2K 纹理 | MV decode，depth copy | 只服务 depth | ~1.6 GB |
| 1 | 1 | 两条都 4K 编码 | 两条都 decode | **不需要** | 2.1 GB |
| 0 | 1 | MV 2K 纹理 + depth 4K 编码 | depth decode，MV copy | 只服务 MV | ~1.6 GB |

各自独立的锚点：`read_percent()`（每条流各自强制 100）、`layout_streams()` 的 per-stream
`codec` 位与 `slot_w/h`、`place_slots()`（buffer vs texture）、`on_record` 的两段 encode/skip
分支；消费端是 `mv_codec_shared()` / `depth_codec_shared()` 两个谓词加两段 decode 分支。

混合档（MV 4K + depth 2K）特别验证过两处容易踩的地方：

- `record_upsample` 必须**继续运行**（depth 只有 2560×1440，不抬到 4K 会让 XeFG 报
  `ERR_INVALID_ARGUMENT`）；此时它的 MV 半边是 1:1 恒等重采样，只有 depth 被放大。
- 容量只由非 codec 流决定（codec 流按自己的 content 发布 `slot_w/h`），否则 depth 的纹理槽
  会被 MV 的 4K 撑成 35 MB/槽。

两端的启动日志会各打一行 `fr: transport plan: mv=codec 3840x2160 depth=texture 2560x1440 ...`，
A/B 时直接看这一行就知道跑的是哪一档。

### 17.9 源尺寸不匹配（DLSS 档位不同）

XeFG 要求 tag 的 MV 与 depth **同尺寸**，但游戏给的源不一定：常见是 DLSS 质量档
MV 在输出分辨率（3840×2160）、depth 在渲染分辨率（2560×1440）。旧方案靠
`StreamPercent` 把两条流都降到同一个尺寸来掩盖，codec 则各自保持 1:1，尺寸差异会原样
保留下来。

处理方式（消费端自动，无需开关）：

- `refresh_input_geo()` 发现 `mv_w/h != depth_w/h` 时，**自动打开联合重建 pass**
  （`g_upsample`），并打一行
  `MV 3840x2160 and depth 2560x1440 differ - the reconstruction pass is forced ON ...`。
  这个 pass 就是归一化器：两条流各自从自己的尺寸重采样到**输入画面尺寸**再 tag。
  其中已经 1:1 的那条是恒等重采样。
- `--no-upsample` 仍然可以显式关掉它（A/B 用），但那样 XeFG 会因为尺寸不一致拒绝帧，
  所以会额外打一条 WARNING。
- codec 流仍是**无损**的：重建 pass 只处理"游戏本来就只给了 2K"的那条流，无损性指的是
  「渲染卡上那份数据 → 消费卡」不变。

带宽上的选择权留给人：`StreamPercentDepth=100`（depth 原生 1440p，14.1 MB）还是
`150`（1707×960，6.3 MB，再由消费端放大）。两者消费端都能正确归一化。

### 17.10 整体性能账与 N/A 混搭兼容（2026-11-21 实测）

#### 真机数据（三个游戏，默认 `MvCodec=auto DepthCodec=auto`）

| | CP2077 4K/3x | PBZ 40x3 | Wuchang 40x3 |
|---|---|---|---|
| 流尺寸 | MV 3840x2160 + depth 3840x2160 | 2562x1441 x2 | 2558x1439 x2 |
| 传输 | MV codec + depth codec | 同（wide depth 先转 R32） | depth codec（MV 走光流） |
| 解码 | 都是 1:1 成功 | 同 | 同 |
| presents | 103/107 窗口 120/120 | 67/69 120/120 | 25/43 120/120（余下 118/119 由 `--interp-cadence` 造成） |
| load | 68% | 64–69% | 20–67% |
| coded bytes | — | — | **depth 7.0–7.6 MB/帧（raw 14.06，1.86–2.21x）** |

#### 单次成本（离线基准，4K 单流 33 MB）

| 阶段 | RTX 3080 Ti | RX 6750 GRE |
|---|---|---|
| encode | 1.02 ms | 1.38–1.41 ms |
| decode | 0.58–0.72 ms | **1.98–2.08 ms** |

N/A 混搭（NV 渲染 + AMD 消费）的净增量就是 `+1.02 ms`（渲染卡，含替换掉 0.34 ms 降采样）
和 `+1.98 ms`（消费卡，同时省掉 14.1 MB 的跨卡拷贝与升采样里 MV 那半边）。反向混搭
（AMD 渲染 + NV 消费）是 `1.38 / 0.6 ms`，更宽松。

#### 还能优化的四处（按收益排序）

1. **AMD 解码的固定往返**（消融测得 0.34 ms 的块扫描 + 布局，与负载无关）：把每个 group
   处理 2 个 tile（group 数 32400 → 16200），预期 1.98 → ~1.7 ms。这是消费卡的主项。
2. **NV 编码的按值 LDS 原子**（0.17 ms）：用 warp shuffle 归并后由 leader 单写，预期
   1.02 → 0.85 ms。
3. **槽步长 264 → 258 words**：映射/地址空间 -2.3%，无性能影响（纯省内存）。
4. **两条流都 1:1 时跳过升采样 pass**：已自动生效（CP2077 双 codec 时不打 `rebuilt`）。

总线侧已经没什么可挖：Wuchang 7.0 MB/帧 @40 fps = 280 MB/s，CP2077 双流约 19 MB/帧 =
760 MB/s，都只占 13 GB/s 链路的 2–6%。**这条链路买的是画质，不是带宽。**

#### 硬件不支持时的降级（本轮实现）

`MvCodec` / `DepthCodec` 现在是三态：`0` 关、`1` 强制开、`auto`（缺省值）＝能跑就用。
`auto` 在**布局之前**由 `fr_resolve_codec()` 判定（槽类型是布局的一部分，中途不能切）：

- 探测：`ensure_fr_objects()`（根签名 + MV/D32 两个 PSO + TileLen 缓冲）能否创建；
- 格式门：MV 必须 R16G16_FLOAT；depth 必须 R32_TYPELESS / R32_FLOAT / wide（后者先转 R32）；
- 任一门失败 → 该条流 `codec=0`，照旧走 `copy_stream`，并打一行
  `fr: codec capability: pass=..., mv fmt 34 ok, depth fmt 19 ok -> MV CODEC(1:1), depth CODEC(1:1)`。

运行期不切换（会破坏布局），但消费端有预算看门狗：codec 开着且 `load` 连续 3 个窗口 ≥85%
时打一条 WARNING，建议把该流改回 0 并重启。
