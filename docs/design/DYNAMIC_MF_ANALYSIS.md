## 第二部分：consumer 数据字典

> 每个字段：**来源 → 算法 → 真实含义 → 容易怎么被误读**。
> 这一节是本轮调试成本最高换来的东西。

### 2.1 输出侧

| 字段 | 来源 / 算法 | 真实含义 | 易误读 |
|---|---|---|---|
| `show=` | `GetLastPresentCount` 窗口增量 ÷ 窗口时长 | 交换链**交付**帧率（平均） | 只是平均值。119.2 与 118.5 可能观感差很多 |
| `out:` presents/expected | 同上 ÷ `Σ applied_k` | 我们请求的张数里，实际上屏的比例 | 含"输入被丢"与"面板丢"，两者性质不同 |
| `presents/vblanks` | 上屏数 ÷ (窗口×refresh) | **面板填充率**（最接近"显示端真实"） | 用假设的 refresh 算；必须用实测周期 |
| `xN=` | `GetLastPresentStatus().framesPresented` 窗口均值 | XeFG 每批**实际**出了几张 | 平均值会掩盖"该出 3 只出 1" |
| `vphase` | `(t_present − t0) mod period` | 我们**提交**落在 vblank 周期的位置 | 在 Present **之前**取值 → 是"我们循环的时刻"，不是显示落点 |
| `HITCH` | 到达 gap 远大于期望输入间隔 | **输入**侧的长间隔 | 不等于显示端卡顿 |

### 2.2 输入侧

| 字段 | 来源 / 算法 | 真实含义 | 易误读 |
|---|---|---|---|
| `arr=` | 我们循环的 WGC 到达间隔 EMA | **我们**的消费节拍（受 pacer 限制） | 曾被我当成"游戏的帧率" |
| `pin=` | producer `frame_time_ms` 的 16 样本中位数 | **游戏真实帧间隔**（每呈现帧一次） | 唯一可用的决策输入 |
| `pq=` | `frame_qpc_ms` 差 ÷ `frame_id` 差 | Evaluate 时刻的间隔（诊断） | **不是**帧间隔（一帧 Evaluate 多次） |
| `jitter=min..max` | 窗口内到达间隔极值 | 输入的抖动范围 | 极值受单个异常帧影响 |
| `arr_gaps=` | WGC 到达被丢弃的次数 | 我们跟不上捕获的帧数 | 与 `qdrop` 不同层 |
| `qdrop` | 颜色队列溢出次数 | **被丢掉的输入帧**（内容跳的来源） | 输出填充可能完全不受影响 |
| `age=` | 捕获帧在 WGC 里等了多久 | 捕获延迟 | 是排队不是工作 |

### 2.3 决策侧

| 字段 | 来源 / 算法 | 真实含义 | 易误读 |
|---|---|---|---|
| `k / m / paced` | 控制器的 Decision | 本帧要输出几张、间距、是否量化输入 | k 是**请求**，实际见 `appliedK` |
| `q=` | `|slots − k·m| / k` | 长保持率：每张输出被多保持的 vblank 占比 | 只在 m>1 时有意义 |
| `regime=` | fillable / cap-limited / input-limited | 输入是否够 J 张、是否快于面板 | cap-limited 会**永久**降低 learnedJ（若被门控误伤，已修） |
| `reason=` | held/up/down/deferred/reuse/hitch… | 本帧决策原因 | `deferred` 多说明门限在挡 |
| `rhythm` | `|k − slots|`；`spacing err = |T/(k·V) − 1|` | **决策**与输入的错配 | 预算 = k·V 时它不代表实际间距 |
| `swloss` | `Σ(expected − presents)` / 切换次数 | 每次换档平均少上屏几张 | 含在途帧和输入丢帧，偏高 |
| `cskip` | 因预测到阻塞而跳过 sink 拷贝的帧数 | 止损次数 | 应为 0 才算健康 |
| `late` | pacer 到期时 `now` 已过槽位 | **不可用**（Present 阻塞后取值） | 恒为高，无诊断价值 |

### 2.4 处理侧（breakdown）

`capture`（取帧排队）/ `work`（提交）/ `present`（Present 阻塞）/ `gpu`（等上一帧 GPU）/
`colour`（66MB sink 拷贝）/ `mvs`（MV/depth 拷贝）/ `copy`（等拷贝落地）/ `total`（整帧）。

判读要点：`total` 的 **p95** 才是决定能否踩上 vblank 预算的量（均值没意义）；
`colour` 超过 40 ms 会触发止损（`cskip`），历史上有 207–222 ms 的阻塞。

## 第三部分：动态多帧的本质

### 3.1 一句话

> **动态多帧不是一个"控制"问题，而是一个"整数分配 + 时间轴对齐"问题。**
> 控制器能做的只有一件事：在"间距不齐 / 丢输入帧 / 面板丢帧"三者之间选一个，
> 而**选哪个由 `f` 与 `R` 的算术关系唯一决定**，没有第四个自由度。

### 3.2 推导

设面板周期 `V`（实测 8.3332 ms），输入间隔 `T = 1/f`，每批输出 `k` 张。

1. 批次起点必须在 vblank 上，且一批的 k 张必须正好铺满 k 个 vblank
   （少铺 = 面板重复一张；多铺 = 面板丢一张）。
2. 于是每批占用时间 `k·V`，批次率 = `1/(k·V)`，**输入消费率 = `1/(k·V)`**。
3. 而输入到达率是 `1/T`。两者之差只能体现为：
   - `1/T > 1/(k·V)` → 输入帧被丢（**内容时间跳变**）；
   - `1/T < 1/(k·V)` → 批次等不到输入 → 出现空洞（**间距跳变**）。
4. 若允许 k 每批变化，让 `Σk/Σvblank = R/f`：平均对齐，但**间距随 k 变化**（carry）。

**所以三种代价是互斥的，且是算术的**：

| 策略 | 谁来吸收 `|k·f/R − 1|` | 观感表现 |
|---|---|---|
| k 固定 + 预算 `T` | 间距（每批被压缩/拉伸） | 间距误差 ~6–8%，**不丢帧** |
| k 固定 + 预算 `k·V` | 输入帧（每 `1/e` 批丢 1 帧） | 间距完美，**内容跳** |
| k 交替（carry） | 两者各一半 | 间距 ±50% 交替，不丢帧 |
| VRR | 无（面板跟随） | 完美（本机不可用） |

### 3.3 三个额外的"非算术"损伤源（这才是我们能赢的地方）

1. **速率估计不准** —— 已踩三次坑。估小 9% → k 掉档 → 输出掉 20%。
2. **单帧超时** —— `total` 的 p95 ≈ 26.5 ms > 25 ms 预算时，约 1/5 批次踩不上槽
   （相位 std 从 0.16 → 1.4 ms）。
3. **3x/4x 模型** —— 复用同一组 MV，几何上自相矛盾；2x@58 fps 顺、3x@40 fps 卡，
   其中一部分与 cadence 无关。

### 3.4 已被数据否定的方向

| 方向 | 为什么不行 |
|---|---|
| 调 hold / deadband 求"顺" | 只是在"平均 vs 间距"上挪位置，动不了 3.2 |
| epoch 档位 | 低档停留 + 整档跳变（HITCH 16 vs 2） |
| out-clock / 缓存捕获帧 | capture 等待 78–87 ms，prefetch 命中 40/40 → 13/17 |
| 逐帧 mean/phase 选 k | 15–31 switches/s，每次换档丢 ~1 张 |
| 用 `--lock` 自己把输入压到 R/k | 丢帧发生在之后，那一批仍跨 2 个输入间隔 —— 只能"规则化" |

### 3.5 结论

1. **整除点必须完美**（锁 40/60 已做到间距 0.1%、min 118）；
2. 非整除点**按算术选一个代价并明确接受**，不让三种代价随机混合；
3. 非算术损伤（估计、超时、模型）逐个降到 0 —— 这部分确定能做。

## 第四部分：方案

### 4.1 决策规则（只用测得的 `f`，不含任何场景常量）

```
输入：f（per-present 中位数）、R（实测刷新）、J（容量）
对候选 k ∈ [2, J] 计算：
    out(k)  = k · f
    e(k)    = |out(k)/R − 1|            // 输出率误差
    under(k)= out(k) ≤ R                // 会留空洞（不丢输入帧）
    over(k) = out(k) > R                // 会丢输入帧（间距完美）

规则（优先级从上到下）：
1. 若存在 k 使 e(k) ≤ 0.02        → 锁该 k，预算 k·V     （整除点，完美）
2. 若存在 under k 使 e(k) ≤ 0.05  → 用该 k（取最大者），预算 k·V（≤5% 空洞）
3. 否则用 k = ceil(R/f)，预算 k·V（丢 e 比例的输入帧）
```
第 2 条的依据：2x@58 fps（=3.3% 空洞）主观"顺"，而 7% 内容跳"卡"。
**宁可少几帧，也不要内容跳。**

换档仍用死区：新 k 的 `e` 比当前好 >3% 且连续 3 帧 → 才换（防止整数边界抖动，
锁 40 曾因此 76 次/53 窗）。

### 4.2 速率估计（唯一信源 + 抗尖峰）

- 信源：producer `frame_time_ms`（每呈现帧一次的 EMA）；
- 抗尖峰：16 样本中位数 + **斜率限制**（每帧允许变化 ≤2%，相当于 50 ms 时间常数）；
- 只在"连续 8 帧都在同一侧超出"时才真正接受速率阶跃（防止场景切换被平滑掉）；
- 日志保留 `arr / pin / pq` 三列，任何一次异常都能立刻定位是哪个估计出了问题。

### 4.3 单帧超时（这是"锁 40 也不稳"的隐藏原因）

- 目标：`total` 的 p95 < 预算 − 1 ms；
- 已做的：colour 止损、mutex 超时、copy-ring 超时、tag 判空；
- 待做：把 `p95` 与 `max` 纳入报告，超过预算就打印当时的 `worst(...)` 分解（现在只有 `total>55ms` 才打）。

### 4.4 模型层（3x/4x）

- 3x/4x 复用 MV 是 XeFG 内部行为，我们改不了；
- 但可以**在选择 k 时偏向 2x**：当 `f ≥ 55` 时优先 k=2（即使 e 稍大），
  因为 2x@58 fps 已证明顺；
- 需要一次 A/B：`f=55–60` 区间 k=2（欠供 5–8%）vs k=3（超额 30%+）——预期 k=2 明显更好。

### 4.5 落地清单（按顺序，每步都可单独验证）

| # | 改动 | 验收 |
|---|---|---|
| 1 | 速率：中位数 + 斜率限制 + 阶跃确认 | `pin` 与 `pq` 并排稳定；k 不再因尖峰掉档 |
| 2 | 决策改成 4.1 的三条规则（新 policy `band`） | 整除点 e≤0.5%；非整除点 k 恒定、e 符合规则 |
| 3 | 报告加入 `holes`（无新帧的 vblank）与 `total p95` | 能直接看到"欠供"和"超时" |
| 4 | 2x 偏向（4.4） | 55–60 fps 场景主观更顺 |
| 5 | 动态场景定默认（按实测选 under/over） | 两轮实机一致 |

### 4.6 判断标准（取代 `show`）

| 指标 | 目标 |
|---|---|
| 间距误差（按 `k·V` 预算时 = 0） | ≤1% |
| `holes`（欠供） | ≤3% 的 vblank |
| 输入丢帧（over-supply） | 规则允许的 e 值，且**均匀** |
| `total` p95 | < 预算 − 1 ms |
| 相位 std | < 0.5 ms |
| 主观 | 无"周期性"顿挫 |

### 4.7 不做的事

- 不再调 hold/deadband 去"追平均"（§3.4 已否定）；
- 不再尝试用我们自己的 limiter 消除非整除失真（物理上做不到）；
- 不再为"非整除"加 UI 引导（按用户决定）；
- 不再凭"读数"猜速率：先看 `arr/pin/pq` 三列再动代码。

## 第五部分：把自己做成 VRR —— 能做到什么，不能做到什么

### 5.1 物理限制

VRR 的本质是**面板可以在任意时刻刷新**，于是输出节奏可以完全跟内容。
我们的面板固定在 120 Hz、只在 vblank 采样。所以 "自己当 VRR" **不能**让显示节奏连续变化，
能控制的只有两件事：

1. **下一批从哪个 vblank 开始**（可以跳过 0/1/2 个 vblank）；
2. **哪一帧被丢掉、哪一帧被重复**。

也就是说，我们最多能做到 **"1 个 vblank 粒度（8.33 ms）的 VRR"** —— 这是硬件允许的上限。

### 5.2 但这里有一个被我们忽略的收益

现在的 drop 和 hold 是**随机混合**的：

- 输入来得快 → 颜色队列溢出 → 丢一帧（内容跳）；
- 输入来得慢 → 批次等不到帧 → 留一个洞（间距跳）。

两种伪影**同时**出现、位置随机，眼睛看到的是"不规则的轻微顿挫"。
而按算术，稳态下**只应该有一种**：

```
drops/s = max(0, f − R/k)      // 输入偏快：只该丢帧
holds/s = max(0, R/k − f)      // 输入偏慢：只该留洞
```

两者不会同时非零。**如果我们把"谁被丢、谁被重复"变成我们自己的决定，
伪影就从"随机混合"变成"单一、均匀、可预测"** —— 这是固定面板上最接近 VRR 的效果，
也是我们目前唯一还没拿到的收益。

### 5.3 设计：抖动缓冲 + 相位控制器

```
[捕获线程] → 队列(3 项: colour + 配对 slot + seq + qpc) → [presenter]
                                                        │
       每批开始前：                                     │
         depth > 2  → 丢最旧（drop++），再取最新的做这批   │  ← 输入偏快
         depth == 0 → 重复上一次（hold++），不推进相位     │  ← 输入偏慢
         else       → 正常取一项                          │
```

- 队列深度 3 用来吸收 WGC 的 2/3/4 vblank 量化与停顿后的追赶突发；
- 目标占用 1，滞回 0–2（避免深度在边界上抖）；
- `k` 仍由算术规则（§4.1）决定，缓冲**不改变 k**；
- 两个计数器 `drop/s` 与 `hold/s` 分开报告，用来验证"稳态下只有一种非零"。

### 5.4 预期与边界

| 项目 | 预期 |
|---|---|
| 间距 | 恒 1 vblank（预算 k·V） |
| 内容漂移 | 只剩一种：均匀的 drop（f>R/k）或均匀的 hold（f<R/k） |
| 观感 | 从"不规则轻微顿挫"→"规则的一次内容步进/一个重复帧"，通常明显更不刺眼 |
| 7% 的非整除失真 | **仍然存在**（物理），但不再与"空洞"叠加 |
| 延迟 | +1 帧（队列深度 1 → 2 的平均占用） |

一句话：**VRR 我们做不了，但"把量化误差放在固定、可预测的位置"是能做到的，
而现在的随机混合正是主观顿挫的主要来源。**

### 5.5 实现要点（在现有代码上）

1. 颜色队列目前只存 colour，配对在 pop 之后；需要把**配对结果（slot/seq）一起入队**
   （`--pub-fifo` 下已有 pub 队列，可直接复用其条目）；
2. 丢掉最旧时，要同时归还它的 slot credit（`ack_previous_slot` 已有机制）；
3. `hold` 必须走 reuse 语义：不推进 cadence 相位、不换 sink、不推进 slot；
4. 报告新增 `tq depth / drop / hold`，并把它写进 `rhythm` 行旁边。

## 第六部分：不可能三角的严格形式（并修正第三部分的表述）

### 6.1 三个性质

| 记号 | 性质 | 含义 |
|---|---|---|
| **S** | 间距 | 相邻两张输出严格相距 1 个 vblank（没有重复帧、没有跳 vblank） |
| **D** | 不丢输入 | 每个输入帧都进入输出时间轴（内容速度无突变） |
| **F** | 铺满 | 输出 ≈ R（面板每个 vblank 都有新帧） |

**先注意**：`S ⟹ F`（每 vblank 一张 = 铺满）。所以真正的冲突是 **S vs D**。

### 6.2 证明：f ∤ R 时 S 与 D 不可兼得

- S：每批 k 张必须正好占 k 个 vblank → 每批时长 `k·V`；
- D：每批只消费 1 个输入帧且不丢 → 批次率 = `f`；
- 于是输出率 = `Σk·f`（每秒 f 批、每批 k 张），而 S 要求输出率 = `R`；
- 稳态 `k̄ = R/f`。k 是整数，所以要么 `f | R`（k 恒定），要么 **k 必须变化**；
- 一旦 k 变化，某批的内容时长（= 1 个输入间隔）与显示时长（k·V）就**不再相等** →
  那一批的**内容速度**偏移 `|k·f/R − 1|`。

**所以三角是 (S, D, 速度恒定)，不是 (间距, 丢帧, 空洞)。** 第三部分的表在结论上没错，
但把"丢输入"和"速度突变"混为一谈了 —— 这里修正。

### 6.3 四种组合，我们测过三种

| 组合 | 实现 | 谁被牺牲 | 实测 |
|---|---|---|---|
| S + 速度恒定（丢输入） | `locked`：k 固定、预算 `k·V` | 每 `1/e` 批丢一个输入帧（内容跳） | 43fps：间距 0.4%，3 个内容跳/s |
| S + D（速度随批变化） | **`fill` + `--cad-budget vblank`**：k 变化、预算 `k·V` | 每次 k 变化那批的速度（43fps：±40%） | **从未在干净构建上测过** |
| 速度恒定 + D（间距不齐） | `optimal`：k≈固定、预算 `T` | 间距（每批被压缩 6–8%） | 43fps：间距 8.4% |
| S + D + 速度恒定 | 只有 `f | R` 时存在 | — | 锁 40/60 已完美 |

**关键发现**：第二行是我们一直**以为**在跑的 carry —— 但我们的 `fill` 默认预算是 `T`
（`feedWholeVblanks=false`），所以历史上的 carry 全是"间距不齐 + 速度随批变化"，
把两种伪影叠加了。**真正"完美间距 + 不丢帧"的组合（k 变化 + 预算 k·V）从未被单独验证过。**

### 6.4 预期

43 fps、k 在 3/2 之间按 Bresenham 变化（约 4:1）：

- 间距：**严格 1 vblank**（每批 k 张正好占 k 个 vblank）；
- 不丢帧；
- 速度：每 5 批有 1 批是 1.4×（其余 0.93×），即 **每 ~116 ms 一次 40% 的速度起伏**。

对比 `locked`：每 ~330 ms 一次 1.87× 的突跳。
**更频繁但更小的起伏** vs **更少但更大的突跳** —— 这只能用眼睛判。

### 6.5 与"自己当 VRR"的关系

第五部分的抖动缓冲解决的是**同一件事的另一面**：
在"必须让某一批偏离"的前提下，决定**哪一批**偏离（让偏离落在固定、可预测的位置），
而不是让它由队列溢出随机决定。两者可以叠加：
`fill + k·V`（保证间距）+ 相位控制器（保证偏离规则）。

### 6.6 下一步实验（只差这一格）

| # | 入口 | 配置 |
|---|---|---|
| A | `run_consumer_locked.bat` | k 固定 + k·V（已知：间距 0.4%、丢 7%） |
| B | `run_dynamic_cq3.bat` | k≈固定 + T（已知：间距 8.4%、不丢） |
| **C** | **`run_carry_kvb.bat`（新）** | **k 变化 + k·V（间距应 ≈0、不丢、速度 ±40%）** |

判据：间距误差（应 ≈0）、`qdrop`（应 ≈0）、**主观"起伏感"vs"突跳感"哪个更可接受**。
如果 C 的观感最好，那么动态默认就应该是 "k 由算术决定 + 预算恒为 k·V"，
而不是现在的 `optimal`（预算 T）。

### 6.7 实测结论（2026-11-15 05:19）：**S+D 那一格是空的**

`run_carry_kvb.bat`（`policy=fill` + `budget=k*vblank`）跑出来：

| 指标 | 值 |
|---|---|
| show / min | 118.2 / 109 |
| present/vblanks | 98.5% |
| speed err（rhythm） | 11.1%（k=2 的批次 1.4×） |
| switches | **8.17 / 窗**（每 5 帧一次） |

原因是：k=2 的批次只占 2 个 vblank（16.7 ms），而输入要 23.3 ms 才来下一帧 →
**下一批只能等** → 空洞。也就是说 "k 变化 + k·V" 并没有得到"完美间距 + 不丢帧"，
它退化成 "carry + 空洞"，把两种伪影都占了。

**结论：不可能三角成立**（S / D / F 取二），第六部分假设的第四格不存在。
`fill + k·V` 应当作为反例保留，不要作为默认。

## 第七部分：为什么"标量函数"不够（以及够用的在哪一层）

### 7.1 现有设计的形状

```
f（一个标量） → 规则 → k（一个整数） → 预算（k·V）
```

这是**无记忆、无预测、无内容感知**的开环映射。它解决的是"平均分配"，
而剩下那部分观感问题，恰好不在这个形状能表达的空间里。

### 7.2 被丢掉的三个维度

| 维度 | 我们丢掉的 | 为什么重要 |
|---|---|---|
| **时间结构** | f(t) 被压成 EMA/中位数 | 同样的方差，"随机抖动"与"周期性抖动"观感完全不同；周期性的可以**相位补偿**，随机的只能摊平。输入也可能双峰（16.7/33.3），标量把它平均成一个不存在的值 |
| **内容** | 完全不知道画面在动什么 | 静止/慢摇时丢一帧几乎看不见；快速平移时丢一帧非常刺眼。同一个 7% 误差，落在哪里决定了它是否被看见 |
| **延迟** | 决策在第 N 帧，显示在 N+2..N+3 帧 | 用"当前 f"决定"未来 3 帧的分配"是开环；应该预测 `Σ_{i=N..N+k} T_i` |

### 7.3 因此应该分四层，而不是一个函数

| 层 | 职责 | 手段 | 复杂度 |
|---|---|---|---|
| **L1 速率** | 给出"未来 k 个批次要覆盖多少时间" | 中位数 + 斜率 + 阶跃检测（已有方向） | 低 |
| **L2 分配** | 在窗口 W（8–16 批）内决定每个 k，使 `Σk = 该窗口的 vblank 数` | 窗口内的整数分配（贪心/DP），而不是逐帧取整 | 中 |
| **L3 调度** | 把不可避免的误差（丢帧或空洞）放在**最不显眼**的位置 | 见 7.4 —— 用内容/间隔作代价 | 中 |
| **L4 闭环** | 比较"打算落在哪个 vblank"与"实际落在哪" | DWM vblank + present count（已有） | 低 |

L2 与 L3 是"标量函数"做不到的两件事，也正好是我们现在最缺的两件事。
L1/L4 是纯工程，风险低。

### 7.4 一个立刻可做、零新数据的新杠杆：**按内容跳最小来丢帧**

43 fps 下每秒必须丢 3 帧（算术）。现在丢哪一帧由"队列溢出那一刻"决定 —— **随机**。
但我们可以选：**丢掉"相邻间隔之和最小"的那一帧**，因为

```
丢帧 i 造成的内容跳 = T_{i-1} + T_i      （前后两段被合并成一段）
```

用我们已有的 `frame_qpc_ms`/到达间隔就能算，不需要任何新数据。
更理想的是用 MV 幅度当权重（快速运动时避免丢）、成本是一次小规模归约；
先用间隔做代理就能拿到大部分收益。

**这正是"简单函数"表达不了的**：它不改变 Σk（平均分配不变），只改变误差的落点。

### 7.5 天花板没变

必须承认：`f ∤ R` 时，误差 `e = |k·f/R − 1|` **必须出现在某处**（间距、内容、或空洞）。
上面四层能做的只是：

1. 让 e 的**落点**可预测、规则、落在不显眼处（L2/L3/L4）；
2. 让 e 不被"非算术"因素放大（L1：估计误差；以及单帧超时、3x 模型）。

**所以"能不能用一个简单函数解决问题"的准确回答是：**
- 在整除点（锁 40/60）：能，而且已经做到了；
- 在非整除点：**不能**。不是函数不够聪明，而是它不在正确的抽象层上 ——
  需要的是"窗口分配 + 落点选择 + 闭环"，不是"更好的 f→k 映射"。

## 第八部分：被忽略的层级、想简单的地方、可能想错的地方

### 8.0 元问题：我们把"代理指标"当成了"眼睛看到的真值"

这一轮里被指标骗过的清单：`show`（119 却观感差）、`late`（恒高、无意义）、
`game=`（其实是我们自己的到达）、`pin`（改了三次才对）、`rhythm`（kV 预算下测的是速度不是间距）。
**每一次都让我们朝错误的方向修了一轮。** 这不是巧合，是测量层缺失的必然结果。

### 8.1 L0 测量层（最大盲点）

- 没有**显示端真值**：`GetFrameStatistics` 不支持；DWM 只给合成时钟。
- 所有"间距/相位"都是**推算**，不是观测。我们从未看过面板实际显示了哪一帧。
- 检验（便宜）：同时记录 `IDXGIOutput::WaitForVBlank` 的 QPC 与 DWM `qpcVBlank` 的差；
  若两者差值稳定且≈0，DWM 时钟可用；否则相位校正在错的网格上。
- 终极检验：已知运动的测试图 + 相机/光电 —— 才能定义"客观平滑"。

### 8.2 L1 合成/扫描层（完全没碰）

- overlay 是独立窗口 → **DWM 合成**。我们"vblank-locked 提交"，实际会被合成器**再采样一次**。
- DWM 的 vblank 不等于**扫描输出** vblank；差 1 个 vblank 就足以让所有相位推断偏移。
- 未尝试：MPO/直连翻转（窗口不透明时 DWM 可给独立平面）、`--tearing` 快速路径、
  用 `WaitForVBlank` 直接当提交截止时刻。
- 检验：`--tearing` 跑一次，看 presents/vblanks 与相位行为是否明显不同 —— 不同就证明合成层在改我们的节奏。

### 8.3 L2 XeFG pacer 的内部铺法（关键假设未验证）

- 我们假设 k 帧在 `frameRenderTime` 内**均匀**铺开。
- 头文件里只有一句 `float frameRenderTime;`，**没有任何语义说明**（已确认 `xefg_swapchain.h:169`）。
- 若它按"到下一个真实帧的比例"铺，则 `k·V` 与 `T` 的不一致会直接变成间距误差 ——
  这能解释我们即使 k 恒定、预算 kV 仍看到的残余。
- 检验：固定 k=2，把 renderTime 从 0.8T 扫到 1.2T，画 presents/vblanks 与相位 → 一条曲线反推铺法。

### 8.4 L3 输入被当成"一个速率"

- 输入是**双峰/量化**的（16.7 / 33.3），标量平均出一个现实中不存在的 f。
- pacer 的网格 `g_fgi_next_ms` 是**自我延续**的链，会相对游戏 present 漂移；
  我们从未锁到"游戏自己的 present 相位"（虽然有 `frame_qpc_ms`）。
- 检验：记录 `(我们的提交 QPC − 游戏 frame_qpc) mod T` 的分布：
  窄 → 可以相位锁定（收益大）；宽 → 正在漂。

### 8.5 L4 内容感知（缺失）

- 丢哪一帧、哪一批速度偏移，完全不知道画面在动什么。MV 就在手边（我们已在用它做插值）。

### 8.6 L5 `optimal` 是"用错误信号闭环"的控制器

- 它的反馈量 `PresentedFps = (count+1)/frameMs`，而 `frameMs` 是**我们的捕获间隔**
  （被 pacer 限制到 40/s），不是显示帧率。
- 也就是说：它以为自己在闭环，实际是**拿错误信号做开环**。这是从 OptiScaler 移植继承的
  设计错误（单卡语境下 `frameMs` 接近显示间隔，双卡 + 我们这套 pacer 就不成立了）。

### 8.7 L6 产品层

- 已验证 2x@58 fps 主观"顺"，而 3x/4x 复用 MV 有模型问题。
- 所以"**让游戏跑到 60 用 2x**"可能比"动态 3x"更正确 —— 这不是技术失败，而是产品选择。

### 8.8 一句话

我们一直在**控制层**找答案，但问题分布在
**测量(L0) → 合成(L1) → pacer 语义(L2) → 输入结构(L3) → 内容(L4) → 控制器(L5) → 产品(L6)**。
控制器只是其中一层，而且**不是最可疑的一层**。

### 8.9 便宜的验证顺序（每项都能在一轮内出结论）

| # | 假设 | 检验 | 成本 |
|---|---|---|---|
| 1 | DWM vblank ≠ 扫描 vblank | 同时记录两者 QPC，比差值与稳定性 | 低（10 行日志） |
| 2 | XeFG 均匀铺 renderTime | 固定 k，扫 renderTime 0.8T–1.2T，看 presents/vblanks | 低（参数 + 一次跑） |
| 3 | 可锁到游戏 present 相位 | 记录 `(submit−game_qpc) mod T` 的分布 | 低（10 行日志） |
| 4 | 内容感知有收益 | 同段输入下"最小跳丢帧"vs"随机丢帧" | 中（改丢帧选择） |
| 5 | 合成层在干扰 | `--tearing` 一轮对比 | 低（开关） |
| 6 | optimal 的信号错了 | 打印它的 PresentedFps 与真实 presents/s 的差 | 低（一行日志） |

## 第九部分：还有哪些空白（含实测证据）

### 9.1 输入配对有 10–20% 的缺口（**实测，从未分析**）

解析所有近期日志的 `pf:` 行：

| 日志 | pub/窗 | served | missed | copy-in-flight | **overflow** |
|---|---|---|---|---|---|
| fixed3x_cq2 | 46.1 | 86% | 0.1% | 0.3% | **14.0%** |
| fixed3x_nolock | 42.1 | 88% | 4.0% | 1.5% | **6.1%** |
| fixed4x_cq2 | 43.6 | 91% | 0.1% | 0.0% | **9.3%** |
| locked | 40.5 | 81% | 3.4% | **9.7%** | **5.5%** |
| locked_T | 42.2 | 85% | 3.1% | **5.5%** | **6.4%** |
| locked_lowlat | 49.4 | 80% | 0.1% | 0.1% | **19.9%** |

含义：`overflow` 的 publication 拿不到预拷的 MV/depth，只能
(a) 退回**在帧内现拷** —— `mvs` 落到关键路径上（worst 1.8 ms），直接吃掉 25 ms 预算；
(b) 配对到上一组输入 —— 用**过期 MV** 做重投影，画面会出现"跟不上"的错觉。

**检验**：把 `overflow/in-flight` 与 `total` 的 p95、`HITCH` 做相关性；若强相关，
先修这一层（pub 队列深度 4 → 6 或改为按需拷贝）。

### 9.2 呈现线程没有优先级保护（代码确认）

`main.cpp:374` 只给 **capture 线程** `THREAD_PRIORITY_ABOVE_NORMAL`；
帧循环（25 ms deadline 所在）是 `NORMAL`，也没有 `AvSetMmThreadCharacteristics("Games")`。
在"游戏跑在另一张卡 + 驱动线程很忙"的机器上，0.5–2 ms 的调度延迟就足以让批次错过 vblank。
这是**最便宜、最可能立刻见效**的一项。

### 9.3 `BufferCount = 2`，`--buffers 3` 从未试

FLIP_DISCARD + 2 buffers 意味着合成器可以扣住一张 → 多一帧延迟 + 一帧的抖动余地。
`--buffers 3` 可能是"零成本的一帧松弛"。

### 9.4 我们从未验证"我们是否拖慢了游戏"

链路里存在一条潜在反馈：我们把捕获消费得很慢（pacer 等待），WGC 池被占住，游戏的 present 可能被拖慢；
再加上消费者自己的 GPU 工作（convert + 66 MB 拷贝）与 XeFG 在同一张卡上。
**检验**：同一场景对比——消费者关闭 / 1X / 3x 三种状态下游戏自身的帧率（游戏内计数器或 producer 日志）。

### 9.5 颜色 ↔ MV 的跨适配器偏斜从未分析

颜色走 WGC、MV/depth 走跨卡拷贝，两条路径延迟不同；配对偏斜会随负载漂移。
日志里 `age=`（WGC 年龄）与 `bias=`（配对偏置，恒 0）都有，但从未与观感关联。

### 9.6 VRR 也许并非真的不可用（需复核）

VRR 是**输出链路**的属性：AMD 卡 → 显示器（FreeSync）。
游戏跑在 NVIDIA 上不影响这一点。之前的结论是"不支持 VRR"，但没有区分
"显示器/驱动不支持"与"我们没试过让 overlay 的 swapchain 走 VRR"。
**如果这条路能通，不可能三角直接消失** —— 值得花 5 分钟在 AMD 驱动里确认。

### 9.7 限帧方式从未对比

游戏内限帧 / RTSS / 驱动限帧的**抖动特性**不同。我们的固定基线依赖外部限帧，
但到底是哪一种最稳，从未比较过。

### 9.8 消费者的 GPU 工作全压在 FG 卡上

convert draw + 66 MB 色彩拷贝 + XeFG 全在 AMD。
把 convert 移到 producer 卡（帧本来就在那里）或降低色彩拷贝量（先降采样）都可能降低 FG 卡的抖动。

### 9.9 我们对 XeFG 的自我报告是全盘信任

`xN`、`presents/expected` 都基于 `GetLastPresentStatus().framesPresented`。
若它乐观上报，我们的"填充率"指标就偏乐观。目前只有 `GetLastPresentCount` 可交叉验证（按调用计）。

### 9.10 修订后的验证顺序（按"便宜 × 可能收益"排序）

| # | 项 | 成本 | 预期 |
|---|---|---|---|
| 1 | 呈现线程优先级 + MMCSS | 3 行 | p95 超时减少 → 相位稳定 |
| 2 | `--buffers 3` | 一个开关 | 一帧松弛（+1 帧延迟） |
| 3 | pf overflow 的相关性 | 分析 | 决定是否加深 pub 队列 |
| 4 | 消费者是否拖慢游戏 | 三次运行 | 若拖慢，先解决它（否则一切控制都是徒劳） |
| 5 | VRR 复核 | 5 分钟 | 若可用，整个三角消失 |
| 6 | 限帧方式对比 | 三次运行 | 基线稳定性 |
| 7 | L1 合成层（WaitForVBlank/DWM 对比） | 10 行 | 相位校正是否在正确的网格上 |

## 第十部分：代码层验证 —— 三个结构性设计错误（已核实行号）

### F1. pacer 的"网格"其实是一条链，迟到会被永久编进相位

`modules/frame.cpp:45-69`：

```cpp
if (g_fgi_next_ms > now) { ...等到 g_fgi_next_ms... }
else { ++g_fgi_late; now = qpc_ms(); }
g_fgi_next_ms = now + (double)k * vb;     // ← 用 now 重新起锚
```

一旦迟到 1.7 ms，下一个目标点就整体后移 1.7 ms，**并且永远不会回到面板的网格上**。
这解释了：

- `late` 只增不减（不是"偶尔错过"，而是"网格一路漂"）；
- `vphase mean` 在窗口之间来回游走（§21 里我们看到 0.2 → 6.1 → 3.9 → 7.3）；
- 为什么"锁 40 完美、43 有残余"：整除时 `k·vb == T`，迟到≈0；非整除时每批都有残差，
  每个残差都被累加进相位。

`fg_input_pace_ms()`（`frame.cpp:73-94`）的 `else` 分支同样是 `now + budget_ms`。

**修法（二选一）**

```cpp
// A. 保持相位：迟到只跳过整周期，绝不以 now 重新起锚
double due = g_fgi_next_ms;
if (due > now) { /* wait to due, now = due */ }
else { ++g_fgi_late;
       due += (std::floor((now - due) / vb) + 1.0) * vb; }
g_fgi_next_ms = due + k * vb;

// B. 更彻底：直接对齐到实测 vblank 网格
//    due = g_vb_t0_ms + ceil((now - g_vb_t0_ms) / g_vb_period_ms) * g_vb_period_ms
```

### F2. 真实 vblank 校准只在 `--interp-cadence` 下执行

`cadence.cpp:1033` 的 `vblank_init()` 位于 `cad_core_configure()`，而后者只在
`if (g_interp_cadence) { cad_core_configure(); }`（`cadence.cpp:1769`）里调用。

所以**固定倍率基线（我们用来对照"顺"的那套）根本没有 vblank 测量**，
也没有 `vphase`。最需要诊断的配置恰恰没有诊断。

**修法**：在 `init_fg()` 末尾无条件调用一次 `vblank_init()`（它只阻塞 ~一个刷新周期）。

### F3. 管线深度 1 + 决策用"当前"区间 → 控制回路有 2–3 帧滞后

运行时事实（日志）：

```
FG swap chain: 3840x2160 buffers=2 flags=0x0
SetMaximumFrameLatency(1): hr=0
gpu_throttle(): 等上一帧的 g_frame_fence（深度 1）
```

即：第 N 帧的决策 → 第 N+1 帧的 Present 入队 → 第 N+2 帧上屏。
而决策用的是**第 N−1 帧测到的输入间隔**（`s.inputMs` 来自上一帧）。

**合计滞后 = 2–3 帧 = 50–75 ms（40–43 fps 下）。**
场景阶跃（进战斗、开门、加载）时，k 要晚 2–3 帧才改，这段时间的输出节奏是错的。
这不是 bug，但**没有任何地方对"管线深度"建模**。

**修法**：决策输入用"未来 k 帧窗口的预测 T"（中位数 + 斜率外推），或者把深度改成 2
（`--buffers 3` / `--latency 2`）换松弛 —— 两者都要在仿真里先看代价。

### F4. 附带：所有 bat 都用 `--pool 4`，而代码默认是 2

日志 `mode: ... buffers=2 pool=4 latency=1`。
`--pool` 是 WGC 帧池深度，4 比 2 多最多约两帧的捕获延迟。
"lowlat" 那轮感觉延迟变好，可能主要来自 `--pool 2`，而不是 `--colour-queue 1`。
（代码默认本来就是 2；是我们生成的 bat 覆盖成了 4。）

### F5. `optimal`（默认）根本没有输入 pacer

`frame.cpp:2620` 附近：只有 `g_cad_paced`（optimal 的 paced 分支）或 `policy != 0`
（fill/even）才调用 pacer。默认 optimal 非 paced → **提交完全自由跑进 2 缓冲队列**，
节奏完全由 XeFG 内部决定。这与"我们在控制提交时点"的假设不符。

## 第十一部分：算法层理论核对与修正（2026-11-15 06:0x）

对各算法做了"定义 → 理论行为 → 实现 → 偏差"的核对，发现并修掉 5 处，
另有 1 处量化后留待下一轮。

### A1. 代价函数对"超额供给"是瞎的（已修）

```cpp
double out = std::min(R, fIn * k);          // 43fps, k=3 -> min(120,129)=120
+ _cfg.wFps * (|out - target| / target)     // => 0；7.5% 的丢帧在代价里完全看不见
```

**后果**：`optimal` 认为 "3x@43fps（丢 7.5% 输入帧）" 与 "3x@40fps（恰好 120）" 同价，
所以它在非整除点上永远没有理由倾向"少丢帧"的方案。

**修法**：显式加一项

```cpp
const double over = (rawOut > R) ? (rawOut - R) / R : 0.0;
cost += _cfg.wOver * over;      // wOver 默认 0.5
```

### A2. 代价是线性的，没有"感知死区"（已修）

空洞 3% 与 30% 按同一斜率计价，但实测 **2x@58fps（3.3% 空洞）主观"顺"**，
而 7% 的内容跳"卡"。所以感知阈值以下不该有代价：

```cpp
const double qEff    = max(0.0, q    - kImp);   // kImp = 0.05
const double overEff = max(0.0, over - kImp);
```

### A3. `locked` 的 k 规则用错了目标（已修）

之前用 `round(wantK)`（最小失真）：
35 fps 时 `round(3.43)=3` → **105 Hz**（12.5% 空洞），而 4x 是 120 Hz（14% 丢帧）。
按"空洞 ≤5% 可接受、超过则保速率"的规则，35 fps 应该选 4x。

新规则（显式实现三角取舍）：

```
under = (R - floor(wantK)*f) / R
k = (under <= kImp) ? floor(wantK) : ceil(wantK)
```

仿真对照（table 5c）：

| 输入 | 旧（round） | **新规则** |
|---|---|---|
| 40 fps | 3x, 120 | 3x, 120 |
| 43 fps | 3x, 129（丢 7.5%） | 3x, 129（同） |
| 35 fps | 3x, **105**（12.5% 空洞） | **4x, 120**（14% 丢帧） |
| 58 fps | 2x, 116（3.3% 空洞） | 2x, 116（同，且判为可接受） |

### A4. pacer 的网格以 `now` 重锚（已修，见 F1）

```cpp
// 旧：迟到被永久编进相位
g_fgi_next_ms = now + k * vb;
// 新：网格按期推进，迟到只按整 vblank 跳过
due = g_fgi_next_ms;
if (now > due) { ++g_fgi_late; due += (floor((now-due)/vb) + 1.0) * vb; }
g_fgi_next_ms = due + k * vb;
```
