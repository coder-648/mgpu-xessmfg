## 1. 本轮改了什么

### 1.1 `CodecStreamPercent`（新档位，默认不改变行为）

`lock_frame/producer/producer.cpp`

- 原来 `read_percent()` 里写死：`MvCodec/DepthCodec != 0` ⇒ 流强制 100%。
- 现在改为读 `fakerFG.ini` 的 `CodecStreamPercent`：缺省 / 0 / 100 与旧行为**完全一致**；
  设成 150 就是 `LOSSLESS_TRANSPORT.md` §16.2 的 **B 档**（先降采样再编码）。
- 顺带修掉 B 档跑不起来的真正原因：MV 分支原来是
  `if (mv_codec() != 0 && !scaled_mv && ...)`，一旦发生降采样就掉进裸拷贝分支，
  等于"用了 codec 就不能缩放"。现在缩放后的 `g_ds_tex[1]` 也会走 `fr_encode_dispatch`
  （depth 分支早就是这样，MV 是唯一的例外）。

预期（文档实测值折算）：

| 档位 | 渲染卡 SM/帧 | 消费卡解码（AMD） | MV/depth |
|---|---:|---:|---|
| `CodecStreamPercent=100`（默认） | 2.04 ms | ≈4.0 ms | 比特精确 |
| `CodecStreamPercent=150` | ≈1.52 ms | ≈1.8 ms | 已降采样，非精确 |

### 1.2 Dispatch 合法性判定（潜在 bug 修复）

`producer.cpp`：`dispatch_lane_ok` 原来只判断 `gpu_list != nullptr`。
一个 **COPY-only** 的标题 command list（部分 UE5 tag 车道）会因此把
`Dispatch` 记到 COPY 队列上 —— 文档里 PBZ 的 `INVALID_CALL` 设备移除就是这个形状。
现在这个谓词同时要求 list 类型是 `DIRECT`/`COMPUTE`，encode / synth / scale /
hudless 转换四处共用它。

### 1.3 marker 探测：每帧 syscall → 1 s 缓存

`lock_frame/faker_fg/backend_xefg.cpp`

- `consumer_present_event()`：原来每个 Present 都 `OpenEventW + CloseHandle`。
  现在**命中后缓存 1 s**；未命中仍然每帧重试（否则消费者刚启动会有 ~40 帧无 marker）。
- `marker_disable.on` 的 `GetFileAttributesW`（走文件系统 + 杀软过滤）：改为 1 s 一次。
- 这两处在**游戏的 present 线程**上，40–120 次/秒。

### 1.4 计时修正（这一步是为了后面能测）

| 位置 | 问题 | 现在 |
|---|---|---|
| `modules/160_main.inc` `capture=` | `GetTickCount64` 15.6 ms 量化，读数只能是 0/16/31 | `qpc_ms()` |
| `modules/140_frame.inc` `g_frame_ms_ema` | 同上，喂给步进统计与首窗口 `show=` | `qpc_ms()` |
| `modules/060_frame_io.inc` `g_last_frame_tick` 类型 | `ULONGLONG` tick | `double` ms（QPC） |

`PERF_BASELINE.md` §3.1 修过 `work/gpu/present/colour`，漏了这三个。
`capture=` 恰好是消费端最大的一块"看不见的时间"，它被量化等于这块时间一直没被量到。

### 1.5 每帧一次 64 元素排序 → 每报告窗口一次

`--fg-rt-mode auto` 用的 `g_rt_ema_slow` 只在报告窗口里被读，却每帧算一次
64 样本中位数（`arr_slow_median_ms`，插入排序）。现在改到报告块里算。

### 1.6 sparse unblend：空 tile 不再采样 UI / 跑 PQ 数学

`lock_frame/shaders/ui_occ.hlsl`（新）、`shaders/unblend_ui.hlsl`、`modules/085_ui_unblend.inc`

消费端的 unblend 是 `Dispatch((w+7)/8, (h+7)/8)`（4K = 129,600 组），每像素读 present +
双线性采样 UI，`Linear=1` 时还要跑两次 PQ（各 6 个 `pow`）。而稀疏 UI codec 早就把
"空 32×8 tile" 标成 `mode=3`，解码时把这些 tile 写成 0 —— 也就是说这些像素的
`ui.a == 0`，unblend 的结果恒等于 `present`。

现在按 tile 头派生一张占用表（`ui_occ`，4K 下 129.6 KB/帧，**不走链路、协议仍是 v30**），
unblend 对空 tile 直接写 `present`：

| 项 | 改前 | 改后 |
|---|---|---|
| 空 tile 的像素 | 读 P + 采样 UI + 2×PQ `pow` + 除法 + 写 H | 读 P + 写 H |
| 占用表派生 | — | 507 组 × 64 线程、每 tile 读 4 B（≈0.01 ms） |
| 协议 | v30 | v30（无新字段） |

安全性：
- `mode=3` 的解码分支写的是**全 0**（`fr_codec.hlsl:350-356`），所以 `ui.a == 0` 是精确的；
- 走捷径写的 `present.rgb` 比原路径更准（原路径要经过 `pq_decode`→`pq_encode` 往返）；
- 只在 **全分辨率 UI + codec 流 + 源不是 Hudless** 时启用（8×8 组必须与 UI texel 一一对应，
  半分辨率双线性会把邻域像素拉进"空" tile）；条件不满足自动退回旧 PSO；
- 老 producer / `UiSparseCodec=0` 永远不写 `mode=3` → 占用表全 1 → 行为与改前一致（只多一次
  0.01 ms 的小 pass）。

观测：日志新增一次 `ui-unblend: sparse dispatch ON (N tiles …)`；收益看消费端 `load`/`gpu`。
空 tile 的实际占比没有实测（取决于 HUD 布局），不要按 93% 估。

## 1.7 UI 本地纹理按 UI 槽位建（VRAM：1.06 GB → 265 MB）

`modules/060_frame_io.inc`（新 `ui_slot_index()`）、`085_ui_unblend.inc`、`140_frame.inc`

`g_ui_local[]` 原来按 **MV/depth 的 32 个 publication slot** 建：4K 全分辨率 R10 每张 33 MB
⇒ **1.06 GB**。而 producer 的 UI 环只有 `UiSlots`（默认 8，单槽 ~34 MB），
`decode_ui_slot()` 也一直是按 `slot % UiSlots` 读共享槽。

现在本地解码目标同样按 UI 槽位索引：`ui_slot_index(slot) = slot % (UiSlots ?: kMaxSlots)`。

- 4K 全分辨率：**32×33 MB → 8×33 MB（省 ~0.8 GB）**；1080p 按比例。
- `g_ui_fresh[]` 同步改成按 UI 槽位记，`copy_inputs_local` 顶部算一次、UI 段与 `085`/`140` 共用。
- 老 producer（`slots == 32`）时 `slot % 32 == slot`，等价于改前。
- 安全性：解码 → unblend → tag 都在同一帧、同一条 command list 里；`gpu_throttle()` 把队列深度
  限制在 1，所以两个映射到同一 UI 槽的 MV slot 不可能同时在飞行中（要 8 帧前瞻才撞上）。
- 没动的一处：`g_hudless_local[]`（stream 4，`HudlessStream=0` 默认关闭）还是 32 张；要用时
  同样可以按 `g_hudless_slots` 收缩。

## 1.8 depth 走 fp16 精度 + 常量 tile 早退（2026-11-23）

`shaders/fr_codec.hlsl`（`-D DEPTH32 -D DEPTH_FP16`）、`build.sh`、`producer.cpp`、`fakerFG.ini`

### 1.8.1 量化放在 codec 的读入端，不需要额外的转换 pass

`ldPix()` 的 DEPTH_FP16 变体把值过一遍 `f32tof16 → f16tof32` 再当成码字，所以链路里传的是
**16 位精度**的 depth，而 producer 不用多跑一个 33 MB 的转换 pass（原方案要）。
解码器**不改**：它写回的就是被编码的那些字，本来就是 f16 取整后的 float，回环仍然 bit-exact。

实测（真实 4K CP2077 depth，`f00_depth.raw`，reversed-Z、p50=0.0030）：

| | coded | ratio | max 相对距离误差 | mean |
|---|---:|---:|---:|---:|
| `DepthFp16=0`（今天） | 13.61 MB | 2.44x | – | – |
| `DepthFp16=1` | **8.95 MB** | **3.71x** | 0.089% | 0.017% |

reversed-Z 下 `d ∝ 1/z`，所以上面的相对 z 误差就是**相对距离误差**；对只做 disocclusion 的
XeFG 可以忽略。MV+depth 因此从 25.3 → 20.6 MB/帧。

### 1.8.2 常量 tile 早退（字节完全不变）

量化后 **70% 的 tile 残差全 0**（fp32 时只有 1.0%）。这种 tile 的编码结果本来就是
`header(w=0,mode=0) + 绝对像素`，所以编码器可以在**扫描之前**直接写这 8 个字节并返回：

- 跳过 mask 写入 + 8 步前缀扫描（8 次 barrier）+ pack + 大部分 flush；
- **字节与通用路径逐字节相同**，解码器不需要知道这件事，协议不变；
- 离线证明：`tests/lossless_bench/fr_codec.h` 加了同样的早退路径，`fr_codec_test` 在同一批
  dump 上**尺寸一字未变**（13.61 / 11.17 / 15.64 / 8.95 MB）且仍然 bit-exact。

预期 depth 编码从 1.02 ms 降到 ~0.4–0.6 ms（70% 的 tile 直接返回）——这条由真机 `prof:`
验证，不在离线结论里。

### 1.8.3 测量便利：两个开关 + 一个定时器

- `FrCodecAblate` / `DepthFp16` / `ProfGpu` 现在**每秒重读一次** ini（`prof_reload_ini()`），
  一次游戏启动就能跑完整个消融矩阵。影响槽布局的键（`CodecStreamPercent`、`UiStream`、
  codec 开关）仍然需要重启。
- 消费端新增 `--run-sec N`：跑满 N 秒自动退出，每段 30 秒可复现。
- 消费端新增 `--no-sparse-unblend`：不碰 producer 的 ini 就能 A/B 掉 sparse unblend。
- `prof:` 行加了 `t=<ms>`（producer 日志跨会话追加，靠它切分段落）。

## 2. 为什么本轮**没有**动 codec 编码器（上一轮列为 A1）

上一轮的假设是"每 group 一个 tile，group 数太多 → 每 group 2–4 个 tile 能省 30%"。
按代码重新算了一遍，这个假设不成立：

- 一个 tile 的编码块里有 **约 13 次 `GroupMemoryBarrierWithGroupSync`**
  （直方图合并 / mode 决策 / mask / 8 步 Hillis-Steele 扫描 / flush 各一次）。
  把 2 个 tile 塞进一个 group，**每个 tile 仍然要做完自己那 13 次**，只省了 group
  的 launch/teardown。4K 下 32,400 个 group、每个 256 线程，launch 占比很小。
- 真正能砍掉的是**扫描的 8 次 barrier**（分层扫描 + `WavePrefixSum`），那需要
  `cs_6_0`，即 DXC（`dxcompiler`），而构建链现在是 `fxc` + `cs_5_0`；
  或者把 tile 的编码改成不依赖前缀和的形状（等于换位流，风险大得多）。
- 文档 §16.4 的"1.02 → 0.35 ms"是待 profiler 验证的**目标**，不是已测结论；
  按上面的 barrier 算术，`cs_5_0` 下的现实下界在 0.5–0.6 ms 附近。

结论：这条要单独开一轮，前置条件是 ① 真机 profiler 确认 barrier vs 原子占比，
② 决定是否引入 DXC/`cs_6_0`。**不要**在没有 GPU 验证的情况下改位移流。

## 3. 怎么验（一次只改一项，A→B→A）

`CodecStreamPercent` 只影响 producer，改完**必须重启游戏**（槽尺寸在 layout 时定死）。

| 步骤 | 配置 | 看什么 |
|---|---|---|
| A1 | `CodecStreamPercent=100`（默认） | `fr: coded mv/depth`（应 ≈33MB 原始 → 26–29MB）、消费端 `load`、`bus:` |
| B | `CodecStreamPercent=150` | `fr: coded` 是否变小；`bus:` 是否从 28.1 → ≈12 MB/帧；消费端 `load` 是否下降；`show`/`presents` 是否仍 120/120 |
| A2 | 回到 100 | 与 A1 的漂移量（本机 A/B 噪声 2–10 ms，见 `PERF_BASELINE.md` §3.6） |

VRAM（§1.7）：`UiStream=1` + 4K 跑一局，看显存占用应从 ~1.06 GB（32 张全分辨率 UI）
降到 ~265 MB（8 张）；`ui-unblend` 日志、`pair: exact`、画面都不应变化。

**`CodecStreamPercent` 的期望字节（2026-11-23 用真实数据集离线测出，
`tests/lossless_bench/README.md`）**：

```text
                 MV                     depth
CodecStreamPercent=100   fr: coded  9.5–15.6 MB   11.5–13.6 MB     （MV+depth 24.8–28.0 MB）
CodecStreamPercent=150   fr: coded  5.8–7.6  MB   6.0–6.6   MB     （MV+depth 12.4–13.6 MB）
```

真机 `fr: coded mv/depth` 落在上表区间内即算通过；明显偏大说明 150% 的重采样方式与
离线近似不同（离线用 3×3 中值，shader 用 medoid 取样），不是 bug。

判据：`presents=x/x`、`xN=3.00`、`HITCH=0`、`pair: exact`、`xNmiss=0` 不退化。
画质 A/B：B 档的 MV 已经不是比特精确（降采样后再无损），看边缘/遮挡有没有可见变化；
如果有，就留在 100，或者只给 depth 用 150（`DepthCodec` 与 `MvCodec` 是独立档）。

marker 缓存的验证：`marker_disable.on` 放/不放各跑一次，确认仍生效（1 s 内切换）；
消费者后启动的场景（先开游戏再开 consumer），确认 `pair: exact` 在 ~1 s 内恢复。

## 5. 编码器成本的实测方法（`ProfGpu` + `FrCodecAblate`，2026-11-23 追加）

要决定"改分组 / 上 DXC"之前，先把 1.02 ms 拆开。之前的判据只有 RTSS/D3D 占用百分比
（整点量化、±1 pp），拿它去判一个 0.2 ms 的改动没有意义。

### 5.1 `ProfGpu=1`：我们自己的 dispatch 的 GPU 时间戳

`producer.cpp`（`prof_begin` / `prof_end` / `prof_frame_end` / `prof_log_tick`）

- 在 `fr_encode_dispatch()` 与 `synth_ui_dispatch()` 的 `Dispatch` 两侧各插一个
  `EndQuery(TIMESTAMP)`；每帧结束前 `ResolveQueryData` 到一张 DEFAULT 缓冲，再
  `CopyBufferRegion` 到回读缓冲；CPU 侧每秒 Map 一次（与 `fr_bytes_tick` 同一套 1 Hz 模式）。
- 输出一行/秒：

  ```text
  prof: GPU passes mv 1.04 depth 0.98 ui 0.36 synth 0.41 = 2.79 ms/frame (last resolved frame)
  ```

- 关闭时开销 = 一次 ini 读 + 每个 pass 一次判空；打开时每帧 +1 次 resolve、每秒 +64 B 回读。
- 时间戳计数器是**适配器全局**的，所以 pass 记在标题的 list 上、在发布队列上 resolve 也成立；
  但 **Evaluate / Present 两条车道交替的标题**可能把两帧的采样混在一起，按同一条车道跑最干净。

### 5.2 `FrCodecAblate=1|2|3`：同一内核去掉一个阶段

`build.sh` 多编译三个变体（`-D ABLATE_SCAN / ABLATE_ATOMICS / ABLATE_LOADS`），
`ensure_fr_objects()` 建三个额外 PSO，`fr_encode_dispatch()` 只在 **MV 流**、且该键非 0 时选它。
生产 PSO 的字节不受影响（同一份源码 + `#ifdef`，不定义时不进那段）。

| 档 | 去掉什么 | 回答的问题 |
|---|---|---|
| 1 | 8 步 Hillis-Steele 前缀扫描（+ 它那 8 次 barrier） | barrier 占多少？——这是要不要上 DXC/`cs_6_0`（`WavePrefixSum`）的唯一依据 |
| 2 | 每值的 LDS `InterlockedOr` | 原子占多少？（§16.4 的 0.17 ms 估计是否成立） |
| 3 | 像素读取（`ldPix` 换常量） | 访存占多少？ |

其余结构刻意保持：直方图 / 模式决策 / 扫描 / flush 的形状都在；档 1 下 `TileLen` 用一个近似值，
保证 flush 的写入量与生产一致（否则"去掉扫描顺带省了 flush"会污染归因）。

### 5.3 跑法（4 次 × 30 秒，同场景、锁 40、4K）

```text
A  ProfGpu=1 FrCodecAblate=0   -> prof: mv 1.0x   （生产基线）
B  ProfGpu=1 FrCodecAblate=1   -> 扫描的贡献 = A.mv - B.mv
C  ProfGpu=1 FrCodecAblate=2   -> 原子的贡献 = A.mv - C.mv
D  ProfGpu=1 FrCodecAblate=3   -> 访存的贡献 = A.mv - D.mv
```

判定：
- **B 只降 0.1–0.2 ms** ⇒ 上 DXC 换 warp 扫描不值（收益小、构建链要换）；
- **B 降 ≥0.4 ms** ⇒ 值得单独开一轮 DXC；
- **C 降 ≈0.17 ms** ⇒ 文档估计成立，用 LDS 归并 + leader 单写替代按值原子（`cs_5_0` 内可做）；
- **D 降很多** ⇒ 瓶颈在访存，改分组 / shared-memory staging，而不是改扫描。

**跑之前可以预期的（2026-11-23 用 `E:\mgpu_dataset` 离线测出）**：
`tests/lossless_bench/tile_stats.cpp` 在 49 帧 4K MV+depth 上给出
`plain 16% / exception 84% / raw escape 0%`，且 46% 的 tile 位宽 ≤ 4 bit。
也就是说：① `mode == 2` 的早退分支在真实数据上不触发，**每个 tile 都付满 13 次 barrier**，
所以 B 组测到的就是完整的扫描成本（不会被跳过的 tile 稀释）；② 打包算术量很小，
若 B（扫描）明显而 C（原子）/D（访存）很小，那就是纯同步开销，唯一的大杠杆是 DXC。
注意这批数据是**静态镜头**（`|mv| < 0.1 px`），高运动场景的位宽分布可能更宽，
但 mode 2 需要 32 bit 的残差，理论上仍不会触发。

**警告**：消融档写出的字节不可解码，画面与插值都会坏。只在短跑里用，跑完必须
`FrCodecAblate=0` 并重启游戏（producer 每会话只读一次）。

## 7. 第一组真机数字（2026-11-23 07:51，CP2077 4K、3x@40）

部署后的一次 30 秒基线（`pair: exact=40`、`presents=120/120`、`xN=3.00`）：

```text
prof:  mv 0.24–0.60   depth 1.66–2.63   ui 0.37–0.87   synth 0.20   = 3.3–3.5 ms/frame
fr: coded   mv 5.4–5.8 MB (5.4x)   depth 10.7 MB (2.95x)   ui 1.53 MB (20.6x)
```

三条**改变优先级**的结论：

1. **贵的不是 MV，是 depth**：同一个内核，depth 1.7–2.6 ms 而 mv 只有 0.24–0.60 ms。
   差 3–4 倍的原因在位宽分布（MV 1–3 bit，depth 7–16 bit → LDS 原子/移位/写入量都更大）。
   所以 §1.8 的 **DepthFp16 + 常量 tile 早退正对着最贵的那条流**，先做它比改共享内核划算。
2. **"1.02 ms/流"只能当量级**：真机上 MV 0.5 / depth 2.0，取决于内容。做预算要用 `prof:` 的
   实测值，不要用 §16.1 的单流均值。
3. 消费端在 3x@40 下 `load=9–10%`、`total=2.4–2.6 ms`：余量非常大，所以**任何消费端优化
   （sparse unblend、解码、VRAM）都不会体现在帧率上**；只有渲染卡的时间会。

### 7.1 六段消融/对比的结果（2026-11-23 08:0x，同一个游戏会话）

| 段 | mv p50 | depth p50 | coded mv | coded depth | 说明 |
|---|---:|---:|---:|---:|---|
| `base` | **0.79** | 2.12 | 6.02 MB | 11.03 MB | 生产内核 |
| `ablate1`（去扫描） | **2.04** | 2.67 | 9.93 MB | 11.03 | **测不出来，见下** |
| `ablate2`（去原子） | 0.72 | 2.62 | 6.22 | 10.88 | −0.07 ms，**在噪声内** |
| `ablate3`（去读像素） | **0.31** | 2.58 | 0.25 | 11.05 | 结构不同，可信 |
| `fp16`（DepthFp16=1） | 0.61 | 2.41 | 5.63 | **7.34** | 字节 −33%，**时间无变化** |
| `unblend_off` | 0.75 | 2.22 | 6.08 | 7.34 | 消费端 unblend 没跑起来，作废 |

**必须先说的噪声**：`depth` 在*同一段* 30 秒里 p10–p90 = **1.41–4.03 ms**（代码完全没变），
因为编码时间随内容（位宽分布）变化。所以 `base/ablate1/2/3` 的 depth 2.12/2.67/2.62/2.58
**全是噪声**，段间差异 <0.5 ms 一律不可信。下次要做 A/B 必须**交替**（A-B-A-B 各 10 s）
或用 p10/median 之外的更稳统计。

结论：

1. **`ablate1` 是无效测量，不是"扫描很贵"**。去掉扫描后每个值都落在同一个 bit offset，
   255 个线程用 `InterlockedOr` 抢同两个 LDS 字 → 原子串行化；字节也从 6.02 涨到 9.93。
   它测到的是"原子争用"，不能用来说明扫描成本。（这是我消融设计里的缺陷，记下来。）
2. **`ablate3` 干净可用**：所有 tile 都退化成常量 tile（早退命中 100%），mv 0.79 → **0.31 ms**。
   也就是说 MV 编码里 **~0.48 ms（60%）是 mask+扫描+打包+flush**，剩下 0.31 ms 是
   读像素 + 直方图 + 决策 + 早退写出。
3. **按值原子的成本 < 噪声**（≤0.07 ms），和文档 §16.4 的 0.17 ms 估计同量级但更小。
4. **`DepthFp16` 只省字节、不省时间**：11.03 → 7.34 MB（−33%，与离线 −34% 吻合），
   depth 的 ms 无变化（2.41 vs 2.12，噪声内）。原因推测：量化把"中等位宽"变成
   "70% 零位宽 + 30% 更宽位宽"，早退省下的时间被剩下的宽 tile 吃回去。

### 7.2 决策（2026-11-23，用户口径：画质优先）

- `CodecStreamPercent` **保持 100**（MV 必须比特精确）。`CodecStreamPercent=150` 不再测。
- `DepthFp16` **保持 0**：它是**有损**（相对距离误差 mean 0.017% / max 0.089%），
  而它只省链路字节（总线只用了 ~1 GB/s / 13 GB/s，不是瓶颈），时间上无收益 ⇒ 不值得。
- 代码保留（默认关闭），`MvCodecPercent` / `DepthCodecPercent` 让"MV 精确 + depth 缩放"
  成为可能——**这是下一个值得测的档**：depth 是 2.1 ms 的贵项，而深度分辨率按
  `FINAL_CONFIG` §2.1.2 是不敏感的，`depth 150%` 能把它的 tile 数砍到 ~44%。


另外：这次运行**没有** `--ui-source auto`，消费端的 UI 组合是关的（`unblend=0`），
`run_perf.bat` 已经补上这个开关（消费端 UI 组合的默认值是关）。



### 7.3 第二轮：`DepthCodecPercent=150`（MV 保持 100% 精确）

`base2` / `unblend2` / `d150` 三段，同样 30 秒、同样的 4K/3x@40：

| 段 | mv | depth | ui | synth | 渲染卡合计 | coded mv | coded depth | depth 槽 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `base2`（全 100%） | 0.67 | **2.05** | 0.64 | 0.20 | 3.56 | 5.96 | **10.82** | 31.6 MB |
| `unblend2`（同上，sparse 关） | 0.60 | 2.60 | 0.47 | 0.20 | 3.87 | 6.02 | 11.01 | 31.6 MB |
| **`d150`（depth 150%）** | 1.29 | **0.79** | 0.61 | 0.20 | **2.89** | 6.07 | **5.56** | **14.1 MB** |

- **depth 编码 2.05 → 0.79 ms（−61%）**，coded bytes 10.82 → **5.56 MB（−49%）**，
  槽容量 31.6 → 14.1 MB（tile 数 32,400 → 14,400）。
- 深度编码几乎**线性于 tile 数**：≈65 ns/tile（14,400 × 65 ns ≈ 0.94 ms 预测 vs 0.79 实测）。
- **MV 完全没动**（仍 100% 比特精确；coded 5.96 → 6.07 MB 是同场景噪声）。
- 消费端：`load` 11% → 12%（多了一次 joint MV/depth 重建），`total` 2.10 ms 不变，
  `HITCH=0`、`presents` 正常、`pair 961/962`；日志确认
  `transport plan: mv=codec 3840x2160, depth=codec 2560x1440, upsample runs (depth)`。
- `d150` 那一段 mv 读到 1.29 ms（p90 2.22），但同段 coded mv 只涨了 2% ⇒ 不是内容变复杂，
  而是**换了会话**（换档必须重启游戏）叠加 depth 降采样 pass 挤掉缓存。做预算时用低的那档。

**结论**：`DepthCodecPercent=150` 是这一批里唯一值得开的东西 —— 不碰 MV 画质的前提下，
拿掉 **1.26 ms 渲染卡时间 + 5.3 MB/帧链路**。剩下的唯一风险是"重采样后的 depth 在遮挡边缘"
的主观画质，需要人眼确认（`FINAL_CONFIG` §2.1.2：深度分辨率不敏感，480×270 都够用）。
