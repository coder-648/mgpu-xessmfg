# 定案：MV/深度降采样与升采样（2026-11-13）

> 本文把 `TIMING_4K40.md`、`DECOUPLED_IDEAL.md`、`STREAM_AUTOSCALE.md`、`UPSAMPLE_QUALITY.md`
> 收敛成一个决定，并记录**已经落地了什么、还差什么、开关怎么留/怎么删**。
>
> 一句话：**降采样滤波器无条件改进；升采样做成一个 UI/CLI 开关（默认关），在实测后决定去留。**

## 0. 硬约束（先写在最前面）

`XESS_FG_NOTES.md` / `XESS_MFG_PRODUCER.md` 都有实测：**XeFG 要求 MV 与 depth 同尺寸**，
尺寸不等会 `ERR_INVALID_ARGUMENT` / `MISMATCH_INPUT_RESOURCES`。

由此得到两条不可绕过的推论：

1. **升采样只能是“成对”的**：要么两条都按流尺寸交给 XeFG，要么两条都重建到同一个目标尺寸。
   不能只升 MV、不升 depth。
2. **非对称降采样（MV 100 / depth 200）不能直接喂**：depth 必须先升到 MV 的尺寸。
   这条方案（`UPSAMPLE_QUALITY.md` 方案 C）**本轮不做**，作为后续独立模式；
   它的价值仍然在（深度分辨率不敏感、MV 敏感），但不能靠“再加一个开关”解决，
   必须作为 `StreamPercent` 的按流拆分配置，等自动档位一起做。

## 2. 开关语义（StreamPercent × Upsample）

| StreamPercent | Upsample | 跨卡传输 | 副卡 tag 的尺寸 | 额外成本 |
|---|---|---|---|---|
| 100 | 关 | 63.3 MB | 渲染尺寸（无变化） | 0 |
| 100 | 开 | 63.3 MB | 渲染尺寸（pass 是空转，**自动跳过**） | 0（`tw <= mw` 直接 return） |
| 150 | 关 | 28.1 MB | 流尺寸（≈2/3） | 0 |
| **150** | **开** | **28.1 MB** | **渲染尺寸** | 一次联合 pass ≈0.3–0.5 ms（4K） |
| 200 | 开 | 15.8 MB | 渲染尺寸 | 同上（低分辨率输入，权重更粗） |
| 400 | 开 | 4.0 MB | 渲染尺寸 | 同上；边界误差明显，只用于极限带宽 |

升采样的 pass 只在**真实输入帧**上录：`--no-depth`、`--fg-of`、`--no-inputs`、
`--depth-lag > 0`、`kRequestRawMv` 时直接跳过，回落到“按流尺寸 tag”（不报错、不改变语义）。
`g_reuse_frame`（重复呈递）不重跑 pass，但继续 tag 上一次的重建结果。

**非对称 / 自动档位（v15）**：

| 开关 | 请求（MV / depth） | 说明 |
|---|---|---|
| 全关 | 0 / 0 | 生产端按 `fakerFG.ini` 的 `StreamPercent`（或 `StreamPercentMv/Depth`）跑 |
| `--stream-asym` | **100** / 0 | MV 1:1、depth 按 ini；隐含 `--upsample`，depth 被重建到 MV 尺寸 |
| `--stream-auto` | 控制器值 / 控制器值 | 每统计窗口按 `age` p10 + 拷贝模型选档 |
| 两个都开 | **100** / 控制器值 | MV 无损，自动只调 depth（本仓库推荐组合） |

控制器参数（`bridge.cpp` `stream_controller_tick()`）：阶梯 `{100,125,150,175,200,250,300,400}`、
`age` 取最近 64 帧的 p10、余量 1.5 ms、拷贝模型 `bytes/13 GB/s + bytes/17.6 GB/s`、
带宽上限 5.5 GB/s、下降 2 窗确认 / 上升 4 窗确认 / 最小驻留 2 s。
**生产端容量按渲染尺寸预留**（4K ≈ 280 MB，`cap_dim` 把高度对齐到 2304），否则档位只能降不能升。

## 4. 实测计划（决定开关去留）

### 4.1 两组 A/B（不要混在一起）

| 组 | A | B | 目的 |
|---|---|---|---|
| **A（生产端滤波器）** | 旧 `xess_mfg_producer.dll` | 新 DLL | D1 是否真的把边界 EPE 降下来；**只有这一组能单独验证 medoid/median** |
| **B（消费端升采样）** | 新 DLL + `--upsample` 关 | 新 DLL + `--upsample` 开 | 开关本身值不值；两组用同一个 producer，避免混淆 |
| **C（自动档位）** | 固定 `StreamPercent` | `--stream-auto` | 自动是否在同画质下减少 `skip`/`slow`；看 `autoscale:` 日志的档位与切换次数 |
| **D（非对称流）** | `--upsample`（同档） | `--stream-asym`（MV 100 / depth 档） | 用 41 MB 换全分辨率 MV 是否值；必须 `starts` 相同 producer |

每一组：4K/40（3x）、1440p/40（3x）、4K/30（4x）、4K/60（2x），各 ≥60 s，A→B→A 三轮。
组 C/D 还要额外记录 `active_percent_mv/depth` 回显（生产端日志 `content is now …`）。

### 4.2 指标与判据

| 指标 | 采集方式 | 通过条件 |
|---|---|---|
| 边界 EPE | `--dump` + 真值全分辨率 MV（临时导出） | p95 下降 ≥30%（组 A） |
| 画质 | 快速平移段的移动边缘（拖影/串色） | 不出现新的边界鬼影 |
| `gpu` | `--report 40` | 升采样开启后增量 ≤0.3 ms（4K/40 的余量只有 0.3 ms） |
| `skip` / `slow` | 同上 | 不比关闭时差 |
| `load` | 同上 | 不超过 100% |
| `compose->photons` | `scripts/latstats.py` | 增量 ≤0.5 ms |

### 4.3 去留规则（写死，避免“再测一次看看”）

**保留开关** 当且仅当：
- 组 A 的边界 EPE p95 下降 ≥30%，**且**没有肉眼可见的新伪影；
- 组 B 在至少 2 个分辨率/帧率组合里 `skip` 或 `slow` 有改善，或 EPE 再降 ≥15%；
- 组 B 的 `gpu` 增量 ≤0.3 ms。

**移除开关**（代码和 UI 一起删）当且仅当：
- 组 B 在所有组合里 `gpu` 增量 >0.5 ms，或 `skip`/`slow` 反而变差；
- 或组 A 已经足够（B 没有可测收益）。

**只保留默认关**：介于两者之间时，开关留在 UI 的 A/B 区，不进默认配置。

## 5. 已知风险（实测时重点看）

| 风险 | 现象 | 处理 |
|---|---|---|
| medoid 逐帧跳变 | 运动边界闪烁 | 记录；必要时给边界块加时域保持 |
| depth 中位数丢细前景 | 栏杆/头发变薄（或变厚，视中位数落点） | 记录；可切 3×3 min/max（需 Z 约定） |
| 低分辨率引导的极限 | 边界误差只能到 1–2 px 带 | 方案 C 已落地为 `--stream-asym`（MV 全分辨率） |
| 升采样与 XeFG 抢算力 | `gpu` 增量超预算 | 降 `StreamPercent` 或关开关；后续把 pass 挪到 COMPUTE 队列/WGC 等待里 |
| 第一版关掉了 copy-queue/prefetch | `--input-copy-queue`/`--prefetch-inputs` 在开启时无效 | 启动日志已说明；第二版把 pass 移到 COMPUTE 队列后恢复 |

## 6. 下一步顺序

1. **真机跑组 A**（只换 producer DLL），先确认 medoid/median 不引入新伪影；
2. **真机跑组 B**（`--upsample` 开/关），按 §4.3 决定开关去留；
3. **真机跑组 C/D**（`--stream-auto`、`--stream-asym`），确认协议 v15 的回显与档位切换；
4. 若升采样保留：把 pass 移到 COMPUTE 队列（与 `--prefetch-inputs` 同一时机），恢复解耦；
5. 最后再做生产端 COPY 队列（`DECOUPLED_IDEAL.md` §4.1），那时 `T_P + T_C` 的预算会再收紧一次。

|---|---|---|---|---|---|---|---|---|
| A（150，无升采样） | 28.1 MB | 25.35 | 3.3 | 30.25 | 114% | 8 | 40 | 基线；4K/40 本身已超预算 |
| B（+upsample） | 28.1 MB | 25.80 | 3.1 | 29.95 | 115% | 8 | 40 | **pass 未运行**（日志无 `reconstruction targets`）→ B 数据无效 |
| C（auto） | 中位 3.9 MB | 20.7 | 3.8 | 24.8 | 97% | 1 | 1 | 控制器 100↔400 振荡（p10 被重复帧污染 + 选档取了最后一档） |
| D（asym） | 63.3 MB | 27.85 | 5.0 | 37.05 | 117% | 16 | 40 | depth 没回到 ini 的 150（请求 0 被当成“保持上一次的 100”） |

已修：

1. 生产端：请求 0 → 回退 `fakerFG.ini`（D 的根因）；并发布 `frame_time_ms`（record 间隔 EMA）。
2. 控制器：年龄改**中位数**；选**第一个满足**的档（最低 percent）；全不满足回退 400；
   生产端用增量头寸 `T_in − (frame_ms − T_P(now))`，避免自激振荡。
3. 升采样 pass 加一次性诊断 `--upsample: check ...`，下一次运行会直接打印是哪个前置条件挡住的。

待复测（需要重启游戏以加载新 producer）：**B、C、D**；A 不需要，但可作为复测时的基线。
B 重点看 `--upsample: check` 与 `reconstruction targets`；C 看是否稳定在一个档位；
D 看生产端是否打印 `content is now mv 3840x2160 (100%), depth 2560x1440 (150%)`。

### 7.1 第二轮（B/C/D）与 drop 归因

| 组 | bus | gpu | present | total | load | skip | xN | 输出空 vblank/40 帧 | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| A（基线） | 28.1 | 25.35 | 3.3 | 30.25 | 114% | 8 | 3.00 | 24.5 | 4K/40 3x 超预算 |
| B（upsample） | 28.1 | 24.9 | 3.2 | 29.5 | 112% | 8 | 3.02 | 22 | pass 仍未运行（`deploc=0`：depth 在 `g_depth_ring`，不在 `g_depth_local`） |
| C（auto） | **63.3** | 28.1 | 4.5 | 37.4 | 119% | 15 | 3.27 | **52** | 控制器没动作（无 `autoscale:`，待诊断）；100/100 时 XeFG 的 MV 数据相关工作更贵 |
| D（asym） | 45.7 | 0.4 | 2.1 | 2.7 | 9% | 0 | **1.00** | 90 | tag 尺寸不一致（MV 4K/depth 1440p）→ `ERR_INVALID_ARGUMENT`，FG 被关成 1X |

**drop 的归因**（A/B/C 的逐帧账）：

```text
gpu(XeFG 3x 4K) + present ≈ 25.4+3.3 … 28.1+4.5 = 28.7 … 32.6 ms   > T_in 25.0
⇒ load 112–132%，slow 40/40，skip 8–15，输出每 40 帧空 22–52 个 vblank
```

而传输侧：`bus` 1.1–2.5 GB/s（链路 9.19 GB/s），`mvs≈0`、`copy≈0`、`wait=0`、
`timeouts=0`、`producer_overrun` 未见增长。**结论：不是传输效率，也不是同步机制，
是 4K 3x 的 XeFG 生成时间本身超过了 25 ms 的输入预算**（与 `TIMING_4K40.md` §4.2 的
`gpu+1vblank = 28.9 > 25` 完全一致）。C 之所以更差，是它跑在 100/100（63.3 MB），
XeFG 对全分辨率 MV 的数据相关工作更贵；D 是上面的尺寸 bug。

第三轮修复：升采样的 depth 源改用 tag 同款的 `g_depth_ring[g_ring_write]`（不再要求
`g_depth_local`），B/D 的 pass 会真正运行；C 增加一次 `autoscale: first window v=… frame=…`
诊断，若 `frame=0.00` 就说明生产端的 `frame_time_ms` 没到桥（下一轮直接可见）。

### 7.2 第四轮（B–F）与“渲染卡被拖慢”

| 组 | bus | game= | gpu | present | total | load | skip | 空 vblank/40 | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| A | 28.1 | 25.15 | 25.35 | 3.3 | 30.25 | 114% | 8 | 24.5 | 4K 3x 超预算 |
| E（den2） | 28.1 | 25.1 | **11.0** | 12.65 | 24.45 | **94.5%** | **0** | **1.5** | 1080p 生成 → 不掉 |
| F（scale .75） | 28.1 | 25.1 | **14.45** | 7.85 | 22.5 | **91%** | **0** | **2.0** | 1440p 生成 → 不掉 |

**副卡侧结论**：4K/3x 的 `gpu` 是唯一超预算项；E/F 把 `gpu` 降到 11/14.5 后 drop 基本消失。
**渲染卡侧结论**：`game=` 随 StreamPercent 上升（150→25.1，100→27.2），说明拷贝确实串在
游戏帧上；同时发现 `frame_time_ms` 用了 record 间隔（7.5 ms）而不是帧时间，导致 C 的控制器误判。

已修（第四轮）：

1. **生产端异步拷贝**：第二条 **DIRECT** 队列（需要 barrier，COPY 表不能发），
   `present` 时游戏队列 Signal → 拷贝队列 Wait → 拷贝 → Signal(fwd)。游戏 Present 不再被拷贝
   阻塞；发布点后移 `T_copyP`，仍早于 WGC 交付。
2. **`frame_time_ms` 改为 publish 间隔**（每帧一次，≈25 ms），控制器据此算生产端余量。
3. 升采样 depth 源改用 `g_depth_ring[g_ring_write]`（B/D 的 pass 现在会真正运行）。
   注意：拷贝改到 present 之后后，消费端窗口从 `age` 缩到 `age − T_copyP`（4K/40 仍有余量）。

待复测：重启游戏后跑 A（基线，看 `game=` 是否从 25.1 降到 ~23.5）与 C（`frame≈25`，档位应落在
250 左右）；B/D 看 `reconstruction targets` 与 `xN≈3`。E/F 已经是“要 120 fps 就用 1440p/1080p
生成”的实证，可继续作为推荐配置。

### 7.3 A 复测：DMA 队列生效，渲染卡回到 90%

```
producer: DMA (COPY) queue ready - transfers leave the 3D engine
[mv] copy ... (declared state 0x800, list type 3)   ← 3 = COPY 队列
```

- 用户实测：渲染卡占用 **99% → 90%**，与 DMA 路径一致；
- 桥的 `game=` 仍是 25.0（游戏被 RTSS 锁在 40 fps，帧时间被锁本身饱和在 25 ms），
  所以渲染卡的收益要看**占用率**，不是 `game=`；
- A 的副卡数据不变：`gpu 25.9 + present 2.6 > 25`、`load 114%`、`skip 9`、空 vblank 24 ——
  这是 4K 3x 的算力上限，与传输无关；E/F 才是掉帧的解法。
- 复测中发现 `publish frame=` 仍是 13.1 ms：present detour 每帧调两次 publish。
  已改为“同一 `frame_qpc_ms` 只计一次”，部署后 `frame≈25`，C 的控制器才会按真实帧时间选档。

### 7.4 拓扑修正：WGC/DWM 在消费卡上，不在渲染卡

显示器接在消费卡（AMD）上，WGC 抓取与 DWM 合成都发生在消费卡；渲染卡（NVIDIA）只负责游戏渲染
和 producer 的 downsample/copy。因此：

- 渲染卡 90→99% 的 **+9% 全部是 producer 的降采样 + 拷贝**（150 档约 2 ms/25 ms ≈ 8–9 个百分点），
  不是 WGC/覆盖窗口；DMA 队列后回到 90%，这条修复是完整的。不要再拿 `--overlay-hidden` 去解释
  渲染卡占用（它只影响消费侧的合成与抖动）。
- 配对问题因此更硬：producer **拿不到 WGC 的颜色**，消费者必须把 WGC 颜色与 producer 的
  MV/depth 对齐。producer 的 `present_id` 在 WGC 侧不存在，只能靠时间戳或 producer 的
  `frame_qpc_ms` 做查表；这也是为什么“三队列完全不配对”不能直接成立。
- 唯一能真正做到“三路同源、零配对”的架构是：**颜色也由 producer 传**（backbuffer/HUDless，
  走 DMA/PCIe），三路同一个 key，消费者不需要 WGC。代价是 33–66 MB/帧颜色流量；收益是去掉
  WGC 的一帧延迟和消费侧的抓取/合成，而不是渲染卡占用。

### 7.5 为什么“舍弃 WGC”不会降低渲染卡占用

- WGC/DWM 在消费卡上；对渲染卡是 **0 成本**。渲染卡的 +9% 已经由 DMA 队列解决（90%）。
- 当前 CP2077 `Mode=consume` 的 record 是 **untagged**（`record: upscaler lane (untagged)`，
  只有 MV/depth）——producer **根本没有颜色**。要让 producer 传颜色，只能拿 fakerFG 自己拥有的
  XeFG 链 backbuffer，在 Present 前/后用第二条队列拷 4K FP16（66 MB，或 10-bit 33 MB）。
- 历史实测（`ARCHITECTURE.md` §6.1）：`Color=1` 让渲染卡 **80% → 95%（+15 个百分点）**，
  而且 bridge 当时根本不读这条流——这正是当年改用 WGC 的原因。
- 因此：**舍弃 WGC 会增加渲染卡占用**，与 90% 的目标相反。若目的是解决配对/延迟，应做
  “producer publish → prefetch 拷贝 → WGC 到达时 frame_key/时间戳查表”，而不是换颜色源。
- 如果仍然要走“无 WGC”，需要 fakerFG 暴露链 backbuffer + producer 新增 colour 槽
  （两路合计约 550 MB 共享内存），并且接受渲染卡 +10–15%；这条作为可选模式，不应是默认。

### 7.6 输入预拷成为默认（2026-11-14）

按“消费者一边 WGC、一边拷贝，到货只查表”的模型落地：

- `--prefetch-inputs` + `--input-copy-queue` **默认开**；上一帧 Present 之后就在 consumer 的
  COPY 队列上记录下一槽的拷贝，copy 队列在 GPU 侧等 producer 的 `fwd`（不占 CPU）。
  CPU 随后阻塞在 `TryGetNextFrame`，所以跨卡读与 WGC 抓取并行，数据落进本地显存
  （`g_mv_local[slot]` / `g_depth_ring[]`，4 槽）。
- WGC 到达后 `pair_slot_for_wgc` 只做**本地查表**（WGC 时间戳 vs producer 的 `frame_qpc_ms`）；
  命中就直接用预拷好的那份，不再发起拷贝；未命中才补拷该槽（日志 `pf: hits/misses`）。
- 升采样与预拷共存：命中时在录 pass 之前对 copy fence 排一次 GPU 侧 Wait；未命中时该帧的
  拷贝留在 direct list 上（pass 必须能读到）。
- `--no-prefetch-inputs` / UI「输入预拷 (A/B)」关闭，恢复“WGC 到达后再拷”的旧顺序。

### 7.7 A/C 复测：预拷把 4K/3x@40 的 drop 消掉，控制器需按副卡预算反馈

|---|---|---|---|---|---|---|---|---|
| **A（150 + 预拷）** | 28.1 | **21.2** | 2.7 | 24.8 | **96%** | **1** | **4** | 34–37 / 3–6 |

- A 说明：预拷把 `gpu` 从 25.9 降到 21.2（拷贝不再落在 XeFG 的关键路径上），

  producer 的 `active_percent`。150 档 `gpu+present=23.9`，落在死区内，应保持 150。
