# 三方合流：双卡补帧场景下还能吸收哪些节奏算法

> 输入：本仓 `xess_mfg_consumer` 的节奏栈（`docs/design/PACING_VS_OPTISCALER.md`）、
> OptiScaler 的六条限帧路径与 Dynamic MFG（`docs/design/OPTISCALER_FPS_PACING.md`）、
> XeLL 的标记/睡眠机制（同上 §6.2 + 本仓 DLL 实测），以及双卡链路的硬约束
> （`docs/design/TOTAL_ARCHITECTURE_AND_DATAFLOW.md`、`TIMING_4K40.md`）。
>
> **TL;DR**：真正值得吸收的不是"再做一个限帧器"，而是四类东西——
> ① **相位锚换成游戏时钟**（`frame_qpc_ms`，QPC 系统级共享，这是我们比 OptiScaler 更有条件做的事）；
> ② **切换的验证/撤销/退避**（OptiScaler `XeFG_DynamicCap` 的 meta 算法）；
> ③ **失活状态机 + 观测口径**（OptiScaler 的 20 帧守卫 + Magpie 的分位数）；
> ④ **XeLL 的完整契约**（调用顺序、INPUT_SAMPLE、日志回调、frames reports）。
> 明确不吸收：在 consumer 里做限帧、给 XeLL 设 `minimumIntervalUs`、VRR、
> `TargetAsCap` 那套"限帧器当控制器"的框架。

---

## 1. 三方各自的"真本事"

| 来源 | 真正的贡献 | 与我们的关系 |
|---|---|---|
| **本仓** | 交付**相位**：绝对 vblank 网格、无债、过期整周期跳、真实 vblank 校准、`k·vblank` 预算、applied-k 记账 | 已经领先；缺的是"锚点"和"验证" |
| **OptiScaler** | **目标值治理**（单一 `targetFps` + 唯一 owner + 0=不接管）、**切换治理**（hold / 验证窗 / undo / 退避）、**失活守卫**（20 帧无输入即退出）、墙钟 pacer 的反面教材 | 目标治理与切换治理可直接借 |
| **XeLL** | **标记即时钟**（6 个 required marker + frame id）；睡眠是可选的；`xellGetFramesReports` 是官方观测口 | 契约要补全；睡眠在 A 卡上不指望 |

## 2. 双卡场景的硬约束（决定"能采纳什么"）

```
游戏（NVIDIA 渲染卡）          共享内存(32 槽)            xess_mfg_consumer（AMD 6750 GRE）
 fakerFG 记录 MV/depth  ──发布──▶ colour/MV/depth ──拷贝──▶ 转换 → XeFG → 代理交换链 Present
 帧时钟 frame_qpc_ms（游戏自己的 present 时钟）
```

1. **限帧必须在游戏进程**：我们只有"交付相位"。任何在 consumer 加的限帧都
   等价于丢帧或加延迟（已在上一份文档论证）。
2. **地板不可压**：总耗时 = 跨卡拷贝 + 转换 + FG 单批成本 + Present。
   `TIMING_4K40` 的结论是 4K 3x@40 装不下——pacing 只能排列，不能创造时间。
3. **QPC 是系统级的**：producer 的 `frame_qpc_ms` 与 consumer 的 `qpc_ms()` 同一计数器。
   这是**双卡链路独有的机会**：我们可以把交付相位锚在游戏帧时钟上，
   而不是"帧到我们手里"的时刻。OptiScaler 在同一进程里没有这个问题，所以它没做。
4. **XeFG 自己会 present pacing**：`Present` 内部可能阻塞十几毫秒、库内还有高优先级
   pacing 线程（`XESS_FG_NOTES.md` §1）。所以**不能再叠 `--pace`**（bridge 里已有告警）。
5. **A 卡 XeLL 只提供契约 + 标记**（上一轮结论）：`xellSleep` 实测 0.0 ms；
   标记缺了反而会拖坏 XeFG 的节奏（`FINAL_CONFIG.md` §5.1）。
6. **VRR 关闭是前提**：网格算法假设固定 vblank。

**由此推出采纳的边界**：我们只优化"把帧交给 XeFG 的时刻"和"每批出几张"，
以及"这些决策怎么被验证、怎么回退"；不碰"游戏跑多快"。

## 3. P0：先补"观测与守卫"（低成本、不改控制律）

### P0-1 XeLL 契约补全（把"有没有睡"变成可测）

| 项 | 现状 | 改动 |
|---|---|---|
| 调用顺序 | `SIMULATION_START` → `xellSleep` → `SIMULATION_END`（`frame.cpp:1427-1435`） | 改成 `xellSleep` → `SIMULATION_START`，与 OptiScaler `ll_xell.cpp:125-132` 一致 |
| `XELL_INPUT_SAMPLE` | 未发 | 在"输入采样"点（公共 header 里已有 `frame_qpc_ms`）补一个 marker，给 XeLL 算 input→present 距离 |
| 日志 | 无 XeLL 内部日志 | `xellSetLoggingCallback` 接一行（限流 1 条/秒），直接看到 `No sleep algorithm available.` / `Slept for ...` |
| 帧报告 | 未用 | 接 `xellGetFramesReports`，把 XeLL 自己的帧统计并入报告行（只读） |

**验收**：`xell=` 是否从恒 0.0 变为非 0；`Slept for` 是否出现。
若仍为 0，说明 A 卡 cross-vendor 路径在我们的用法下不解锁，**结论写死，不再投入**。

**风险**：极低。顺序改动若让 XeFG 的呈现行为变化，A/B 一次即可回退。

### P0-2 单一"目标 + owner"入口

OptiScaler 的做法值得照搬的是**形式**，不是内容：

```cpp
// 目标值：面板 / 用户上限 / 成本上限，取 min；0 = 不限
double pace_target_hz();
// 执行者：谁负责这一帧的等待（只允许一个）
enum class PaceOwner { None, InputGrid, Opportunistic, LegacyTick };
PaceOwner pace_owner();     // 每个报告窗口打一次，不进热路径
```

现状：`--fg-out-hz`、`--cad-budget`、`--cad-kmax`、`g_pace_ms`、`g_cad_latency_budget_ms`
各自独立，组合起来会出现"以为在锁 40，其实 k 被成本上限压到 2"的情况。

**改动**：把上述旋钮收敛到一个 `PaceConfig`（`init_fg()` 末尾算一次），
启动打一行 `pace: target=… owner=… budget=… Λ=…`；运行中只在变化时打。
**验收**：配置组合不再互相打架（用 `--list-modes` 风格的表格自检）。

### P0-3 `fg_input_pace` 补"超前重锚"

`FpsLimiter` 有两条守卫，我们只有一条：

| 守卫 | OptiScaler `ll_fps_limiter.cpp` | 本仓 `fg_input_pace` |
|---|---|---|
| 过期（`next <= now`） | 重锚 `now + interval`，不睡 | 按整 vblank 跳（**更好**） |
| 超前过多（`next - now > interval`） | 重锚 | **缺**（只有 `>100 ms` 的 stall 重置） |

后果：把 `k` 从 4 降到 2、或从 `--cad-budget vblank` 切回 `input-T` 时，
下一批可能等一个"旧的大间隔"。改动一行：

```cpp
if (due - now > std::max(k * vb * 1.5, 100.0)) { due = now; g_fgi_reanchor++; }
```

**验收**：切档后第一帧的 `gap` 不再出现 > 1 个旧预算的尖峰；新增 `reanchor` 计数进报告。

### P0-4 失活状态机（OptiScaler 的 20 帧守卫 + Magpie 的 idle）

现状：只有 `now - next > 100 ms` 的单点重置；暂停恢复后 `cadence` 的估计器
（`src/cadence_core.h` 的 `Sample`/EMA）仍带着旧值。

**设计**：

```
Running --(连续 20 个时隙没有新发布)--> Stalled
Stalled --(新发布到达)--> Resuming: grid = now + k·vb, cadence.Sample.reset(),
                                   phase=0, 不清 applied_k
Resuming --(连续 3 批按时)--> Running
```

OptiScaler 用 `presents_without_input <= 20`、`_updatesWithoutMarker > 20` 两处同样阈值，
20 帧（60 fps 下 0.33 s）是"这个源停了"的经验值。

**验收**：菜单/加载进出后 `late` 不再持续增长、`switches` 不因恢复而抖一次；
`rhythm` 的 >0.15vb 占比在恢复后 1 s 内回到基线。

### P0-5 报告行补"节奏观测"（Magpie B4 的口径）

现在报告里有 `pace=… repres… skip…` 和 `cadence … fgpace=… late=…`，
但缺**分位数**与**预算符合度**。建议加 4 个字段（只统计，不影响控制）：

```
pace(ms p50/p95)  late%  skip%  budget_err(p50/p95)   grid_phase(std ms)
```

口径必须写清："**provider submissions, not display events**"——真要验收平滑度
仍然要 PresentMon/ETW。这一条是 Magpie 反复强调的，也是我们日志里最容易过度解读的地方。

## 4. P1：控制律的三处实质改进

### P1-1 相位锚换成游戏时钟（双卡独有的机会）

**问题**：现在 `fg_input_pace` 的 `due` 从"帧到我们手里"的 `qpc_ms()` 起算。
于是跨卡拷贝、配对等待、转换的抖动都会**平移相位**——同样的游戏节奏，
今天相位落在 vblank 的 0.2 ms，明天落在 2.8 ms，主观上就是"说不清的轻微顿挫"。

**依据**：producer 已经在每个发布里写了 `frame_qpc_ms`（游戏自己的 present 时钟），
且 QPC 是系统级计数器。`frame.cpp:1295-1305` 已经用它算输入间隔（还带单调性守卫），
但**没有用它做相位**。

**设计**：

```
game_t = frame_qpc_ms[n]                       // 游戏的第 n 帧时钟
offset = median(handoff_qpc[n] - game_t[n])    // 我们的固定管线延迟（慢速中位数，500 ms 窗）
due[n] = snap_to_vblank(game_t + offset)       // 把"游戏第 n 帧"映射到最近的 vblank 格
```

- `offset` 只跟踪慢变（管线延迟），不跟单帧抖动；
- snap 仍按现有规则（过期整周期跳、不追赶）；
- 若某帧 `frame_qpc_ms` 缺失/倒退（配对失败），退回现在的到达时刻锚点并计数。

**收益**：相位误差从"管线 jitter（我们实测有几 ms）"降到"offset 估计误差"，
而且**跨卡抖动只影响"能不能赶上"，不再影响"落在哪"**。

**风险**：`frame_qpc_ms` 是 Evaluate 时刻（`frame.cpp:1902` 注释：一帧可能 Evaluate 多次），
不是 present 时刻；需要先确认它与 present 的差是常数（或慢变），否则 offset 里会混入它的抖动。
建议先做**影子模式**：只计算 `phase_error = due_from_game - due_from_arrival` 写进日志，
跑 2 分钟看分布，再决定是否切换。

**验收**：`grid_phase(std)` 下降 ≥ 50%；`rhythm` 的 >0.15vb 占比下降；主观顿挫消失。

### P1-2 切换的"验证 → 撤销 → 退避"（OptiScaler `XeFG_DynamicCap` 的 meta 算法）

我们已经有：`minDwell`、`deadband`、`NoteSwitchLoss`、`autoTuneDwell`（默认只测量）。
缺的是 OptiScaler 那套**改变之后的闭环**（`XeFG_DynamicCap.h:82-119`）：

| OptiScaler 的规则 | 我们要补的等价物 |
|---|---|
| 切完跳过 3 帧（还在飞的是旧 k），再统计 ≥6 帧 / ≥0.4 s | 切 k 后跳过 `k_old` 帧，再用 ≥6 帧统计"输出是否仍 ≥ target×0.97" |
| 若不达标 → **撤销（回到旧 k）** 并记录"这次切换失败" | 撤销 + `++switch_fail` |
| 撤销后**指数退避** 5 s → 60 s 不再降档 | `down_blocked_until = now + backoff`，`backoff *= 2` |
| 若"可达帧率"涨了 10%，提前解禁 | 用 `1000/(T − 自身等待)` 判断（我们已有 `fgpace` 与 `gpu`） |
| 成功则 `backoff = 5 s` 复位 | 同上 |

**为什么这条最重要**：`CADENCE_STRATEGY_V2.md` 的实测是"切换 ≈ 丢一张输出"，
而当前逻辑只**测量**成本、不**回滚**错误决策——一次错误的降档会一直留在低 k，
直到下一个死区。OptiScaler 把它变成"试错 + 记住失败"。

**落点**：`src/cadence_core.h` 的 `Update/Commit` 外加一个 `SwitchGuard`
（纯计算，可在 `tests/cadence_core/sim.cpp` 用仿真覆盖：注入"降档后输出不达标"的输入，
断言 60 s 内不再降档）。**验收**：`switches` 下降、`switch_fail` 可见、`out` 的 p50 不降。

### P1-3 延迟预算 Λ 自适应（方差/分位，来自 FFX 的 pacing 公式）

现在 Λ = `g_cad_latency_budget_ms`（固定值）。FFX 的思路值得借一半：

```
target_delta = mean(frame) − variance×factor − safetyMargin
```

我们不需要它那句"目标帧时间"，但需要"**抖动大时少等**"：

```cpp
Λ_eff = clamp(Λ_cfg, 0.15×vb, 0.5×vb) × (1 − min(1, jitter_p95 / vb))
```

即：到达 jitter 的 p95 接近一个 vblank 时，放弃机会式对齐（P4 走"立即提交"分支），
把预算让给延迟；jitter 小的时候才追求相位。
再叠加一条**背压联动**：`gpu_throttle` 的等待 > 0.5×vb 时，本次不再 pace
（GPU 已经在饱和，排队只会加延迟）——这条是双卡特有的，OptiScaler 的 present 路径没有
"上一帧 GPU 还没干完"这个概念。

**验收**：`pace skip%` 与 `late%` 上升（预期），但 `total` 的 p95 与 `age` 下降；
主观延迟变好、节奏不变差。

## 5. P2：结构性补充

### P2-1 双卡成本模型成为 `locked` 的准入条件

`locked`（`k·vblank` 预算）要求"每批真的能在 `k·vb` 内做完"。
现在 `costPerOutputMs` 是手工/估计值；应该用实测 p95：

```
准入：copy_p95 + convert_p95 + k×fg_cost_p95 + present_p95  ≤  k×vb × 0.9
不满足 → 不进入 locked，落到 cap-limited（并说明原因）
```

出处：OptiScaler 的 `costPerOutputMs` / `overheadMs` 概念（`cadence_core.h` 里已有字段），
加上我们自己的 `TIMING_4K40` 预算表。**注意**：准入失败时不要自动降 k，
而是"退出 locked、回 carry"，因为降 k 会改变输入需求（连锁反应）。

### P2-2 高分辨率定时器替代自旋

现在 `Sleep(wait-1)` + `YieldProcessor` 自旋最多 1 ms/帧。40 fps 下约 4% 一个核，
120 fps 下约 12%，而且自旋会与游戏/拷贝线程抢超线程。
Magpie 的做法（`FramePacingWait.h`）是 `CreateWaitableTimerExW(HIGH_RESOLUTION)`
睡到 deadline 前 ~0.2 ms 再自旋。OptiScaler 也是 2 ms 阈值。

建议：`wait > 1.5 ms` 时用可等待定时器睡到 `due − 0.3 ms`，最后 0.3 ms 自旋；
失败时退回现在的 `Sleep(wait-1)`。**验收**：`cpu=` 下降、`grid_phase(std)` 不升。

### P2-3 标记去重与 frame id 单调守卫

OptiScaler 在 `InputCommon::set_marker` 里做了一件我们没做的事：

```cpp
// 同一 marker 类型 + 同一 frame id 重复到达 → 直接返回
if (last_marker_frame_ids[type].exchange(frame_id) == frame_id) return InputResult::Ok;
```

它是因为 TW3 会在 present 之后重发 `RENDERSUBMIT_END`。我们的风险不同但同类：
若将来把 `--pace` 的"重复上一帧"用到 XeFG 路径，`present_id` 会重复，
libxell 会打 `Marker already submitted for frame:` / `Different marker submitted before ...`
并可能污染它自己的帧统计。

建议：加一层 `xell_marker(type, fid)` 守卫（同类型同 id 丢弃、id 倒退则记一次事件），
并给 `present_id` 加"每帧必须递增"的断言（`g_reuse_frame` 时不发标记）。

### P2-4 观测升级：把"显示事件"接进来

现在所有验收都基于 provider 提交（`presents`、`vblank_phase`、`rhythm`）。
Magpie 反复强调这不是显示事件。P2 的最小版本：
用 `IDXGIOutput::WaitForVBlank` 的相位统计（已有）+ ETW/PresentMon 的一次性对照，
在文档里给出"提交间隔 vs 显示间隔"的偏差，避免把 p95 当成画面结论。

## 6. 明确不采纳

| 候选 | 为什么不做 |
|---|---|
| 在 consumer 里做真正的限帧（`FrameLimit`/`FpsLimiter` 等价物） | 位置错误：输入已采到，晚了只能丢/加延迟；限帧属于游戏进程 |
| 给 XeLL 设 `minimumIntervalUs` | 会与 XeFG 内部 pacing 双重限帧；A 卡上睡眠本来就是空的 |
| `TargetAsCap` 整套（限帧器钉住 target、再调 k 去够） | 我们的 FG 输出方就是 XeFG，k 是已知量；"驱动自己数帧"的路径不存在 |
| 用墙钟做 deadline | OptiScaler 的反面教材（NTP step 会丢时隙）；我们已全 QPC |
| `--pace` 与 FG 同开 | XeFG 自己在 present 里 pacing，叠加会串行（bridge 已有告警，`FINAL_CONFIG` §5.3） |
| VRR 兜底 | MFG pacing 假设固定 vblank；VRR 是第二个控制器 |
| 把 FSR-FG 的 `mean − k×variance − margin` 直接当输入预算 | 那是 present 调度的余量公式；输入侧我们用的是 vblank 整格，语义不同。只借"抖动大就少等"的思想（P1-3） |

## 7. 目标架构（合流后）

```
                    ┌──────────────── 观测（只读，每窗口一行）────────────────┐
                    │ pace wait p50/p95 · late% · skip% · phase std · xell/fg/gpu │
                    └───────────────▲────────────────────────────────────────────┘
                                    │
frame_qpc_ms ──► 相位锚(P1-1) ──► due ──► wait(定时器+自旋, P2-2) ──► 交给 XeFG
      │                             ▲
      └──► cadence core ──► k, budget┘
             │  ▲
             │  └── SwitchGuard(P1-2)：验证 / 撤销 / 退避
             ├──► 成本准入(P2-1)：copy/convert/fg p95 ≤ k·vb
             └──► Λ(P1-3)：jitter p95 + gpu_throttle 背压

owner 仲裁(P0-2)：InputGrid | Opportunistic | LegacyTick | None —— 永远只有一个
失活状态机(P0-4)：Running / Stalled / Resuming
XeLL(P0-1, P2-3)：xellSleep → SIMULATION_START → …；标记去重；frames reports 只读
```

|---|---|---|---|---|
| E1 | XeLL 顺序 + INPUT_SAMPLE + 日志回调 | 现状 | `xell=` 非 0 或明确打印 `No sleep algorithm available.` | 还原顺序 |
| E2 | P3 超前重锚 | 现状 | 切档后 `gap` 无尖峰；`rhythm` 不变差 | 删 3 行 |

| E4 | 相位锚 = `frame_qpc_ms`（影子 → 启用） | 到达锚 | 影子期 `phase_error` 分布 < 0.5 vb；启用后 `grid_phase(std)` −50% | 切回到达锚 |
| E5 | SwitchGuard（撤销 + 退避） | 现状 | `switches` 下降、`switch_fail` 有记录、`out` p50 不降 | 关 `--cad-guard off` |
| E6 | Λ 自适应 + 背压联动 | 固定 Λ | `total` p95 / `age` 下降，`rhythm` 不变差 | 固定 Λ |
| E7 | locked 成本准入 | 现状 | 进 locked 的窗口不再出现 `load>90%` 的批次 | 只用 `--cad-budget vblank` |

每组 2 分钟同场景，报告必须同时给：`rhythm`（|k−slots|>0.15vb 占比 / spacing err）、
`out` p50/p95、`presents/vblanks`、`late%`、`switch_fail`、`HITCH`、主观。

## 9. 优先级与判断依据

1. **先做 P0（1–2 天）**：全部是观测与守卫，不改控制律，风险接近零，
   但能把后面所有实验的"能不能测出来"补齐。
2. **再做 P1-2 与 P1-3**：这两条直接对着已知痛点（切换丢帧、延迟 vs 相位）。
3. **P1-1 谨慎推进**：收益最大，但前提是确认 `frame_qpc_ms` 与 present 的差是慢变的；
   先影子跑，不要直接上线。
4. **P2 按需**：成本准入与定时器属于"有预算再做"；标记去重是防未来踩坑。
5. **§10 的自由渲染路线是独立分支**：它把"切换治理（P1-2）、deadband、regime 分类"
   全部替换成"固定 k + 抽帧门 + 欠供安全阀"，实现更简单，但**先要解决 MV 语义**；
   建议在 P0 的观测（尤其 `drop%`/`underfill%`/`in_step`/`out_step`）做完之后再开 E8。

一句话：**我们已经把"排相位"做到了 OptiScaler 之上，缺的是"锚在游戏时钟上"、
"切换要能反悔"、"失活要能重来"、"观测要能验收"这四件事。**

## 10. 场景变体：主卡不限帧 + 动态渲染帧数 + 固定倍率

这是另一种需求：**不给游戏任何限帧**（主卡跑满，f 由 GPU 负载自然决定、逐秒变化），
消费端用**固定倍率 m**（2x/3x/4x）补帧。它和前面所有方案的前提都不一样：
前面的方案默认"输入节拍稳定、k 可变"，这里正好反过来——**k 固定、f 自由**。

### 10.1 算术：先看它到底能不能成立

```
面板 R 帧/秒（固定刷新，120 Hz）
游戏 f 帧/秒（GPU 决定，自由变化）
固定倍率 m = k+1（每张真帧出 m 张）
输出 = m·f
```

固定 m 时，输出帧率**跟着 f 走**。要让它落在固定刷新面板上，只有三种结局：

| regime | 条件 | 现象 | 能不能救 |
|---|---|---|---|
| **均匀抽帧**（推荐） | `m·f ≥ R` | 输出多于面板 → 丢掉一部分**输入**帧，让"被保留的输入"恰好每 `m·vb` 来一张 | ✅ 可控、可均匀、延迟有界 |
| **理想** | `m·f = R` | 一张不多、一张不少 | ✅ 无需动作 |
| **欠供** | `m·f < R` | 输出少于面板 → 面板重复 | ⚠️ 只能靠 m+1 / VRR / 接受 |

关键的一点：**"抽帧"不等于慢动作或抖动**。只要
(a) 保留哪些输入是**均匀分布**的（Bresenham），
(b) `frameRenderTime` 喂的是"上一个保留帧 → 当前帧"的真实间隔，
(c) 交接节拍是 `m·vb`，
那么 XeFG 会在 `m·vb` 里均匀插出 m 张，**每张显示正好占 1 个 vblank**，画面节奏
与"锁帧 3x@40"完全一致——区别只是游戏实际在 70 fps 跑，我们只用了其中 57% 的帧。

### 10.2 数字（120 Hz，m = 3，预算 25 ms）

| f（输入） | m·f（输出） | 需保留 | 抽帧率 | 面板显示 | 备注 |
|---|---|---|---|---|---|
| 38 | 114 | 100% | 0% | 114 | **欠供**，每秒约 6 次重复 |
| 40 | 120 | 100% | 0% | 120 | 理想点 |
| 45 | 135 | 89% | 11% | 120 | |
| 50 | 150 | 80% | 20% | 120 | |
| 60 | 180 | 67% | 33% | 120 | |
| 70 | 210 | 57% | 43% | 120 | 主卡跑满的常见情形 |
| 90 | 270 | 44% | 56% | 120 | 浪费开始明显 |

推论：**m 必须按"最差帧率"选**，否则会掉进欠供：

```
m = ceil( R / f_p5 ) 且 m × f_p5 ≥ 1.02 × R     // f_p5 = 输入帧率的 5% 分位
```

用 p5 而不是最小值，是为了允许极短欠供；用 2% 余量是为了避免 f 在边界附近抖动时
在"刚好够"和"欠供"之间来回。m 一旦选定就**不再改**（下面 §10.5 有安全阀）。

### 10.3 核心新增：均匀抽帧门（decimation gate）

现状的 `locked` 策略**不能直接用**：它要求 `k·vb ≥ T`（预算不小于输入间隔），
否则 pacer 会比发布慢，而主循环是"一发布一帧、取最旧"，backlog 会一路堆到 32 槽
（`main.cpp:1076-1080`），最后配对失败。所以必须有**显式丢帧**，且丢在最早的位置：

```cpp
// 在"选出最旧未处理发布"之后、跨卡拷贝之前调用
// q = 应保留的比例（慢速 EMA，只在变化 >5% 时更新）
static double acc = 0.0;
bool keep = false;
acc += q;
if (acc >= 1.0) { acc -= 1.0; keep = true; }

if (!keep) {
    ack_publication(pub);      // 只 ACK，不拷贝：让 producer 立刻回收槽位
    ++g_dec_dropped;
    continue;                  // 不推进 pacer 的 due
}
```

四条不变式：

1. **先丢后拷**：丢在 `wait_slot`/`copy_inputs` 之前，省掉跨卡拷贝 + 转换 + FG 的整段成本；
   ACK（`colour_seq` 水位）必须照发，否则 producer 的信用窗口会卡住。
2. **丢最旧、不丢最新**：与现有"取最旧"一致，队列深度恒为 1，延迟不随抽帧率增长。
3. **q 的更新必须慢**（≥0.5 s EMA，变化 >5% 才改）：q 抖 → 抽帧图案抖 → 内容步长不均匀。
4. **不推进 `due`**：`due` 只在真正交接后 `+= m·vb`，所以显示网格与抽帧解耦。
5. （可选优化）交接时**不取"最旧未处理"，而取"时间戳 ≤ due 的最新一张"**：
   `frame_qpc_ms` 是游戏时钟，可以直接比较。这样每批都用最新鲜的内容，
   延迟最低；被跳过的那几张反正本来就要丢。

### 10.4 必须同时解决的三个问题（否则会坏）

**① MV 与 frameRenderTime 的语义断裂（最大风险）**

XeFG 的插值输入是 `(prev, cur) + MV(prev→cur) + frameRenderTime`。
一旦丢掉中间帧，保留对变成 `prev = n−1, cur = n+1`，而游戏给的 MV 只描述
`n → n+1`（一个间隔）——**位移被低估一半，插出来的中间帧位置全错**（快速平移时会看到
"贴图滑动/重影"，比抖动更难看）。

三种解法，按推荐顺序：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 消费端光流** | 丢帧时改用 FidelityFX OF 在 `(prev, cur)` 之间重算 MV（我们已有 `--fg-of`，实测约 0.3 ms） | 消费卡 +0.3 ms/批；质量取决于 OF |
| **B. producer 侧合并 MV** | producer 在发布 `n+1` 时，把 `MV(n→n+1) + MV(n−1→n)` 相加后发布 | 渲染卡多一个小 pass（省 PCIe，因为 MV 本来就要传）；遮挡区会错 |
| **C. 反馈给 producer "哪些 seq 被保留"** | `colour_seq` ACK 里加一个 `kept_seq`，producer 只发布"相对上一个 kept"的 MV | 需要游戏 MV 可按帧累加；实现最重 |

无论选哪种，**`frameRenderTime` 必须与 MV 描述同一个时间跨度**（保留帧的间隔），
否则 XeFG 的 pacing 与位移会互相矛盾。这是这条路线唯一的硬约束，也是最容易漏测的地方。

**② 槽位与信用窗口**

丢掉的发布必须**立刻 ACK**（推进 `colour_seq` 水位），否则 producer 的信用窗口会卡住；
`--prefetch-inputs` 的 copy-on-publication 也要在抽帧门之后才做预拷，
否则省下的带宽又被预拷吃回去。注意 `colour_seq` 是单调水位，**只能按序丢**（丢最旧），
不能"挑着丢"。

**③ `slow` / `load` 的统计口径**

抽帧会让"发布间隔"与"交接间隔"分离。`slow`、`load`、`jitter` 必须用**各自的口径**：

- `jitter`/`arr` 用 producer 的发布间隔（游戏真实节奏）；
- `slow`/`load` 用**交接间隔**（我们真正处理的节奏）；
- 新加 `drop%`、`underfill%`、`in_step`（保留帧间隔 / 输入间隔，理想 ≈ k）。

### 10.5 欠供（f < R/m）的三个选项

| 选项 | 做法 | 适用 |
|---|---|---|
| 接受 | 记 `underfill%`，面板重复。`m·f` 只差 1–2% 时肉眼几乎不可见 | 轻微、短时 |
| **安全阀：m+1（迟滞）** | `underfill > 5%` 持续 2 s → m+1；之后 `underfill ≈ 0` 且持续 10 s 才允许回到 m | 游戏帧率在边界附近波动 |
| VRR | 面板跟随 `m·f` | 需要确认 MFG+VRR 可行（本仓未验证） |

安全阀不是"动态倍率"：它只在异常持续 2 s 后动一次，且单次只 ±1，
与 `DynamicCount` 每帧决策完全不同。要保留"固定倍率"的语义，就把安全阀做成默认关闭。

### 10.6 收益与代价（说清楚，别夸大）

| 项 | 结论 |
|---|---|
| **主收益** | 主卡不再被限帧：画质/分辨率可以拉满，GPU 利用率由游戏自己决定；不再需要"为了锁帧而降设置" |
| **次收益** | 内容更新鲜：端到端延迟平均降 `(1/f_kept − 1/f_render)/2`，40→70 fps 的场景约 **5–11 ms** |
| **消费卡成本** | **与 locked 完全相同**：保留率 × m = R，FG 每秒批次数不变（`R/m`）；不额外增加 |
| **主卡浪费** | 丢帧比例 `1 − R/(m·f)`，只是"渲染了但没显示"，不影响链路时序 |
| **代价** | 插帧的输入跨度变大（相邻保留帧可能隔 2 个渲染帧）→ 遮挡/重影风险上升；需要 §10.4① 的 MV 方案 |

一个容易误解的点：**"主卡不限帧"不会提高显示帧率**（上限永远是 R），它提高的是
"游戏在相同画质下的自由度"和"内容新鲜度"。如果目标是"更高画质"，这才是它的价值。

### 10.7 与现有 cadence 的关系：新增 `kPolicyFixed`

```
kPolicyFixed：
  k = 用户值（--fg-interp N），永不改
  budget = k × vblank
  q = clamp(R / (m × f_ema), 0, 1)     // 抽帧比例，慢速 EMA
  不做 regime 分类、不做切换、不需要 SwitchGuard
```

好处：**直接消灭"切换丢帧"这一类问题**（P1-2 在这条路线上不再需要），
控制律退化成"一个乘法 + 一个累加器"，可预测性最好。
坏处：f 大幅波动时只能在"浪费"和"欠供"之间二选一，没有中间态。

可以保留的观测（都很便宜）：`q`、`drop%`、`underfill%`、`in_step`/`out_step` 分布、
`out p50/p95`、`presents/vblanks`、`of=`（若启用光流）。

### 10.8 实验（在 §8 的矩阵上追加）

| # | 改动 | 通过标准 | 风险 |
|---|---|---|---|
| E8 | `kPolicyFixed` + 抽帧门（先用游戏 MV） | `out`=R、`presents/vblanks≈1.0`、`rhythm` 不变差；快速平移时观察插帧错误 | MV 语义断裂，可能明显变差 |
| E9 | E8 + 丢帧时切 OF 重算 MV | 插帧质量回到 locked 水平；`of=` ≤0.5 ms | 消费卡成本、OF 失败时的降级 |
| E10 | 欠供安全阀（m+1，默认关） | f 掉到 p5 以下时 `underfill%` 下降，且 10 s 内不会来回切 | 与"固定倍率"语义冲突，需显式打开 |

判据与前面一致：`rhythm`、`out p50/p95`、`drop%`、`underfill%`、`age`、主观，
并且**必须分开看"节奏"和"插帧质量"**——E8 很可能节奏完美但画面更糟，这正是要测的。

### 10.9 什么情况下不要这么做

1. **f 长期低于 R/m**：先降画质/分辨率，或降 m；否则面板一直在重复。
2. **游戏 MV 不可用、又不想付光流成本**：抽帧会直接伤插帧质量，宁可锁帧。
3. **主卡已经功耗/温度受限**：所谓"释放性能"只是让它更热、更吵，帧率未必更高。
4. **游戏逻辑与帧率强绑定**（部分物理/动画/网络插值）：自由帧率会让步长变化，
   锁帧反而更稳。
5. **需要可复现的基准测试**：固定输入节拍才有可比性，自由帧率下每次跑都不同。

## 11. 输入率的两侧摆动：41/35 这类现象怎么解

### 11.1 现象的本质不是"限帧器不准"，而是量化 + 负载

锁 40 fps 时，时间轴上的目标间隔是 25 ms，但限帧器只能在"整帧"上做决定，
而游戏的自然帧时间又会随负载在 23.8–28.6 ms 之间变。于是实测出现两侧：

| 观察值 | 换算 | 本质 | 对我们的后果 |
|---|---|---|---|
| 41–42 fps | T = 23.8–24.4 ms | 游戏自己比限帧目标快，限帧器只能"少睡"，**超供** | 每帧富余 0.6–1.2 ms → pacer 等到 `due` 才交，富余变成积压；直到 `now - next > 100 ms` 触发硬重置（`frame.cpp:79`）才追平，**期间延迟最高 +100 ms，重置点就是一次可见跳动** |
| 35–39 fps | T = 25.6–28.6 ms | 负载把这一帧顶晚了，**欠供** | `due` 已过期 → 现在按整 vblank 吸附 → **整 1 vb 的重复**，且相位永久后移 |

关键量化：120 Hz 面板只能干净地显示 `R/n`（120 / 60 / 40 / 30…）。
**41–42 fps 和 35–39 fps 都不是 R/m 的整数关系**，所以任何"固定倍率 + 固定刷新"的组合，
只要 f 不等于 40，就必然产生 1/2 vb 交替的步长——区别只在**误差是被摊开还是被集中**。

### 11.2 现有采纳点对两侧的覆盖

| 采纳点 | 对上侧（超供 41–42） | 对下侧（欠供 35–39） | 说明 |
|---|---|---|---|
| §10.3 均匀抽帧门 | ✅ **正解** | — | 丢掉多余输入，延迟恒定，显示间距恒 1 vb |
| P0-3 超前重锚 | ✅ 防切档尖峰 | — | 不是日常摆动的解 |
| P1-1 相位锚（`frame_qpc_ms`） | ⚠️ 辅助 | ⚠️ 辅助 | 让"该不该丢/该不该等"的判据基于游戏时间，误差不再来自管线 |
| P1-3 Λ 自适应 | — | ⚠️ 只减少"多等的延迟" | 不改变重复本身 |
| P0-4 失活状态机 | — | ❌ | 它只管"整段停了"（20 个时隙），不管 1–2 帧的凹陷 |
| §10.5 m 安全阀（+1） | ✅（顺带） | ✅ **把欠供转成超供** | 120 Hz 下 m=3→4 后，35 fps 也变成 140>120，**可见的重复变成不可见的丢弃** |
| P1-2 SwitchGuard | ❌ | ❌ | 它管 k 切换，不管 f 摆动 |

结论：**上侧只有 §10.3 能解；下侧现有条目都不够**（状态机只覆盖整段停，安全阀只覆盖持续欠供）。

### 11.3 更好的设计：控制与重采样分离 + 相位浮动 + 单侧偏置

**(a) 控制器只决定 m，重采样器决定每一帧**

```
m     ← 慢变量：f 的 p1/p5 分位 + 2–5% 余量，迟滞，只升不降（除非用户改）
每帧   ← 快变量：交 / 丢 / 浮 三个动作，由到达时刻与 due 的关系决定
```

现在的做法是用同一个 `f_ema` 既选 k 又驱动 pacer，于是 f 的摆动直接变成 k 的切换或
`late` 的累积。拆开之后，**摆动只被重采样器吸收，不再触发决策**。

**(b) 欠供：不要整格吸附，改成"立即交接 + 相位浮动"**

现在（`frame.cpp:91-96`）：

```cpp
++g_fgi_late;
due += (std::floor((now - due) / vb) + 1.0) * vb;   // 吸附到下一个 vblank
```

晚 0.2 vb 时它会**再等 0.8 vb**，代价是一整屏的重复 + 相位永久后移。
改成：

```cpp
if (now > due) {                       // 迟到：立刻交，不吸附
    g_fgi_late_ms += (now - due);      // 只记账
    due = now;                         // 相位从这里继续浮动
}
g_fgi_next_ms = due + k * vb;          // 批内跨 k·vb 不变
```

为什么更好：`Present(0)` 本来就被合成器量化到 vblank，**相位浮动不会让输出掉出 vblank**；
而积累的相位差会在若干批之后自然跨过一个 vblank 边界，形成**偶发的一次 2 vb 步**——
误差被摊成 `1,1,2,1,1,2…`，而不是"整整 1 vb 的定格"。这正是 105 fps 内容在 120 Hz 上
最不坏的表现。

代价：`due` 不再永远对齐 vblank（`grid_phase` 会缓慢漂移）。所以这条要和
**P1-1 的游戏时钟相位锚**一起用：相位以 `frame_qpc_ms + offset` 为目标，
允许在 ±1 vb 内浮动，超出才强制重锚。

**(c) 上侧：超供一律丢，且丢在"网格点"上**

抽帧门（§10.3）已经给了"丢"的动作，这里补一个关键细节：
**丢多少不是由 q 的瞬时值决定，而是由"下一个网格点之前有几个输入"决定**：

```
到 due 为止，如果我手上有 ≥2 个未处理输入 → 只留最新的一个，其余全丢
```

这样"丢"天然是均匀的（每批丢 0 或 1 个），且延迟恒为 1 个输入间隔，
不需要 q 这个额外状态。`q` 只用于**统计**和 m 的选择。

**(d) 单侧偏置：宁可超供，不可欠供**

| 失败方向 | 视觉表现 | 延迟 | 成本 |
|---|---|---|---|
| 超供（丢） | **几乎不可见**（画面内容更新更快，只是少看了几张） | 恒定 | 渲染卡白干 |
| 欠供（重复） | 可见的定格/顿挫，且**每次持续 1 vb 以上** | 抖动 | 无 |

所以 m 的选取应该**在"刚好够"的基础上再高 2–5%**（`m·f_p1 ≥ 1.02R`），
并且安全阀只允许 +1、不允许自动 −1。把系统**故意推到超供侧**，
是这条路线唯一能保证"长期不出可见顿挫"的办法。

### 11.4 与"主卡完全释放"的类比：其实自由运行更稳

用户提到的类比是对的，但方向值得强调：

| 工作点 | f 的摆动 | 落在哪一侧 | 主要失败模式 |
|---|---|---|---|
| 锁 40 + m=3 | 35–42（±9%，围绕 R/m） | **横跨边界** | 反复在"丢"和"重复"之间切换，两种都能看到 |
| 自由运行 + m=3 | 50–70（±17%，但整体在 R/m 之上） | **长期在超供侧** | 只有丢（不可见）；欠供只发生在负载尖峰 |

也就是说：**锁在均值上是最差的工作点**——它让系统长期骑在"昂贵失败"的边界上。
自由运行虽然摆幅更大、频率更高，但因为整体偏在"便宜失败"的一侧，
配合抽帧门反而**更稳定**。前提是 m 按 f 的**下分位**选，而不是按均值。

> 反过来说：如果一定要锁帧，正确的做法是锁在 `R/m` **之上一点**（例如 42–45 fps 目标、
> m=3），让限帧器工作在"经常超供"的一侧，而不是正好 40。这与"给驱动留 0.3 ms 余量"
> 是同一个思路（见 `OPTISCALER_FPS_PACING.md` §1.2）。

### 11.5 观测：唯一能直接看到这个问题的指标

现有报告只有 `arr`/`jitter`/`late`，看不到"步长"分布。新增（P0-5 的一部分）：

```
in_step      : 相邻"被保留输入"之间的间隔（vb），本仓应 ≈ k
out_step     : 每张输出在面板上占的 vblank 数，理想恒 1
drop%        : 被抽帧门丢掉的比例
underfill%   : max(0, R − m·f)/R
phase_err_vb : fmod(due − (game_t + offset), vb)，均值/标准差
```

判据：
- 超供场景 `in_step` 应恒 ≈ k，`out_step` 只有 `{1}`，或 `{1,2}` 且 2 的占比 ≈ `1 − R/(m·f)`；
- 欠供场景 `repeats/min` 应接近 `(R − m·f)/m`，且**不应出现连续 2 次以上**。

### 11.6 实验

| # | 改动 | 对照 | 通过标准 |
|---|---|---|---|
| E11 | 欠供改为"立即交接 + 相位浮动"（不吸附） | 现状（整格吸附） | 35–39 fps 场景下 `repeats/min` 下降、连续重复消失；`out_step` 出现均匀的 2 vb |
| E12 | 抽帧门改为"到 due 只留最新的一个" | 现状（等待/积压） | 41–42 fps 场景下 `age`/`total` p95 下降、`drop%`≈1−R/(m·f)、无积压 |
| E13 | m 按 p1 + 2–5% 余量选（并故意偏置到超供侧） | 按均值选 | `underfill%` < 1%、`repeats/min` ≈ 0；`drop%` 上升（预期） |

三者可以独立开关，也可以组合成"§10 自由运行"的完整形态。

### 11.7 一句话

**41/35 不是噪声，是"固定刷新 × 可变输入"的量化误差；它只能在重采样器里被摊开，
不能在控制器里被消除。** 正确的分工是：慢变量选 m 并故意偏向超供，
快变量在网格点上丢/交/浮，观测看 `in_step`/`out_step` 而不是 fps。

## 12. 再加一条硬上限：输出不得超过面板刷新率

### 12.1 需求形式化

```
C = min(R, 用户上限)         // 输出帧率硬上限
目标：presented ≤ C 恒成立，且尽可能接近 C
约束：m 固定（用户选定），面板固定刷新
```

和 §10/§11 相比，这条上限带来一个**结构性简化**：

> 上限不是靠"估计 q 再抽帧"来保证的，而是靠**槽位数量**保证的。
> 每秒只开 `C/m` 个输入槽，每槽最多交一张 → 输出恒等于 `m × C/m = C`，
> 与 f 怎么摆、q 怎么抖都无关。

也就是说，`q = C/(m·f)` 从"控制量"降级为"诊断量"。控制律变成：

```
slot_ms = m × 1000 / C              // 槽间隔；C=R 时恰好 = m·vb，C=R/2 时 = 2m·vb
slot_due 每 slot_ms 开一次（即每秒 C/m 次）
每槽：取"手上最新的一张"交接，其余同槽输入全部丢弃（计数 drop）
手上没有 → 等（有界），到位就交，next = handoff + slot_ms（相位浮动）
```

**注意 `slot_ms` 不是 `m·vb`**（除非 C=R）：上限低于刷新率时，槽间隔必须按 `C` 放大，
否则输出会回到 R。

由此还得到一条容易漏掉的配套：**`frameRenderTime` 必须喂"槽到槽"的间隔（≈`slot_ms`），
而不是 producer 的 `1/f`**。XeFG 用这个值决定把 m 张摊多开——喂 `1/f` 会让它把 3 张
挤在 1/f 里，输出瞬间超上限；喂 `slot_ms` 才能得到 `slot_ms/m = 1000/C` 的输出间距
（C=100、R=120 时即 1.2 vb，由面板量化成 `1,1,2…` 的均匀图案）。

### 12.2 三条不变式（都可以直接用日志测）

| 不变式 | 含义 | 测法 |
|---|---|---|
| **INV-1 上限** | 任意窗口 `presented ≤ C·Δt + 1` | `presents / vblanks ≤ 1.0`（C=R 时应 ≈1.000） |
| **INV-2 步长** | `C = R` 且 `m·f ≥ C` 时 `out_step` 恒为 1 vb；`C < R` 时 2 vb 占比 ≈ `1 − C/R` | 直方图 `{1: %, 2: %}` |
| **INV-3 欠供** | 只有 `m·f < C` 才出现重复，且不连续 | `repeats/min ≈ (C − m·f)/m` |

**INV-1 是关键**：它不依赖任何速率估计。只要"每槽最多交一张"，
即使 f 从 40 暴涨到 90，输出也不会超过 C——多余的输入被同槽丢弃。
这比"用 EMA 估计 q 再决定丢多少"稳得多（后者在 f 突增时会有几个槽的超调）。

### 12.3 结构影响：主循环要从"发布驱动"变成"槽驱动"

现在的循环是"一发布一帧、取最旧"（`main.cpp:1076-1080`），槽驱动需要：

```cpp
// 伪代码：每次循环
wait_for(publication_event || next_slot_due);   // 定时等待，MsgWaitForMultipleObjects
drain_newest();                                  // 把队列里所有新发布折成"最新一张"，
                                                 // 其余 ack + drop（同槽丢弃）
if (now >= next_slot) {
    if (have_stash) {
        handoff(stash);  stash = none;
        next_slot = max(now, next_slot) + slot_ms;   // 迟到就浮动，不吸附
    } else {
        ++underfill;                                 // 空槽：不动 next_slot（保留债务）
    }
}
```

与现状的差异（三处，都必须改）：

1. **等待要有超时**：没有新发布时也要在 `next_slot` 醒来（否则空槽无法计数、欠供无处体现）。
2. **同槽多帧只留最新**：这是 INV-1 的唯一保证点，也是延迟恒定的来源。
3. **`next_slot` 用 `max(now, next_slot) + m·vb`**：迟到浮动（§11.3b），不吸附到 vblank。

### 12.4 C 的取值：只有 `R/n` 是干净的

输出 C 帧/秒要摊到 R 个 vblank 上，只有 `C = R/n`（n 为整数）时才能**每帧 1 vb 均匀**；
否则必然出现"每 R/(R−C) 个 vblank 重复一次"的 Bresenham 图案：

| C（R=120） | C/R | 图案 | 观感 |
|---|---|---|---|
| 120 | 1.000 | 每 vb 一张 | 完美 |
| 60 / 40 / 30 | 1/2, 1/3, 1/4 | 每 n 个 vb 一张 | 完美（等效降刷新） |
| 100 | 0.833 | 每 6 个 vb 重复 1 次 | 轻微、均匀的顿感（50 ms 一次） |
| 90 | 0.750 | 每 4 个 vb 重复 1 次 | 同上 |
| 116（常见 VRR cap） | 0.967 | 每 30 个 vb 重复 1 次 | 几乎不可见 |

所以：**上限要么给 `R/n`，要么接受"均匀但可感知"的重复**。
如果用户就是想要"116 这种略低于刷新率"，那也没问题——Bresenham 会把它摊得很匀，
只是 `out_step` 里会有 ~3% 的 2 vb 步。

### 12.5 m 的取值：和"浪费"直接挂钩

上限把 m 的选择变成了一个**取舍**：

```
q = C / (m · f)                     // 需要保留的比例，也等于丢帧率
浪费 ≈ 1 − q                        // 渲染卡白干的比例
欠供风险 ≈ P(m·f < C)               // 只在 f 的下分位才可能
```

| 选法 | 结果 | 适用 |
|---|---|---|
| `m = ceil(C / f_p1)` | 几乎不欠供；f 高时浪费大（f=70, C=120, m=3 → 丢 43%） | **默认**（宁可丢，不可重复） |
| `m = ceil(C / f_p50)` | 浪费小，但一半时间在欠供侧 | 只在能接受少量重复时 |
| `m = 最小可行` + 安全阀 +1 | 折中：平时少丢，掉帧时 +1 把欠供转成超供 | 帧率波动大的游戏 |

关键提醒：**上限越紧（C 越小）或 m 越大，q 越小，MV 抽帧问题（§10.4①）越严重**。
f=70、C=120、m=3 丢 43% 时，相邻保留帧经常隔 2 个渲染帧——这时光流（或 producer 合并 MV）
不是可选项，而是**必须**。

### 12.6 与"完全释放主卡"的组合：两条合法路线

| 路线 | 渲染侧 | 消费侧 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. 全自由 + 消费端封顶**（推荐先试） | 不限帧，跑满 | 槽驱动 + 同槽丢弃，C=R | 主卡自由、延迟最低（内容最新鲜）、上限由结构保证 | 浪费大（1−q）；MV 抽帧问题最重 |
| **B. 渲染侧上限 + 消费侧吸收摆动** | `fakerFG` 里加绝对网格限帧到 `≈C/m + 3%`（OptiScaler `FpsLimiter` 的 QPC 绝对时隙，而不是相对 sleep） | 槽驱动，q 只在 ±5% 内波动 | 省电、省热、浪费小；`out_step` 几乎恒 1 | 游戏仍被限帧（违背"释放"）；需要往游戏进程注入限帧 |

如果用户的真实目标是"**别超过显示器上限**"而不是"主卡必须跑满"，路线 B 更划算；
如果目标是"主卡完全自由，只是画面别撕裂/超频"，路线 A 更直接。
两条路可以共存：B 作为省电档，A 作为性能档，用同一个槽驱动内核。

### 12.7 实验

| # | 改动 | 通过标准 |
|---|---|---|
| E14 | 槽驱动（同槽丢弃 + 定时等待 + 相位浮动），C=R，m 固定 | INV-1/2/3 全过；`presents/vblanks` ∈ [0.999, 1.001]；`out_step` 恒 1 |
| E15 | C 取非整除值（如 116 / 100） | `out_step` 的 2 vb 占比 ≈ 1 − C/R，且分布均匀（无连续 2 次） |
| E16 | 路线 A vs B（B 用 fakerFG 绝对网格限帧） | A：`age`/`total` p95 更低；B：`drop%` 更低、功耗/温度更低；两者 `out_step` 相同 |

### 12.8 一句话

**上限是这条链路里最便宜的一条约束**：它把"跟住 f"变成"开固定数量的槽"，
于是输出上限由结构保证（INV-1），不需要估计、不会超调。
代价是 `q = C/(m·f)` 的浪费和随之而来的 MV 抽帧问题——所以上限要么给 `R/n`，
要么接受均匀的 Bresenham 重复；m 要么按 `f_p1` 选（宁可丢），要么在渲染侧加一个
绝对网格限帧（省电档）。
