## What this actually shows

The capture side behaved identically everywhere: host loaded, queue wrapping installed, submit hook
fired, `wrap cpu:` lines every 300 submits, zero crashes on all four (after command lists stopped
being wrapped). No title was distinguished by our code.

The difference is upstream of us:

* `slIsFeatureSupported(DLSS-G)` is non-zero on the three titles **and on the second CP2077 run**, and
  the user reported exactly what that implies - the in-game frame-generation toggle is missing or
  refuses to switch on ("hardware not supported"). DLSS-G never runs, so nothing produces MV/depth.
  Cause: the survey package shipped `ArchSpoof=0`, so Streamline sees the real AMD architecture.
* CP2077 run 1 (`ArchSpoof=1`, answering 0x190) reports `= 0` and produces tags immediately - with
  frame generation still **off** in game. So the tag lane does not need FG to be running.

## Structural difference between titles (the real finding)

| group | how it publishes FG inputs | what we get |
|---|---|---|
| tag model (CP2077) | `slSetTag` with resource + open command list | MV, depth, hudless, camera - everything |
| NGX DLSS-G only (PBZ, Wuchang) | NGX parameter block | `dlssg_mv=0x0` in every eval; params carry no MV |
| older Streamline (Khazan) | `sl.interposer` without `slSetTagForFrame`, and `slSetTag` never called | nothing |

So "is FG acquisition consistent across games?" - no, and the split is exactly the same one this
project already hit on CP2077: only the tag lane carries buffers. The NGX route is empty by design.

## Correction (2026-11-12, evening) - the NGX row above is not a property of the API

The run that produced the table installed no enabler, so `slIsFeatureSupported(DLSS-G)` answered
"unsupported" **on every title except the `ArchSpoof=1` one**, and the game's frame generation was
never created. `dlssg_mv=0x0` is what an evaluate looks like when the feature is not running; it is
not evidence that the DLSS-G parameter block never carries motion vectors.

Consequences for this project (binding, see `docs/design/CAPTURE_RULES.md` rule 8):

* we no longer treat "the NGX DLSS-G lane is empty" as a design fact, and we do not gate on it;
* the survey must be repeated with an enabler installed and frame generation actually on
  (`dlssg_sm86` + `[capture] Claim=1`), which is also what the user asked for: prefer the game's own
  FG whenever it can run, because that is the most reliable declaration;
* the DLSS-G parameter block is a legitimate FG lane and should be usable as a *source*
  (`mgpu::kInputApiNvngxFg` exists but no source implements it yet) - until then, titles that only
  declare through NGX have no FG lane to read.
