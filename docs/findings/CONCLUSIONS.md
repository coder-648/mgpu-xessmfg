## 1. 这个 FG 到底消费什么

| 输入 | 是否被消费 | 证据 | 备注 |
|---|---|---|---|
| **彩色**（WGC 抓屏） | ✅ 必需 | 没有它什么都不生成 | `Color=0`，颜色走 WGC 而不是跨卡拷贝 |
| **运动矢量** | ✅ **消费**（旧结论是错的） | `--mv-shadow` 三组对照：游戏 MV vs 关 MV，画面不同 | 见 §2 |
| **jitter** | ✅ | 传游戏自己的 jitter 才对齐；`--fg-jitter-zero` 已弃用 | |
| **深度** | ⚠️ 官方要求，实测无画质差别 | 有无/延迟 1..3 帧都无差别，代价 2 ms | 别在这上面花时间 |
| **合成投影 / FOV / near-far** | ❌ 无差别 | 30° / 58.7° / 120° 三组画面一致 | 这个 build 不吃投影 |
| **帧时间** `frameRenderTime` | ✅ 影响节拍 | 必须喂"游戏自己的帧间隔" | §5.4 |

## 2. 运动矢量：三种来源，各有对的应用场景

2026-11-08 的 `--mv-shadow` 对照推翻了早期"MV 是死输入"的结论 —— XeFG **确实**
在读 tag 进去的 MV。但"能读"不等于"随便用都好"：

| 来源 | 渲染卡额外开销 | 适用 | 问题 |
|---|---|---|---|
| **AMD 光流**（`--fg-of`） | **0.3 ms** | **3x / 4x 首选** | 快转时边缘比游戏 MV 略脏 |
| 游戏 MV（`SkipMv=0`） | **+7.4 ms** | 2x 画质优先 | 3x/4x 会**闪烁**（见 §4） |
| 不用（`--no-mv`） | 0 | 预算最紧 | 快转时边缘更脏 |

方向已经验证过是对的：`--mv-flip`（反向）更差。

## 3. 三条硬约束（踩过的坑，别再踩）

1. **不要轮询跨卡 fence。** 跨适配器 fence 在消费节点上读出来是 `UINT64_MAX`，
   任何"等一下"都会变成空转，还会把游戏拖垮。要做同步只能靠 header 里发布的值
   （协议 v10 的 `FrameShared.published` / `SharedControl.consumed`）。
2. **不要读较旧的共享槽。** 槽位是"最新覆盖"语义，回读旧槽等于拿过期数据。
3. **不要自己配速。** `--pace` 默认关掉；XeFG 自己会配速，`Present()` 本身就阻塞
   ~15 ms（`docs/findings/FINAL_CONFIG.md` §5.3）。

## 4. 倍率：2x 是原生，3x 以上是"补丁"

`libxess_fg` 在这个 build 里只有 **2x 模型**。3x/4x/5x/6x 是靠
`--unlock-mfg` 解开数量限制后**把 2x 模型跑多遍**（`fg_keep_2x_model`）得到的。
后果：

- **3x/4x + 游戏 MV 会闪**，而且丢帧治不好它（三组不同丢帧率下闪烁一样）
  ⇒ 闪烁是 MFG 补丁的固有属性，不是你的配对/深度/MV 方向写错了；
- **光流不闪**，因为每对相邻帧的运动都由当帧重新算，不依赖游戏 MV 的时序；
- 所以定稿是：**3x 用光流**、**2x 用游戏 MV**。

## 5. 节拍：`frameRenderTime` 必须吸附到整 vblank（`--fg-rt-mode quant`）

输出间隔必须是整数个 vblank，否则"不卡但不匀"。这件事现在由 **`--fg-rt-mode quant`**
自动完成，也是 `bridge.exe` 的默认值：取实测输入间隔，四舍五入到整数个 vblank 再喂给 XeFG。

| 场景 | 实测间隔 | quant 吸附后 | 结果 |
|---|---|---|---|
| 2x，锁 60 fps | 16.0 ms（锁帧器 1 ms 粒度让间隔在 16/17 之间交替，中位数偏低） | **16.67 ms** = 2 vblanks | 120.0 fps = **1.00 vblank/帧** |
| 3x，锁 40 fps | **25.0 ms**（合成器时间戳，正好 3 vblanks） | **25.0 ms** = 3 vblanks | 120.0 fps = **1.00 vblank/帧** |

> 2026-11-08 修正：过去这一格写的是"3x 输入约 31 ms → 吸附 33.3 ms"。
> 31 ms 是**量出来的假数**：到达间隔原来用 `GetTickCount64` 的墙钟差值算，
> 1 ms 分辨率下同一毫秒内的两帧会丢一个样本，把中位数推高到 31，
> quant 于是吸附到 4 个 vblank，输出只有 96.8 fps。改成用 WGC 帧自带的
> `SystemRelativeTime` 之后中位数就是 25.0，实测 1.00 vblank/帧。
> 详见 `PERF_BASELINE.md` §3.7。


为什么必须吸附：16.0 ms 的 2x 输出是 **125 fps**，比 120 Hz 面板快 4%，
多出来的帧被合成器周期性丢弃（每 ~0.2 s 一次）；吸附到 16.67 ms 后正好 120.0 fps。

`--input-ms X` 现在**只影响 `load`/`slow` 统计**，不再参与 pacing（`quant` 用实测中位数）；
历史实现在 EMA 模式下才用它，实测 3x 下 `slow` 17→0、`skip` 19→13、**延迟不变**
（`docs/findings/FINAL_CONFIG.md` §5.18.1）。

### 5.1 固定倍数 vs 动态逐帧：为什么"固定"在游戏帧率抖动时不可能同样丝滑

固定倍数的输出是 `转发帧率 × 倍数`。转发率由 bridge 按队列深度 1 节流到 ~40 fps，
只要游戏在 30–55 fps 之间漂，输出就离开 120 Hz，必然出现空刷新（空洞 = 眼睛看到的顿）。
实测（固定 3x，`--fg-rt-mode auto`，同一场景交替 3 轮）：

| 场景 | 空刷新 | 最大空洞 |
|---|---|---|
| 平稳（游戏 ≈40 fps 稳定转发） | **0.1–0.3%** | 2 个 vblank |
| 游戏帧率在 48–56 fps 间漂 | 1.0–4.6% | 26–31 个 vblank |

动态逐帧（`--interp-cadence`）把这段抖动吸收掉，所以它更均匀——**这不是固定模式变差了**。
想让固定模式也接近满帧，就用 UI 里"锁帧"那行给出的建议值（`刷新率 / 倍数`），
或者直接换动态逐帧。

顺带排除的两个候选：`--fg-rt-mode ema`（把转发间隔的 EMA 喂给 pacer）配对测 3 轮
0.2/0.4/0.5%，比 `auto` 的 0.1/0.1/0.3% **更差**（平滑估计在速率真的变化时会滞后）；
`--cadence-hold`（限流改倍率）`gpu` 不变而空刷新翻倍，也是白丢刷新。

动态逐帧这边真正的修法是另一件事：**批次的长度和 pacer 的时间预算必须一致**。
输入不稳时 k 只能在 3/4 之间跳（35–45 fps 要 2.67–3.43 帧/真帧），k=4 的批次实际铺满
33.3 ms，而原来喂的是中位数 25.0 ms —— 4 帧被挤进 3 个 vblank 再空等 1 个，**每次 k=4 都是
一次可见的顿**，而空刷新计数器毫无反应（每个 vblank 都拿到了帧，只是帧的时间不对）。
现在默认 `--fg-cad-rt 1`：rt = 批次 × vblank，日志里显示 `cad:batch`。

## 6. 协议与构建必须同源

`kSharedVersion = 10`。add-on 与 `bridge.exe` **必须是同一次提交构建的**；
版本不匹配时两端会拒绝通信（这是故意的，旧版配新版会静默读垃圾）。
协议演进见 `docs/design/PROTOCOL.md`。

## 7. 性能口径（本机实测，供量级参考）

实测机器：渲染 RTX 3080 Ti，帧生成 RX 6750 GRE，120 Hz 面板。

| 项 | 量级 |
|---|---|
| 捕获 + 跨卡拷贝（无 MV、无颜色） | 数 ms |
| XeFG 单帧生成（4K） | §9.8 有实测反推 |
| 光流 | 0.3 ms |
| 游戏 MV 的额外开销（渲染卡） | 7.4 ms |
| 深度转换 | ~2 ms |
| 端到端延迟 | ~40–70 ms（随倍率/配置变） |

> 数字只说明量级，换卡/换游戏都会变。**不要把这些当成规格。**
> 完整基线（跨卡带宽、显存/总线流量、各项实测出处）、怎么看 `breakdown`、
> 以及还没做的优化候选：`docs/findings/PERF_BASELINE.md`。
