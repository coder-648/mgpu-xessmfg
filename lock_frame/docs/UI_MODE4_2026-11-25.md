# UI 合成（mode 4 / support patch）审查：渲染卡开销 + 小 UI 抖动

日期：2026-11-25。范围：`producer.cpp` 的 `synth_ui_dispatch()` + stream 4 稀疏编码 +
consumer 的 `record_ui_unblend()` / `unblend_ui.hlsl` / `patch_lut3d.*`。

## 0. 结论摘要

| # | 问题 | 结论 | 本轮动作 |
|---|---|---|---|
| 1 | patch 的编码/传输能否更省渲染卡 | 生成（synth dispatch）是主要成本，其中**覆盖率计数器/诊断的逐像素 atomic 每帧都在跑**；编码（稀疏）和传输（按支撑域）已经没有大空间 | 计数器改为每 N 帧一次（`UiStats`，默认 60）；暴露 `UiSynthThreshold`；给出下一步（hit-first / group gate / LUT 侧优化） |
| 2 | mode 4 下小 UI 移动时抖动 | 支撑是**二值 alpha（阈值 8/255）+ 不膨胀**，而 consumer 用 **7×7 盒平均 + smoothstep** 做羽化：小 UI 的权重按 1/49 步进变化，且淡边/孤立 UI 根本不在支撑里（H' 里留了 UI，mode 4 把它当场景插值） | 新增 `--ui-patch-hard-edge`（5×5 max 硬膨胀，默认关）做 A/B；暴露阈值 knob；列出 LUT 时间噪声作为次要怀疑 |

两个新 knob 都在 ini/CLI 里，**默认行为与之前完全一致**，可以逐项 A/B：

```ini
; fakerFG.ini（producer 侧）
UiSynthThreshold=8     ; 1/255 码值；调低 = 支撑覆盖更多淡边/孤立 UI
UiStats=60             ; 覆盖率计数器每 60 帧写一次（0=从不，1=每帧）
```
```
; consumer 侧
--ui-patch-hard-edge   ; 用 5x5 max 硬膨胀替代 7x7 盒羽化
```

## 1. 每帧链路（patch 模式）

```
producer（渲染卡）：
  synth_ui_dispatch        1 个全屏 dispatch: 读 P + H，PQ 解码/编码，写 R10 patch(alpha=binary)
  fr_encode_dispatch(4)    稀疏编码：每 32x8 tile 一个线程，空 tile 写 mode=3
  copy_begin_frame 等      （K，本轮未动）
consumer（插帧卡）：
  decode_ui_slot_from(4)   稀疏解码 -> g_hudless_local
  record_ui_occ            每 tile 1 个线程读 header
  record_patch_lut3d       stride=4 采样 + 33^3 原子累加 + fill（每帧，见 §2.4）
  record_ui_unblend        全屏 compose：H' = blend(present, LUT(patch), weight)
```

## 2. 问题 1：patch 生成/编码/传输的成本与优化

### 2.1 已做：覆盖率/诊断计数器从每帧改成每 N 帧

`synth_ui_full.hlsl` 原来每帧、每像素做：

- `InterlockedAdd(Stats[0/1])`：每个 UI 像素 2 次，全部命中**同两个地址**（4K、UI 覆盖率
  6% ⇒ ~50 万次/帧）；
- 每 8×8 像素再做一个诊断块：4 次额外的 `Hudless.Load` + 4 次 `InterlockedAdd`
  （~13 万组/帧，同样打在 4 个固定地址上）。

这些数字只被 `ui_stats_tick()` 以 **1 Hz** 读出来打一行日志（`ui-synth: coverage ...`），
所以每帧写是完全浪费。现在由 `UiStats`（默认 60）控制：默认每 60 帧写一次，
`StatsOn=0` 的帧连清零都不做（`synth` 的常量 12→13，`StatsOn` 传进去）。

预期：渲染卡每帧省掉几十万次 atomic（量级 0.3–0.8 ms，需要 `ProfGpu=1` 确认：
`prof: mv .. depth .. ui .. synth ..`）。

### 2.2 下一步（未做）：hit-first，非支撑像素不做 PQ 编码

现在 patch 分支对**每个像素**都算 `h_enc`（`to_pq_white` / `pq_encode`），即使
`hit == 0`；这些像素的 RGB 只被 consumer 的羽化用到。如果 §3 的 hard-edge 方案成立
（羽化不再采样支撑外的 RGB），就可以把编码移到 `hit` 判定之后，非 UI 像素只写 0：
4K 下省掉 ~94% 的编码工作。**依赖**：先确认 hard-edge 不引入可见接缝。

### 2.3 下一步（可选）：8×8 group gate

非 patch 分支已经有一个"每个 8×8 group 用 4×4 点采样做 gate"的路径（`g_ui_group_hit`），
patch 分支没有。给 patch 加同样的 gate（阈值取 `Threshold/2` 保守一点），非 UI group
直接 return，可省掉两次全屏 `Load`（P/H）。风险：细线 UI 可能被点采样漏掉——所以只作为
`UiPatchGroupGate=1` 的 A/B 项，不设默认。

### 2.4 consumer 侧的 LUT 开销（插帧卡，不是渲染卡，但顺带）

`patch_lut3d.hlsl` 每个 stride=4 采样点会做 **25 次 `Patch.Load`**（排除 ±2 px AA 环）
+ 4 次 atomic；4K 下 ~518k 采样点 ⇒ ~1300 万次纹理读/帧。可以改成从 `Occ`（已有）
推导"这个 tile 是否贴着支撑"，只在边界 tile 上做环形检查，内部 tile 直接跳过。
这条不影响渲染卡占用，但能降插帧卡负载（和 `load≈90%` 的场景相关）。

### 2.5 传输本身：没有大空间了

- patch 的 RGB 是"UI 下面的场景"，必须全分辨率、R10（PQ）否则 mode 4 的颜色对不上；
- 稀疏编码已经按 32×8 tile 只发非空 tile（CP2077 实测 UI 覆盖 6.4–6.8%），
  日志里的 `fr: coded ...` 是码流真实字节；
- alpha 只有 2 bit（R10 的 A2），只是"支撑/非支撑"，够用；想做"软 alpha"就得换 RGBA8，
  会丢掉 PQ 精度，不建议。

## 3. 问题 2：小 UI 移动时抖动（mode 4）

### 3.1 机制 A（首要怀疑）：支撑是二值 + 不膨胀，淡边/孤立 UI 留在 present 里

`synth_ui_full.hlsl` 的 patch 分支：

```hlsl
bool hit_b = (d > max(Threshold, 0.002f));       // 阈值默认 8/255
if (UseAlpha != 0) { hit_b = hit_b || (alpha > 0.002f); }
hit = hit_b ? 1.0f : 0.0f;
Ui[p] = float4(saturate(h_enc), hit);            // alpha 是 0/1
```

- **没有膨胀**：`Dilate` 参数只在非 patch 分支里用，patch 分支从没读过它；
- 阈值 8/255（相对 nits）意味着 UI 的 AA 软边、半透明光晕、细线文字**不在支撑里**；
- consumer 的 H' 在支撑外 = `present`，而 present **就是带 UI 的画面**。
  于是这些像素在 H' 里仍然是 UI → XeFG mode 4 认为"backbuffer 和 HUDless 一样"，
  把它们当场景 + 运动矢量插值 → 小 UI 的边缘/光晕被"拉丝"、随相机抖动。

为什么小 UI 明显：一个 10×10 的图标/准星，周长/面积比很高，软边和淡像素占比大；
大 HUD 面板的绝大多数像素都在支撑内部，本来就干净。

独立证据：`patch_lut3d.hlsl` 自己在采样时排除了 "±2 px AA ring"，注释写着
"Exclude the AA ring around support: present there can still contain UI." ——
作者已经知道 present 在支撑外 2 px 内还带 UI，但**合成时**却把这块 present 混进去了。

**验证/尝试**：把 `UiSynthThreshold` 调到 2（fakerFG.ini，重启游戏），
看小 UI 边缘是否变干净；如果改善，说明就是"支撑漏了淡边"。

### 3.2 机制 B：7×7 盒平均 + smoothstep 的权重是量化的

`unblend_ui.hlsl`（默认路径）：

```hlsl
float blend = saturate(u.a);                     // 0 或 1
if (blend < 0.5f) {
    float cov = 0;                               // 7x7 内支撑像素数 / 49
    ...
    blend = smoothstep(0.02f, 0.35f, cov);
}
```

`cov` 只能是 `k/49`。UI 每移动 1 px，边界处的 `cov` 跳 1–7/49，`smoothstep` 的结果
就在 0.9 和 0.3 之间跳。也就是说：**patch 和 present 的混合比例逐帧变化**。
mode 4 里 XeFG 用 `backbuffer - H'` 判 UI；混合比例变化会让"被判为 UI 的区域"
每帧形状/强度都不同 → 小 UI 的边缘看起来在抖（大 UI 时这条边界在画面里占比很小，
而且远离 UI 主体，看不出来）。

**本轮已做**：`--ui-patch-hard-edge` 换成 **5×5 的 max**（膨胀 2 px），权重只能是
**恰好 1 或 0**：1 px 的 UI 移动只会让边界整体平移，不会改变混合强度。过渡环落在支撑外
2 px（正是 `patch_lut3d` 认为 present 干净的位置），所以硬边只暴露 LUT 误差（通常 <1 code）。

### 3.3 机制 C（次要）：33³ LUT 每帧重建，没有时间平滑

`patch_lut3d.hlsl` 每帧只采样 1/16 的像素（`Stride=4`），按 H 码分到 33³=35937 个 cell
里做原子累加，`patch_lut3d_fill.hlsl` 每帧重算。平均 ~14 样本/cell，暗部 cell 常常只有
1–3 个样本：均值逐帧变化 → `LUT(patch)` 的颜色逐帧抖。对**小 UI**：被 patch 的区域小、
又常落在暗部，抖动直接出现在 UI 周围的场景上。

**建议**（未做）：给 LUT 加时间平滑（33³ 只有 36k texel，一个 ping-pong blend pass 成本
可忽略），或者按 `--lut3d-interval N` 每 2–4 帧重建并保持最后一张（同时省掉 §2.4 的成本）。
先做机制 A/B 的 A/B，再决定要不要动 LUT。

### 3.4 三者的判定顺序（成本从低到高）

1. `UiSynthThreshold=2`（只改 ini + 重启游戏）→ 若小 UI 边缘干净了，是机制 A；
2. `audit_ui_hard_edge.bat`（`--ui-patch-hard-edge`）→ 若抖动减轻，是机制 B；
3. 若 1、2 都没变，再做 LUT 时间平滑（机制 C）。

## 4. 部署与 A/B 步骤

本轮已构建并部署（producer 需重启游戏）：

- `xess_mfg_producer.dll`（`UiSynthThreshold` / `UiStats` / `StatsOn`）
- `lock_frame.exe`（`--ui-patch-hard-edge`）
- 游戏目录 `fakerFG.ini` 增加 `UiSynthThreshold=8`、`UiStats=60`
- 新脚本 `audit_ui_hard_edge.bat`（与 `audit_2_3x_keep2x_ui.bat` 相同，再加 hard-edge）

A/B 顺序（同场景、同转速，各 ~60 s）：

1. `audit_2_3x_keep2x_ui.bat`（基线，默认 feather）
2. 改 `UiSynthThreshold=2` 重启游戏 → 再跑一次 1
3. `audit_ui_hard_edge.bat`（hard edge，阈值保持 2）→ 再跑一次
4. 观察点：准星/小图标边缘的"毛刺/拖影"、UI 周围 2–7 px 的暗环是否闪、以及
   `prof: ... ui .. synth` 的耗时（`ProfGpu=1`）。

> 注意：`UiSynthThreshold` 与 hard-edge 都只影响 H'（插值帧里的 UI 保留区），
> 不会改变真实帧的 UI 像素；也不改协议。

## 5. 风险

- `--ui-patch-hard-edge` 在 LUT 误差较大的场景可能露出 2 px 的矩形接缝（默认关，A/B 用）；
- `UiSynthThreshold` 调低会略微扩大支撑区（更多 tile 非空 → 码流和编码成本上升）；
- `UiStats=1` 恢复旧行为（每帧写计数器），仅供对照；
- 本轮没有改 `record_patch_local` / `patch_gain`（这两条路径在默认配置下不启用）。



## 6. A/B 结果与第二轮改动（2026-11-25 深夜，CP2077 4K）

用户实测（阈值 2，`audit_2_3x_keep2x_ui.bat` vs `audit_ui_hard_edge.bat`）：

- 两者都比阈值 8 时**抖动更小** → 机制 A（支撑漏掉淡边/AA）确认；
- hard-edge 比默认 feather **更好** → 机制 B（1/49 量化权重）确认；
- 仍有**轻微**抖动 → 指向机制 C（每帧 LUT 噪声）。

producer 日志里的支撑覆盖率也印证了 A：阈值 8 时 6.4–6.8%，阈值 2 时 **8.5–11.2%**
（`ui-synth: coverage ...`），多出来的部分正是之前漏掉的软边。

### 6.1 本轮改动（consumer only，默认生效）

1. **hard edge 设为默认**（5×5 max 膨胀）。`--ui-patch-box-feather` 可回到旧的 7×7 盒羽化。
2. **LUT 直方图时间平滑**（机制 C）：
   - 新 shader `patch_lut3d_decay.hlsl`：每帧把 `LutSum`（H 码 → P 码的和 + 计数）按
     `Retain%` 衰减，而不是清零；
   - 新开关 `--ui-lut-decay N`（1..99，默认 **92** ⇒ ~12 帧记忆；`0` = 旧行为，每帧清零）；
   - 成本：36k cell × 4 word 的一次 dispatch，可忽略；`patch_lut3d_fill.hlsl` 未改。
   - 效果预期：`LUT(patch)` 的颜色不再逐帧跳，XeFG 用 `backbuffer - H'` 判出的 UI 区域
     也随之稳定 —— 这是"轻微抖动"最可能的残留来源。

### 6.2 下一步 A/B（若还有残留）

1. `--ui-lut-decay 0` 对照（应能看出差别；若没有差别，说明抖动不是 LUT 来的）；
2. `--ui-lut-decay 96`（更长记忆，更稳但跟随场景变化慢）/ `85`（更短）；
3. `UiSynthThreshold=1`（更激进地收淡边，字节略增）；
4. 若需要更宽的边界余量：把 hard-edge 从 5×5 扩到 7×7（2 px → 3 px），或改为
   producer 侧把支撑整体膨胀 2 px（consumer 就不再需要膨胀）。

## 7. 消费端 H' 重建的视觉 dump（2026-11-25 深夜）

`--tag-dump N`（`118_tag_dump.inc`）在 tag 之前抓 XeFG 实际收到的三张图，现在多了两张：

| 文件 | 内容 | 看什么 |
|---|---|---|
| `tag_XX_backbuffer.bmp` | 送 Present 的链缓冲 P（含 UI） | 基准画面 |
| `tag_XX_hudless.bmp` | **重建出的 H'** | 应该只有场景；如果还能看出 UI 形状，就是支撑漏了 |
| `tag_XX_patch.bmp` | 传输的 patch（画面下场景） | 黑块 = 该 tile 是直接从 P 拷的 |
| `tag_XX_alpha.bmp` | patch 的 alpha（= 支撑掩码） | 白色区域应完整覆盖 UI 并外扩 ~2 px |
| `tag_XX_diff.bmp` | **|P − H'| × 8**（灰） | 全黑最好；UI 轮廓内出现亮块 = H' 还留着 UI；边界一圈亮 = LUT/边界误差 |
| `tag_XX_meta.txt` | present id / slot / source / mode5 / patch / 尺寸 | 确认 source=patch、patch=1 |

注意：BMP 写的是 **R10 原始码值（PQ）**，没有做 PQ→sRGB，所以看起来会比屏幕亮/灰；
两张图用的是同一种编码，横向比较是有效的。

用法（`audit_ui_tagdump.bat` 已封装）：

```bat
lock_frame.exe --game Cyberpunk2077.exe --mode 3x --interp 2 --unlock-mfg
  --mfg-model=keep2x --streams=mv,depth --overlay-layered --wgc-minint 0 --pool 4
  --latency 1 --fg-rt-mode auto --report 40 --game-quirks apply
  --hudless-stream --ui-source off
  --tag-dump 8 --tag-dump-after 300 --tag-dump-dir "<game>udit_logs	agdump"
```

8 帧连续（第 300 帧起）足够看一个移动中的小 UI；每帧 3 张全分辨率回读约 100 MB，
共 ~0.8 GB 显存/内存，dump 完一次写盘。

判读顺序：

1. `alpha.bmp` 与 `backbuffer.bmp` 叠加：白色区域是否把 UI **完整**包住（含 AA/光晕）？
   有缺口 → 支撑问题（`UiSynthThreshold` 再降 / 支撑膨胀）；
2. `diff.bmp`：UI 区域内部是否有亮块 → H' 残留 UI；边界是否是稳定的细线 → LUT 误差；
3. 连翻 8 帧 `diff.bmp`：边界亮线的**强度是否逐帧变化** → 这就是肉眼看到的"轻微抖动"的来源
   （LUT 噪声 → `--ui-lut-decay` 调大；支撑边界跳 → 阈值/膨胀）。
